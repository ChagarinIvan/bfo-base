# Спецификация фичи: SPA-оплаты персоны

**Ветка фичи**: `016-persons-spa-payments`

**Создано**: 2026-09-05

**Статус**: Draft

**Входные данные**: перенос страницы оплат пользователя на SPA по паттернам
`015-persons-spa-management`.

## Контекст и границы

У персоны есть раздел оплат. Сейчас список оплат и форма добавления доступны через
Blade-маршруты из подробной страницы персоны. Фича переносит этот путь в SPA по
паттернам разделов персон, клубов, соревнований, групп и промптов: отдельный deep
link, единые loading/error/empty-состояния, auth guard и форма даты оплаты.

Канонический вход списка — /app/persons/{personId}/payments. Список и добавление
оплаты доступны только аутентифицированному пользователю, как и в legacy-пути.
Старые payment-only
Blade routes, actions и views удаляются после аудита usages; специальные redirects
для старых URL не создаются.

Поведение доменной оплаты не меняется: год определяется из даты, одна запись на
персону и год сохраняется через существующий create-or-update сценарий, а
`persons_payments` продолжает использоваться протокольными, ranking и другими
shared-сценариями.

В эту фичу не входят удаление оплаты, отдельное редактирование даты, изменение
схемы `persons_payments`, изменение правил допуска к соревнованиям и редизайн
подробной страницы персоны.

## Пользовательские сценарии и тестирование

### Пользовательская история 1 — просмотреть оплаты персоны (приоритет: P1)

Пользователь открывает оплаты из подробной страницы персоны и видит список оплат,
отсортированный по существующему правилу.

**Почему этот приоритет**: просмотр — основной путь раздела и позволяет проверить,
что SPA использует те же данные, что и legacy-страница.

**Независимая проверка**: открыть `/app/persons/3531/payments` для персоны с оплатами,
без оплат и для неизвестной персоны; проверить таблицу, пустое состояние и auth-aware
кнопку добавления.

**Сценарии приёмки**:

1. **Given** существует персона с несколькими оплатами, **When** пользователь открывает
   SPA-раздел, **Then** отображаются год, дата, created и updated для каждой оплаты.
2. **Given** персона не имеет оплат, **When** список загружен, **Then** отображается
   ясное пустое состояние без ошибки.
3. **Given** персона не существует или недоступна, **When** список загружается, **Then**
   API возвращает пустой paginated result без чтения оплат этой персоны.
4. **Given** пользователь не аутентифицирован, **When** он открывает список, **Then**
   SPA и API отклоняют вход стандартным auth-контрактом.

### Пользовательская история 2 — добавить или обновить оплату (приоритет: P1)

Аутентифицированный пользователь добавляет дату оплаты персоны через SPA-форму.
Если за год уже есть оплата, дата этой записи обновляется согласно существующему
create-or-update поведению.

**Почему этот приоритет**: это единственная mutation-операция текущей payment-страницы
и необходимый административный сценарий.

**Независимая проверка**: проверить auth guard, открытие формы, валидную дату, повторную
отправку для того же года, ошибки валидации и сохранение введённого значения.

**Сценарии приёмки**:

1. **Given** аутентифицированный пользователь открыл оплаты, **When** он нажимает
   «Добавить оплату», **Then** открывается SPA-форма с полем даты.
2. **Given** введена корректная дата, **When** форма успешно сохранена, **Then** оплата
   появляется в списке нужной персоны, а пользователь возвращается к списку.
3. **Given** за год уже существует оплата, **When** пользователь сохраняет другую дату
   того же года, **Then** существующая запись обновляется, а дубликат не создаётся.
4. **Given** дата пустая или имеет неверный формат, **When** форма отправлена, **Then**
   поле получает ошибку, а введённое значение не теряется.
5. **Given** запрос сохранения выполняется, **When** пользователь нажимает кнопку повторно,
   **Then** второй mutation-запрос не отправляется и форма показывает pending-состояние.
6. **Given** пользователь не аутентифицирован, **When** он пытается открыть или отправить
   форму, **Then** SPA/API используют стандартный auth-контракт проекта.

### Пользовательская история 3 — завершить миграцию payment-раздела (приоритет: P2)

Пользователь переходит к оплатам из подробной страницы персоны через SPA, а shared
сценарии продолжают использовать те же данные после удаления payment-only legacy.

**Почему этот приоритет**: миграция не должна оставлять два интерфейса или ломать
проверку оплаты в протоколах и рангах.

**Независимая проверка**: проверить ссылку из person details, отсутствие старых
payment-only routes/views/actions и регрессионные тесты shared consumers.

**Сценарии приёмки**:

1. **Given** открыта подробная страница персоны, **When** пользователь нажимает
   «Оплаты», **Then** открывается `/app/persons/{personId}/payments`.
2. **Given** старый payment URL запрошен напрямую, **When** запрос обработан, **Then**
   старый маршрут отсутствует и применяется стандартная обработка неизвестного маршрута.
3. **Given** payment domain/repository используется протоколом или ranking flow,
   **When** migration cleanup завершён, **Then** shared consumer продолжает работать.

### Граничные случаи

- Пустой список оплат показывает empty state, а не пустую таблицу без пояснения.
- Некорректный или отсутствующий `personId` возвращает стандартную API validation error;
  SPA отображает error state.
- Дата с неверным форматом или пустая дата возвращает полевую ошибку без потери ввода.
- Повторное сохранение даты того же года не создаёт вторую запись.
- Быстрые переходы между персонами не позволяют устаревшему ответу заменить актуальный список.
- Ошибки 401, 404 и 422 отображаются отдельно; downstream-запросы оплаты не создают N+1.

## Требования

### Функциональные требования

- **FR-001**: Система ДОЛЖНА предоставлять SPA-список оплат конкретной персоны по
  маршруту `/app/persons/{personId}/payments`.
- **FR-002**: Каждая строка ДОЛЖНА показывать год, дату оплаты и существующие created/updated
  impressions.
- **FR-003**: Список ДОЛЖЕН иметь стабильный порядок и единые loading/error/empty/not-found
  состояния с другими SPA-разделами.
- **FR-004**: Система ДОЛЖНА предоставлять аутентифицированному пользователю SPA-форму
  добавления оплаты из контекста конкретной персоны.
- **FR-005**: Сохранение ДОЛЖНО принимать только действующую дату и определять год из неё;
  ошибки должны возвращаться как полевые без потери ввода.
- **FR-006**: При повторном сохранении для того же person/year система ДОЛЖНА обновлять
  существующую запись, а не создавать дубликат.
- **FR-007**: Анонимный пользователь НЕ ДОЛЖЕН видеть или читать payment-раздел и НЕ ДОЛЖЕН
  выполнять mutation-операцию; SPA и API используют стандартный auth-контракт.
- **FR-008**: Ссылка «Оплаты» на подробной странице персоны ДОЛЖНА вести на новый SPA-маршрут
  с сохранением `personId`.
- **FR-009**: Старые payment-only Blade routes, actions, views и mount-код ДОЛЖНЫ удаляться
  только после аудита usages; redirects и дублирующий интерфейс не создаются.
- **FR-010**: Domain/Application/Repository-контур оплат и его shared consumers ДОЛЖНЫ
  продолжить работать; удаление payment-класса, используемого протоколом или ranking,
  запрещено без целевой замены.
- **FR-011**: Новые сценарии ДОЛЖНЫ соблюдать слои Application / Domain / Bridge / Infrastructure,
  не расширять legacy `app/Services` и не создавать новый legacy repository.
- **FR-012**: Изменения поведения ДОЛЖНЫ быть покрыты API/request и SPA-тестами; unit-тесты
  Application/Domain не создают Eloquent-сущности.
- **FR-013**: Список оплат и его API не должны создавать N+1 или загружать неограниченный
  набор связанных данных.

### Ключевые сущности

- **Персона**: владелец набора оплат; существующая сущность, не изменяемая этой фичей.
- **Оплата персоны**: дата оплаты, год, person id и created/updated impressions; уникальна
  по паре персона/год на уровне существующего application behavior.
- **Форма оплаты**: SPA-представление даты с validation и pending/error состояниями.
- **Legacy-артефакт оплат**: старый route, Blade view или action, удаляемый после аудита.

## Критерии успеха

### Измеримые результаты

- **SC-001**: 100% проверенных переходов из person details открывают SPA deep link и сохраняют
  корректный `personId` без полной перезагрузки страницы.
- **SC-002**: В 100% проверенных случаев список показывает те же оплаты, что и текущий domain
  query flow, включая пустой и not-found состояния.
- **SC-003**: Аутентифицированный пользователь создаёт оплату или обновляет дату существующего
  года в SPA без дубликатов и без потери введённой даты.
- **SC-004**: Неаутентифицированные пользователи не могут открыть payment-раздел, прочитать
  список или выполнить mutation.
- **SC-005**: После миграции payment-only legacy routes/actions/views не имеют рабочих production
  usages, а shared protocol/ranking consumers проходят регрессионную проверку.
- **SC-006**: Список оплат выполняется ограниченным числом запросов, не создающим запрос на каждую
  строку или связанную сущность.

## Предположения

- Существующие `PersonPayment`, repository, factory и Application create-or-update service
  являются источником истины; новая фича добавляет только необходимые API и SPA adapters.
- Существующий auth middleware, API serialization, request validation и Vue/PrimeVue patterns
  переиспользуются без новых зависимостей.
- Список оплат использует общий paginated SPA-контракт с optional year filter; API не должен
  строить запросы на каждую строку.
- Legacy detailed person page остаётся Blade-страницей; меняется только ссылка на payment-раздел.
- Удаление оплаты и редактирование оплаты вне create-or-update по году остаются за пределами фичи.

API списка использует query-параметры `personId`, `year`, `page` и `perPage`.
Mutation использует `POST /api/v1/persons/payments`, где `personId` является
обязательным полем body. Фильтр года в payment SPA использует общий компонент
year-filter и тот же список доступных годов, что и остальные paginated страницы.
