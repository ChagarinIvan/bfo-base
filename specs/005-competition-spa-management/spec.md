# Спецификация фичи: Управление соревнованиями в SPA

**Ветка**: `005-competition-spa-management`

**Создан**: 2026-08-30

**Статус**: Черновик

**Входные данные**: «Поэтапно переносить страницы на новый SPA-фронтенд, улучшая уже
перенесённые страницы; в этом этапе развить раздел соревнований, его поиск, просмотр и
управление, а также расширить навигацию». 

## Контекст и границы

Проект постепенно переносит разделы с существующего сайта в SPA. Этот этап завершает следующий
вертикальный срез раздела соревнований: пользователь находит соревнование, открывает его
страницу с этапами, а аутентифицированный пользователь создаёт, редактирует или мягко удаляет
соревнование. Старые страницы и ссылки на них остаются рабочими; они используются для действий,
которые ещё не перенесены в SPA.

Полная замена Blade-раздела соревнований и очистка относящегося к нему legacy-кода выполняется
позже, когда SPA покроет весь раздел, включая оставшиеся операции с этапами. В этом этапе не
создаются SPA-страницы создания, редактирования и просмотра отдельных этапов.

Раздел флагов намеренно не добавляется в SPA navbar: его навигационный пункт будет удалён вместе
с самим разделом в отдельной будущей работе.

## Clarifications

### Session 2026-08-30

- Q: Какой результат должен получать аутентифицированный запрос списка соревнований и событий без параметра `active`? → A: Параметр `active` не входит в API и DTO; репозитории всегда возвращают только активные записи. Работа с удалёнными записями откладывается в отдельную спеку.
- Q: Как считать `participantsCount` у этапа, если один спортсмен может иметь несколько строк протокола? → A: Количество строк протокола, как в существующем Blade через `protocolLines->count()`.

## Пользовательские сценарии и тестирование *(обязательный раздел)*

### User Story 1 — Найти соревнование (Приоритет: P1)

Посетитель открывает список соревнований, выбирает год и быстро сужает список по части названия
или по дате. Он видит только соревнования, которые соответствуют всем выбранным фильтрам.

**Почему этот приоритет**: Поиск — основной способ найти нужное соревнование в растущем списке и
основа для последующего просмотра или управления им.

**Независимый тест**: Открыть список без авторизации, выбрать год, ввести не менее трёх символов
названия и выбрать дату; убедиться, что отображаются только подходящие соревнования, а неверные
параметры не приводят к ошибке страницы.

**Сценарии приёмки**:

1. **Дано** посетитель открыл список соревнований, **Когда** он вводит не менее трёх символов
   названия и завершает ввод, **Тогда** список обновляется без полной перезагрузки и содержит
   соревнования, в названии которых есть введённый текст.
2. **Дано** посетитель выбрал дату, **Когда** список обновляется, **Тогда** в него входят
   соревнования, у которых выбранная дата находится в диапазоне от даты начала до даты окончания
   включительно.
3. **Дано** посетитель задал несколько фильтров, **Когда** список обновляется, **Тогда**
   применяются все фильтры одновременно.
4. **Дано** в поле названия введено один или два символа, **Когда** пользователь прекращает ввод,
   **Тогда** поиск по названию не отправляется и пользователь видит подсказку о минимальной длине.
5. **Дано** клиент всё же передал слишком короткий текст поиска, **Когда** запрос обработан,
   **Тогда** система отклоняет параметр как невалидный понятным стандартным ответом.

### User Story 2 — Просмотреть соревнование и его этапы (Приоритет: P1)

Посетитель открывает соревнование из списка и видит отдельную SPA-страницу с основной
информацией и таблицей его этапов. Ссылки и действия, которые ещё не перенесены, ведут на
соответствующие существующие страницы.

**Почему этот приоритет**: Страница соревнования объединяет путь от списка к данным этапов и
является следующим самостоятельным экраном мигрируемого раздела.

**Независимый тест**: Открыть соревнование с несколькими этапами из SPA, проверить их названия,
даты, описания и ссылки на существующие страницы; открыть соревнование без этапов и убедиться,
что показано понятное пустое состояние.

**Сценарии приёмки**:

1. **Дано** посетитель нажимает название соревнования в SPA-списке, **Когда** страница
   открывается, **Тогда** он остаётся в SPA и видит сведения о выбранном соревновании.
2. **Дано** у соревнования есть этапы, **Когда** открыта страница соревнования, **Тогда** они
   отображаются в таблице с названием, описанием, датой и количеством участников.
3. **Дано** посетитель нажимает ссылку этапа, **Когда** соответствующая
   функция ещё не перенесена в SPA, **Тогда** открывается корректная существующая страница, а не
   неработающий SPA-маршрут.
4. **Дано** у соревнования нет этапов, **Когда** открыта его страница, **Тогда** показано явное
   пустое состояние.
5. **Дано** посетитель пытается открыть несуществующее или мягко удалённое соревнование,
   **Когда** запрос завершён, **Тогда** он получает понятное сообщение и может вернуться к списку.

### User Story 3 — Управлять соревнованием (Приоритет: P2)

Аутентифицированный пользователь редактирует существующее соревнование той же формой, которой
оно создаётся, либо подтверждает его удаление. Удалённое соревнование исчезает из рабочих
списков, но остаётся сохранённым в системе.

**Почему этот приоритет**: Редактирование и безопасное удаление позволяют поддерживать данные
соревнований актуальными, не возвращаясь в старый интерфейс для базовых операций.

**Независимый тест**: Войти в SPA, открыть строку соревнования, изменить данные и проверить их
после возврата в список; затем подтвердить удаление другого соревнования и убедиться, что оно
больше не видно, но не удалено физически.

**Сценарии приёмки**:

1. **Дано** пользователь аутентифицирован, **Когда** он открывает действия строки,
   **Тогда** доступны «Рэдагаваць» и «Выдаліць».
2. **Дано** пользователь выбрал редактирование, **Когда** открывается форма, **Тогда** она
   заполнена текущими данными соревнования и использует те же поля и правила, что создание.
3. **Дано** пользователь сохраняет валидные изменения, **Когда** операция завершается,
   **Тогда** видит подтверждение, а список и страница соревнования показывают новые данные.
4. **Дано** пользователь выбирает удаление, **Когда** появляется подтверждение, **Тогда** до
   явного подтверждения данные не меняются.
5. **Дано** пользователь подтверждает удаление, **Когда** операция завершается,
   **Тогда** соревнование скрыто из обычного списка и недоступно как рабочее, но его запись не
   уничтожена физически.
6. **Дано** посетитель не аутентифицирован, **Когда** он открывает список или пытается выполнить
   прямое действие редактирования либо удаления, **Тогда** действий в интерфейсе нет, а операция
   не выполняется.

### User Story 4 — Перемещаться между SPA и существующими разделами (Приоритет: P3)

Пользователь видит в SPA тот же набор разделов верхней навигации, что и на существующем сайте.
Уже перенесённые разделы открываются в SPA, остальные — на существующих страницах без потери
доступа к функциям.

**Почему этот приоритет**: Единая навигация делает SPA пригодным для ежедневного использования в
период постепенной миграции.

**Независимый тест**: Проверить navbar без входа и после входа; перейти по каждому пункту и
убедиться, что он открывает либо работающий SPA-раздел, либо соответствующий существующий раздел.

**Сценарии приёмки**:

1. **Дано** посетитель находится в SPA, **Когда** он открывает верхнюю навигацию, **Тогда** видит
   разделы соревнований, кубков, спортсменов, клубов и разрядов.
2. **Дано** пользователь аутентифицирован, **Когда** он открывает верхнюю навигацию, **Тогда**
   дополнительно видит доступные ему группы, справку, API-справку и регистрацию.
3. **Дано** пункт ещё не имеет SPA-страницы, **Когда** пользователь его выбирает, **Тогда**
   ссылка ведёт на существующую страницу этого раздела.
4. **Дано** пункт соревнований уже имеет SPA-маршрут, **Когда** пользователь его выбирает,
   **Тогда** переход происходит внутри SPA.

### User Story 5 — Собрать повторно используемый интерфейс (Приоритет: P4)

Разработчик может использовать одинаковые простые элементы действий, иконки, подтверждения и
представление служебной информации на нескольких SPA-страницах без копирования поведения и
визуального оформления.

**Почему этот приоритет**: Повторное использование снижает расхождения между страницами по мере
миграции разделов.

**Независимый тест**: Открыть список, форму и страницу соревнования; проверить, что одинаковые
действия и представление служебной информации выглядят и работают одинаково.

**Сценарии приёмки**:

1. **Дано** одно и то же действие доступно в нескольких местах, **Когда** пользователь его
   использует, **Тогда** его подпись, иконка, доступность и сообщение о результате согласованы.
2. **Дано** добавляется новая SPA-страница, **Когда** ей нужны уже существующие простые элементы,
   **Тогда** разработчик может использовать их без дублирования их поведения.

### Граничные случаи

- Поиск по названию содержит пробелы, смешанный регистр или символы разных алфавитов: сравнение
  не зависит от регистра, ведущие и хвостовые пробелы не меняют смысл поиска.
- Выбранная дата совпадает с датой начала или окончания многодневного соревнования: оно входит в
  результат.
- После смены фильтра страница пагинации, которой больше нет, сбрасывается на первую доступную.
- Запросы к несуществующему, уже удалённому или параллельно удалённому соревнованию не изменяют
  данные и возвращают понятную ошибку.
- У аутентифицированного пользователя истёк токен во время редактирования или удаления: операция
  не выполняется, пользователь проходит обычный вход заново.
- В таблице этапов нет дополнительных запросов на каждую строку; страницы с большим числом этапов
  остаются пригодными для просмотра.

## Требования *(обязательный раздел)*

### Функциональные требования

- **FR-001**: Система ДОЛЖНА позволять фильтровать список соревнований по фрагменту названия.
  Фрагмент имеет минимум три значимых символа; поиск не зависит от регистра и применяется после
  короткой паузы в вводе пользователя.
- **FR-002**: Система ДОЛЖНА проверять на сервере минимальную длину поискового фрагмента и
  возвращать стандартную ошибку валидации для более короткого непустого значения.
- **FR-003**: Система ДОЛЖНА позволять фильтровать соревнования по одной дате; соревнование
  подходит, если дата входит в его диапазон дат включительно.
- **FR-004**: Система ДОЛЖНА сочетать фильтры года, названия и даты, а также сохранять
  постраничное отображение результатов.
- **FR-005**: Система ДОЛЖНА предоставлять публичный просмотр одного активного соревнования и
  публичный список его активных этапов.
- **FR-006**: Таблица этапов ДОЛЖНА содержать как минимум название, описание, дату и количество
  строк протокола как число участников; не перенесённые действия и ссылки ДОЛЖНЫ вести на корректные
  существующие страницы.
- **FR-007**: Система ДОЛЖНА предоставлять аутентифицированному пользователю возможность получить
  текущие данные одного активного соревнования для редактирования, сохранить изменения и получить
  обновлённое представление соревнования.
- **FR-008**: Форма редактирования ДОЛЖНА использовать те же поля и правила, что форма создания:
  название, описание, дату начала, дату окончания и признак массового старта. Дата окончания не
  может быть раньше даты начала.
- **FR-009**: Система ДОЛЖНА показывать действия редактирования и удаления только
  аутентифицированному пользователю и ДОЛЖНА отклонять соответствующие прямые запросы без
  аутентификации.
- **FR-010**: Удаление соревнования ДОЛЖНО требовать явного подтверждения в интерфейсе и
  выполняться как мягкое удаление: запись и связанные исторические данные не удаляются физически.
- **FR-011**: После мягкого удаления соревнование и его этапы не ДОЛЖНЫ возвращаться ни в одной
  операции чтения этой фичи; параметр `active` не принимается V1 API и не входит в search DTO.
- **FR-012**: SPA navbar ДОЛЖЕН включать пользовательские пути соревнований, кубков, спортсменов,
  клубов, разрядов, а после входа — групп, справки, API-справки и регистрации. Раздел флагов
  намеренно исключён. Путь ведёт в SPA, если соответствующая страница уже перенесена, иначе — на
  существующую страницу.
- **FR-013**: Повторяющиеся простые элементы действий, иконки, подтверждение удаления и
  представление служебных данных ДОЛЖНЫ быть доступны для повторного использования на SPA-страницах.
- **FR-014**: Новые операции чтения и изменения ДОЛЖНЫ выдавать понятные стандартные ответы для
  успешного результата, ошибки валидации, отсутствия данных и отсутствия аутентификации.
- **FR-015**: Все query-параметры и поля JSON request body V1 API ДОЛЖНЫ использовать `camelCase`,
  включая `perPage` и `competitionId`. Имена legacy API, PHP-свойств и Eloquent-колонок не меняются.

### Архитектурные и миграционные ограничения

- **AR-001**: Новые операции реализуются в целевых слоях Application, Domain, Bridge и
  Infrastructure. Новый HTTP action принимает DTO, передаёт его через command в Application
  use case, который использует доменные правила и возвращает view DTO через assembler.
- **AR-002**: Новые маршруты и actions остаются изолированными в версии V1; существующие
  Blade-маршруты и legacy API не меняются, кроме целенаправленной замены страницы после полного
  покрытия соответствующего раздела.
- **AR-003**: Список этапов загружает необходимые связанные данные ограниченным числом запросов;
  N+1-запрос на строку этапа запрещён. Во время разработки это один раз проверяется через query
  listener или лог запросов для одного и нескольких этапов; отдельный unit/request-тест на число
  SQL-запросов не требуется.
- **AR-004**: Изменение поведения покрывается request-тестами и frontend-тестами. Полный набор
  PHPUnit запускается на завершении спеки или после большого логического этапа; в итерациях
  применяются точечные проверки.

### Ключевые сущности

- **Соревнование**: событие с названием, описанием, диапазоном дат, годом, признаком массового
  старта и служебной информацией о создании и обновлении; может быть активно или мягко удалено.
- **Этап**: часть соревнования с названием, описанием, датой и количеством участников, равным
  числу строк протокола; принадлежит одному соревнованию.
- **Фильтр соревнований**: сочетание года, фрагмента названия, одной даты и страницы результатов.
- **Действие управления**: редактирование или подтверждённое мягкое удаление активного
  соревнования, доступное только аутентифицированному пользователю.

## Критерии успеха *(обязательный раздел)*

### Измеримые результаты

- **SC-001**: Посетитель может найти нужное соревнование по названию или дате и открыть его
  страницу не более чем за три действия после открытия списка.
- **SC-002**: Все корректные комбинации фильтров отображают только соответствующие соревнования;
  пограничные даты начала и окончания включаются в результат в 100% проверенных сценариев.
- **SC-003**: Аутентифицированный пользователь завершает редактирование или подтверждённое
  удаление соревнования без перехода в существующий интерфейс; неаутентифицированный пользователь
  не может завершить ни одну из этих операций.
- **SC-004**: Для соревнования с этапами SPA-страница показывает все необходимые данные этапов без
  отсутствующих связанных данных и без отдельного запроса к данным для каждой строки.
- **SC-005**: Все пункты верхней навигации из FR-012 остаются достижимыми из SPA; каждый ведёт на
  работающую SPA- или существующую страницу.
- **SC-006**: После подтверждённого удаления соревнование отсутствует в обычном списке и публичном
  просмотре, при этом его историческая запись сохраняется.

## Предположения

- Любой аутентифицированный пользователь может редактировать и мягко удалять соревнования; роли и
  ownership-проверки в этом этапе не вводятся.
- Поиск по названию использует подстрочное сопоставление, а дата фильтра — одно календарное
  значение, а не произвольный диапазон.
- Пауза перед поиском по названию составляет около 300 миллисекунд и не меняет результат поиска.
- Новый SPA-маршрут просмотра соревнования имеет вид `/app/competitions/{id}`; ссылка этапа и
  другие пока неперенесённые функции остаются существующими URL.
