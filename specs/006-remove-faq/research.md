# Исследование: удаление FAQ-раздела

Фича: 006-remove-faq
Дата: 2026-08-31

## Решение: удалить оба пути к представлениям FAQ

В репозитории есть две страницы legacy Blade:

- /faq -> ShowFaqAction -> resources/views/faq/index.blade.php;
- /faq/api -> ShowApiFaqAction -> resources/views/faq/api.blade.php.

В SPA нет собственных FAQ-страниц. Меню справки для авторизованных пользователей
содержит ссылки на эти legacy URL через authenticatedHelpNavigation.

Обоснование: обе страницы явно входят в область задачи и не имеют замещающего
контента. После удаления маршрутов прямой доступ к ним будет обрабатываться как
обычный запрос к отсутствующему маршруту.

Рассмотренные альтернативы: перенаправление на другую страницу справки отклонено,
поскольку замена не запрошена и отсутствует. Удаление только ссылок отклонено,
поскольку устаревшие страницы остались бы доступны по прямому URL.

## Решение: удалить состояние навигации, используемое только FAQ

Модель навигации SPA содержит spa.nav.faq и spa.nav.api; макет SPA отображает их
через authenticatedHelpNavigation. Navbar Blade импортирует два FAQ action-класса,
отображает обе ссылки и использует isFaqRoute и isFaqApiRoute для выделения меню
справки. Базовые Action и AbstractAction передают эти флаги через данные navbar.

Обоснование: после удаления маршрутов записи навигации и флаги активного состояния
не имеют потребителей и должны быть удалены вместе. Остальные группы навигации и
поведение авторизации должны остаться без изменений.

Рассмотренные альтернативы: сохранение пустого меню справки отклонено, поскольку
в навигации осталось бы оформление без пунктов назначения.

## Решение: удалить переводы только для FAQ и сохранить общие переводы

Единственные потребители app.faq.*, app.api.*, app.navbar.faq, app.navbar.api,
spa.nav.faq и spa.nav.api — FAQ-представления и navbar либо модель навигации SPA.
app.navbar.help и spa.nav.help также являются подписями меню FAQ и станут
неиспользуемыми после удаления всего меню справки. Остальные ключи app.api и
навигации нужно сохранить, если поиск по всему репозиторию найдёт их потребителя
вне FAQ.

Обоснование: очистка переводов должна основываться на использовании, а не на
одном только префиксе ключа.

## Решение: перед удалением проверить фактические legacy API endpoints

Страница API FAQ описывает старые endpoints, например /api/competitions,
/api/competition/{competition_id}/events, /api/event/{event_id}/results,
/api/club и /api/person. Аудит маршрутов, тестов и фронтенд-кода показал, что
`/api/person` используется legacy SPA, а `/api/persons` проверяется отдельным
тестом; остальные четыре endpoint не имеют внутренних потребителей вне FAQ.

Обоснование: удаление страницы документации не должно автоматически удалять
используемый приложением endpoint. Каждый кандидат на удаление контроллера или
маршрута был проверен поиском по всему репозиторию и сопоставлением с маршрутами
и тестами. Внешние клиенты без следов в репозитории в рамках этого аудита не
учитывались.

Рассмотренные альтернативы: удаление всего провайдера legacy API отклонено,
поскольку это удалило бы используемые `/api/person` и `/api/persons`, а также
нарушило бы несвязанные тесты.

## Решение: регрессионное покрытие границ навигации и маршрутов

Добавить или обновить тесты модели навигации SPA и доступности legacy-маршрутов.
Проверки должны подтверждать отсутствие /faq и /faq/api, отсутствие пунктов FAQ в
меню и работоспособность показательных несвязанных маршрутов. Добавить проверку
поиском по репозиторию удалённых имён и запустить стандартные проверки качества
PHP и фронтенда.

Обоснование: это внешне наблюдаемые удаления; проверка только факта удаления
файлов не подтверждает исчезновение старых URL и ссылок меню.
