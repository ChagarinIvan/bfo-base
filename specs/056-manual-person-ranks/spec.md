# Feature specification: Ручные выполнения разрядов

**Feature Branch**: `056-manual-person-ranks`, создана по запросу пользователя
**Created**: 2026-11-08
**Status**: Implemented and locally validated
**Input**: Добавить независимый от протоколов источник разрядов спортсмена: разряд,
дата выполнения и дата активации. Он участвует в построении истории и не теряется
при полном перерасчёте. На странице разрядов доступны добавление и удаление.

## Clarifications

### Session 2026-11-08

- Q: Считать ли ручной юношеский разряд подтверждённым без birthday? A: Да, ручные разряды имеют абсолютное значение относительно возрастного фильтра; даты и общие периоды действия сохраняются.
- Q: Какие операции нужны для ручной записи? A: Добавление и удаление, без редактирования.
  Удаление реализуется выключением с сохранением аудита согласно конституции.

## User scenarios & testing

### User story 1: Добавление известного разряда, P1

Авторизованный сотрудник на странице разрядов спортсмена вводит известное выполнение,
когда протокола/соревнования нет в системе. Это постоянный исходный факт расчёта.

Independent test: спортсмен без протоколов получает ручное выполнение, историю и
соответствующий действующий разряд после добавления и двух полных перерасчётов.

1. Given спортсмен без стартов, when сотрудник указывает разряд и две даты, then
   ручное выполнение сохранено, видно в истории и участвует в текущем разряде.
2. Given смешанные протокольные/ручные выполнения, when выполнен полный пересчёт,
   then оба источника формируют одну историю по правилам повышения/продления/истечения.
3. Given ручная запись, when очищены или заменены протоколы, then запись не удаляется.
4. Given историческое выполнение с истёкшим сроком, when оно добавлено, then оно видно
   в истории, но не становится действующим вопреки обычным срокам.

### User story 2: Удаление ошибочного ручного выполнения, P1

Авторизованный сотрудник удаляет только ручной источник. Отмена записи пересчитывает
историю по оставшимся фактам и сохраняет аудит исходной записи.

Independent test: удалить ручной разряд, пересчитать дважды, проверить исчезновение
его влияния и сохранение протокольных выполнений.

1. Given ручное выполнение, when удаление подтверждено, then запись выключена,
   история и текущий разряд пересчитаны без неё в той же атомарной операции.
2. Given протокольная строка, when открыта история, then действие удаления ручного
   выполнения для неё отсутствует; protocol activation actions сохраняются.
3. Given подмена ID спортсмена или отсутствующий/выключенный источник, when вызвано
   удаление, then API возвращает not found без изменения чужих данных.
4. Given ошибка сохранения/расчёта, when операция завершается неуспешно, then
   источник, история и текущий разряд остаются в прежнем committed состоянии.

### User story 3: Понятное происхождение и доступ, P2

История различает ручные и протокольные выполнения без фиктивных соревнований и ссылок.

Independent test: открыть смешанную историю гостем и авторизованным пользователем.

1. Given ручное выполнение, when история показана, then указано «дададзена ўручную»,
   видны разряд и даты, отсутствуют фиктивные ссылки на протокол/соревнование/кубок.
2. Given гость, when история открыта, then источник читается по существующим правилам
   публичной истории, а добавление/удаление недоступны и через UI, и через API.
3. Given допустимая форма, when сохранение выполняется, then повторная отправка
   заблокирована; ошибка показывает сообщение и сохраняет введённые значения.

### Edge cases

- WithoutRank не является выполнением и не принимается как ручной разряд.
- Дата активации не раньше выполнения; обе даты обязательны, точность до дня.
- Дата выполнения не в будущем. Будущая активация допустима и не влияет на текущий
  разряд до указанного дня; ежедневный расчёт должен найти такую запись.
- Ручное выполнение не является участием в старте и не учитывается в правиле IIIю за три старта.
- Два источника в один день имеют детерминированный порядок, повторный rebuild стабилен.
- Повторное добавление той же активной ручной записи с теми же тремя полями отклоняется;
  после удаления можно снова добавить её. Автоматически объединять ручные и протокольные
  выполнения нельзя: принадлежность одному основанию неизвестна.
- Ежедневная очистка спортсменов без стартов/платежей не выключает спортсмена с активным ручным выполнением.
- Неактивный спортсмен не получает новые выполнения. При его выключении ручной источник
  остаётся сохранённым; через публичный API недоступен вместе со спортсменом.

## Requirements

- **FR-001**: Система MUST хранить ручные выполнения отдельно от производной истории,
  с привязкой к спортсмену, разрядом, датой выполнения и активации, active и created/updated Impression.
- **FR-002**: Все пути расчёта MUST читать активные ручные и допустимые протокольные факты:
  ручной rebuild, refill, ежедневный, обработка/очистка протокола и перепривязка спортсмена.
- **FR-003**: Ручные факты MUST использовать общие правила сроков, продления, повышения
  и определения текущего разряда. Явная дата активации сохраняется при любом расчёте;
  месячное ожидание новых протоколов к ней не применяется.
- **FR-004**: Ручные факты MUST NOT считаться участиями при вычислении IIIю за три старта.
- **FR-005**: API MUST поддерживать authenticated добавление и удаление, без редактирования;
  валидировать rank/dates/duplicate и ownership спортсмена. Гость не может изменять данные.
- **FR-006**: Изменения источника и результата MUST быть атомарны под lock спортсмена.
  Ошибка откатывает source/projection/metadata, без частичного успеха.
- **FR-007**: Создание/выключение MUST быть намеренными domain transitions, записывать
  audit и domain event. События публикуются один раз после успешного сохранения;
  обработчики, читающие состояние, работают после commit. Физическое удаление запрещено.
- **FR-008**: История MUST содержать явный тип источника и ID ручного выполнения;
  protocol/distance/event/competition IDs у ручных строк nullable без фиктивных сущностей.
- **FR-009**: SPA MUST добавлять ручное выполнение и удалять его с подтверждением
  на существующей странице разрядов. PrimeVue, общие формы/кнопки и белорусские тексты.
- **FR-010**: Ручные строки MUST показывать происхождение и даты, без запросов с пустыми
  event IDs и без protocol activation actions. Протокольное поведение сохраняется.
- **FR-011**: Система MUST детерминированно объединять источники и предотвращать
  дубли активной ручной записи при конкурентном добавлении одному спортсмену.
- **FR-012**: Поведение MUST покрываться domain/application unit, integration/API и
  component tests, включая rollback, rebuild persistence, guest access и смешанные факты.
  Завершение включает quality gates и одну updates запись.

## Key entities

- Ручное выполнение: постоянный исходный факт с собственным ID, active и аудитом.
- RankFact: общее входное выполнение с типом и идентичностью источника.
- История разрядов: пересоздаваемая проекция обоих источников с nullable protocol references.
- Person: текущий разряд, расчётные метаданные и ближайшая дата активации.

## Success criteria

- **SC-001**: 100% проверенных активных ручных выполнений сохраняются после двух
  rebuild/refill и повторной обработки протокола, без изменения исходных дат.
- **SC-002**: Добавление/удаление немедленно даёт согласованную историю и текущий разряд;
  100% проверенных ошибок не оставляют частичного изменения.
- **SC-003**: Все проверенные гостевые mutation requests отклоняются; все ручные строки
  отображаются без фиктивных navigation links и protocol-only действий.
- **SC-004**: Смешанный расчёт сохраняет прежние протокольные правила и порядок при повторе;
  ручные записи не меняют подсчёт трёх стартов.
- **SC-005**: Backend/frontend gates проходят; число запросов истории не растёт на каждую строку.

## Assumptions

- Права совпадают с текущими mutation-действиями страницы разрядов: authenticated user.
- Обе даты задаются явно; «не подтверждённый разряд без даты активации» вне этой фичи.
- Ручная запись подтверждает выполнение и не является бессрочным override текущего разряда.
- Ручные юношеские выполнения не фильтруются по birthday/возрасту; это подтверждённые
  факты. Возрастной фильтр протоколов и длительность действия не меняются.
- Без редактирования: ошибку исправляют удалением и новым добавлением.
- Ветку без запроса не менять; commit/push/deploy отдельно. Полный spec-kit запрошен
  пользователем, plan/review/tasks/analyze/implement следуют после фиксации требований.
