# Спецификация фичи: управление клубами в SPA

**Ветка фичи**: `007-club-spa-management`

**Создано**: 2026-08-31

**Статус**: Черновик

**Входные данные**: описание пользователя: «Перевести раздел клубов на SPA: постраничный
список с фильтром по названию, создание, редактирование и просмотр клуба со списком персонов
через новый JSON API; сохранить глубокие ссылки на существующие страницы персонов, удалить
заменённые Blade-страницы и неиспользуемый legacy-код, а ссылки клубов и соревнований в старом
navbar направить в SPA».

## Контекст и границы

Проект продолжает поэтапный перенос пользовательских разделов из Blade в SPA. Эта фича переносит
полный пользовательский путь раздела клубов: поиск клуба, просмотр связанных персонов, создание и
редактирование клуба. Новый раздел следует уже принятому поведению SPA-раздела соревнований и
использует единообразные состояния загрузки, ошибок, пустых результатов, пагинации, действий и
служебной информации.

После завершения переноса старые Blade-страницы списка, создания и просмотра клубов больше не
сохраняются как параллельный интерфейс. Все найденные внутренние ссылки на эти страницы переводятся
на SPA до удаления старых Blade-обработчиков. Старые GET-адреса списка, создания и просмотра клуба
сохраняются только как перенаправления на соответствующие SPA-страницы; старые операции изменения
удаляются. Просмотр отдельной персоны и другие более глубокие функции раздела персонов в эту фичу
не входят: ссылки из клуба продолжают вести на соответствующие существующие страницы.

Удаление клуба, перенос общего раздела персонов в SPA и изменение схемы хранения данных не входят
в эту фичу. Legacy-код удаляется только после проверки фактических использований во всём
репозитории; общие сценарии, которыми продолжают пользоваться другие разделы, сохраняются.

## Clarifications

### Session 2026-08-31

- Q: Что должны делать старые GET-адреса клубов после удаления Blade-страниц? → A: Старые
  GET-адреса перенаправляются в SPA; старые POST-операции удаляются.
- Q: Должны ли отключённые персоны учитываться в количестве персонов клуба и отображаться на
  странице клуба? → A: Только активные персоны учитываются в счётчике и отображаются в списке.
- Q: В каком порядке по умолчанию должны отображаться персоны на странице клуба? → A: Фамилия →
  имя → идентификатор.
- Q: Как разрешить конфликт имени между существующим полным `ViewPersonDto` и новым компактным DTO
  для JSON API? → A: Существующий полный DTO переименовать в `LegacyViewPersonDto`, а новый
  компактный DTO назвать `ViewPersonDto`.
- Q: В каком порядке по умолчанию должны отображаться клубы в постраничном списке? → A: Название →
  идентификатор.

## Пользовательские сценарии и тестирование *(обязательный раздел)*

### Пользовательская история 1 — найти клуб (приоритет: P1)

Посетитель открывает SPA-список клубов, постранично просматривает его и сужает результаты по
фрагменту названия без полной перезагрузки страницы.

**Почему этот приоритет**: поиск клуба — основной вход в раздел и обязательная основа для
просмотра персонов и дальнейшего управления клубом.

**Независимая проверка**: открыть список без авторизации, ввести фрагмент названия разным
регистром и с внешними пробелами, перейти между страницами и убедиться, что отображаются только
активные подходящие клубы с корректным количеством персонов.

**Сценарии приёмки**:

1. **Given** посетитель открыл список клубов, **When** данные загружены, **Then** он видит первую
   страницу активных клубов, общее количество результатов и доступные переходы пагинации.
2. **Given** посетитель ввёл не менее трёх значимых символов названия и закончил ввод, **When**
   проходит короткая пауза, **Then** список обновляется и содержит клубы, в названии которых есть
   введённый фрагмент без учёта регистра.
3. **Given** в поле названия введён один или два значимых символа, **When** пользователь закончил
   ввод, **Then** поиск не отправляется, под полем показана подсказка о минимальной длине, а общая
   ошибка загрузки не появляется.
4. **Given** клиент напрямую передал слишком короткое непустое название, **When** запрос
   обработан, **Then** система возвращает стандартную ошибку валидации именно для поля названия.
5. **Given** пользователь изменил или очистил фильтр, находясь не на первой странице, **When**
   список обновляется, **Then** пагинация сбрасывается на первую страницу нового результата.
6. **Given** список содержит несколько клубов, **When** пользователь переходит между страницами,
   **Then** клубы стабильно упорядочены по названию и идентификатору без повторов и пропусков.

### Пользовательская история 2 — просмотреть клуб и его персонов (приоритет: P1)

Посетитель открывает клуб из списка и видит его название и постраничный список связанных персонов.
Для каждой персоны показываются только необходимые для этого экрана сведения, а переход к
подробностям открывает существующую страницу персоны.

**Почему этот приоритет**: список персонов является главным содержимым страницы клуба и сохраняет
пользовательскую ценность заменяемой Blade-страницы.

**Независимая проверка**: открыть без авторизации клуб с несколькими персонами и клуб без персонов;
проверить состав полей, пагинацию, пустое состояние и переход по имени на существующую страницу
персоны, затем повторить просмотр после входа и проверить служебные данные.

**Сценарии приёмки**:

1. **Given** посетитель нажимает название клуба в SPA-списке, **When** страница открывается,
   **Then** он остаётся в SPA и видит выбранный клуб и первую страницу его персонов.
2. **Given** у клуба есть персоны, **When** их список загружен, **Then** для каждой строки
   отображаются имя, фамилия и год рождения, а служебные сведения о создании и обновлении не
   раскрываются неаутентифицированному посетителю.
3. **Given** пользователь аутентифицирован, **When** он просматривает персонов клуба, **Then** для
   каждой персоны дополнительно доступны сведения о создании и обновлении.
4. **Given** пользователь нажимает имя или фамилию персоны, **When** подробная SPA-страница персоны
   ещё не реализована, **Then** открывается корректная существующая страница этой персоны.
5. **Given** в клубе нет активных персонов, **When** страница клуба открыта, **Then** пользователь
   видит явное пустое состояние без ошибки.
6. **Given** запрошен несуществующий или неактивный клуб, **When** загрузка завершена, **Then**
   пользователь получает понятное сообщение и может вернуться к списку клубов.
7. **Given** к клубу относятся активные и отключённые персоны, **When** пользователь видит клуб в
   списке и открывает его страницу, **Then** счётчик совпадает с количеством активных персонов, а
   отключённые персоны не отображаются ни на одной странице выдачи.
8. **Given** в клубе есть несколько персонов, в том числе с одинаковыми фамилиями или именами,
   **When** пользователь переходит между страницами списка, **Then** персоны стабильно упорядочены
   по фамилии, затем имени и идентификатору без повторов и пропусков.

### Пользовательская история 3 — создать клуб (приоритет: P2)

Аутентифицированный пользователь открывает SPA-форму, вводит название нового клуба и после
успешного сохранения переходит к созданному клубу.

**Почему этот приоритет**: создание необходимо для переноса рабочего сценария администрирования и
позволяет удалить старую Blade-форму.

**Независимая проверка**: войти в приложение, создать клуб с уникальным валидным названием и
убедиться, что он доступен в списке и на странице просмотра; повторить с пустым, слишком длинным и
дублирующим названием и проверить ошибки у поля.

**Сценарии приёмки**:

1. **Given** пользователь аутентифицирован, **When** он открывает список клубов, **Then** ему
   доступно действие добавления клуба, ведущее на SPA-форму.
2. **Given** пользователь отправляет валидное уникальное название, **When** клуб создан, **Then**
   система показывает подтверждение и открывает страницу нового клуба.
3. **Given** название отсутствует, превышает допустимую длину или совпадает с существующим после
   принятой нормализации, **When** пользователь сохраняет форму, **Then** клуб не создаётся, а
   понятная ошибка отображается у поля названия.
4. **Given** посетитель не аутентифицирован, **When** он открывает прямую ссылку формы или
   отправляет запрос создания, **Then** клуб не создаётся и посетитель проходит обычный сценарий
   входа.

---

### Пользовательская история 4 — отредактировать клуб (приоритет: P2)

Аутентифицированный пользователь открывает заполненную SPA-форму существующего клуба, меняет его
название и возвращается на страницу клуба с обновлёнными данными.

**Почему этот приоритет**: редактирование завершает базовый цикл управления клубом и устраняет
необходимость добавлять новую операцию в legacy-интерфейс.

**Независимая проверка**: войти в приложение, изменить название активного клуба, проверить
обновление списка и страницы просмотра, затем отправить невалидное или дублирующее название и
убедиться, что исходные данные сохранены.

**Сценарии приёмки**:

1. **Given** пользователь аутентифицирован и открыл активный клуб, **When** он выбирает
   редактирование, **Then** SPA-форма заполнена текущим названием клуба.
2. **Given** пользователь сохранил валидное уникальное название, **When** операция завершена,
   **Then** страница клуба и список показывают новое название и актуальные служебные сведения.
3. **Given** новое название невалидно или конфликтует с другим клубом, **When** пользователь
   сохраняет форму, **Then** изменения не применяются, а ошибка показывается у поля названия.
4. **Given** посетитель не аутентифицирован либо клуб не существует или неактивен, **When** он
   пытается открыть форму или отправить изменение напрямую, **Then** данные клуба не меняются и
   возвращается стандартный ответ для соответствующей ситуации.

---

### Пользовательская история 5 — завершить миграцию клубных страниц (приоритет: P3)

Пользователь переходит к клубам и соревнованиям из старого navbar и других внутренних страниц по
актуальным SPA-адресам, не попадая на удалённые клубные Blade-страницы.

**Почему этот приоритет**: удаление параллельного интерфейса снижает технический долг только тогда,
когда все рабочие пользовательские пути остаются достижимыми.

**Независимая проверка**: перейти по ссылкам клубов и соревнований из legacy navbar, а также по
всем найденным внутренним ссылкам на клуб; убедиться, что они открывают SPA. Проверить старые
клубные URL и убедиться, что Blade-контент больше не обслуживается, а несвязанные legacy-разделы
продолжают работать.

**Сценарии приёмки**:

1. **Given** пользователь находится на legacy Blade-странице, **When** он выбирает клубы или
   соревнования в navbar, **Then** открывается соответствующий SPA-раздел.
2. **Given** пользователь выбирает клуб из другого сохраняемого раздела, **When** ссылка открыта,
   **Then** она ведёт на SPA-страницу этого клуба.
3. **Given** перенос завершён, **When** запрашивается прежний GET-адрес списка, создания или
   просмотра клуба, **Then** пользователь перенаправляется на соответствующую SPA-страницу и
   старый Blade-контент не отображается; прежняя POST-операция создания больше недоступна.
4. **Given** проведён аудит связанного legacy-кода, **When** у класса, метода, маршрута, шаблона или
   перевода нет потребителей во всём репозитории, **Then** он удалён; если потребители остались,
   артефакт сохранён или явно отделён как legacy.
5. **Given** пользователь со страницы клуба переходит к персоне, **When** подробности персоны ещё
   не перенесены, **Then** существующая страница персоны остаётся доступной и работает как раньше.

### Граничные случаи

- Фильтр содержит ведущие или хвостовые пробелы: они не считаются значимыми символами и не меняют
  результат поиска.
- Фильтр содержит смешанный регистр, кириллицу или латиницу: сопоставление подстроки не зависит от
  регистра и не повреждает введённые символы.
- Пользователь быстро меняет фильтр несколько раз: устаревший ответ не заменяет результат более
  нового запроса.
- После фильтрации результатов нет: показывается пустое состояние, а не ошибка загрузки.
- У персоны нет даты рождения: год отображается пустым значением, без фиктивной даты.
- У персоны есть полная дата рождения: на странице клуба из неё показывается только год.
- Количество персонов занимает несколько страниц: переход между страницами не меняет выбранный
  клуб и не раскрывает служебные сведения посетителю без авторизации.
- В клубе есть отключённые персоны: они не входят ни в счётчик клуба, ни в постраничную выдачу.
- У пользователя истёк срок аутентификации во время создания или редактирования: изменение не
  выполняется, а пользователь проходит обычный сценарий входа.
- Переименование клуба без фактического изменения нормализованного названия не создаёт ложный
  конфликт с самим редактируемым клубом.
- Аудит legacy-кода находит общий сценарий списка клубов, используемый формами событий, персонов
  или кубков: такой сценарий не удаляется вместе с Blade-страницами клубов.

## Требования *(обязательный раздел)*

### Функциональные требования

- **FR-001**: Система ДОЛЖНА предоставлять через версионированный JSON API публичный постраничный
  список только активных клубов с названием и количеством активных персонов, относящихся к
  каждому клубу. Клубы ДОЛЖНЫ быть стабильно отсортированы по названию, затем идентификатору.
- **FR-002**: Система ДОЛЖНА позволять фильтровать список клубов по подстроке названия без учёта
  регистра. Перед проверкой и поиском внешние пробелы удаляются; непустой фрагмент должен содержать
  не менее трёх значимых символов.
- **FR-003**: Поиск по названию ДОЛЖЕН применяться после паузы около 300 миллисекунд. Значение из
  одного или двух символов не ДОЛЖНО отправляться, а интерфейс ДОЛЖЕН показывать подсказку о
  минимальной длине под полем.
- **FR-004**: Серверная проверка ДОЛЖНА отклонять более короткий непустой фильтр стандартной
  ошибкой валидации поля `name`; интерфейс ДОЛЖЕН показывать эту ошибку под полем, не заменяя её
  общей ошибкой загрузки.
- **FR-005**: При изменении или очистке фильтра текущая страница ДОЛЖНА сбрасываться на первую;
  очистка фильтра ДОЛЖНА восстанавливать нефильтрованный список.
- **FR-006**: Система ДОЛЖНА предоставлять публичный просмотр одного активного клуба и через новый
  версионированный JSON API — постраничный список только активных персонов c фильтром по `clubId`.
  Персоны ДОЛЖНЫ быть стабильно отсортированы по фамилии, затем имени и идентификатору.
- **FR-007**: Новый `ViewPersonDto` для списка клуба ДОЛЖЕН содержать только системный
  идентификатор, имя, фамилию, год рождения и служебные сведения о создании и обновлении. Полная
  дата рождения, гражданство, платежи, результаты и другие подробности в эту выдачу не входят.
- **FR-008**: Служебные сведения `created` и `updated` клуба и персон ДОЛЖНЫ передаваться и
  отображаться только аутентифицированному пользователю; в публичном ответе эти поля отсутствуют.
- **FR-009**: Имя и фамилия персоны на странице клуба ДОЛЖНЫ вести на существующую страницу
  просмотра этой персоны до её отдельного переноса в SPA.
- **FR-010**: Система ДОЛЖНА предоставлять аутентифицированному пользователю через
  версионированный JSON API создание клуба по названию и редактирование названия активного клуба.
  Неаутентифицированные запросы изменения ДОЛЖНЫ отклоняться.
- **FR-011**: Создание и редактирование ДОЛЖНЫ применять одинаковые правила поля названия:
  обязательное непустое значение длиной не более 255 символов и существующее доменное правило
  предотвращения дубликатов после нормализации.
- **FR-012**: Ошибки валидации и конфликта названия ДОЛЖНЫ отображаться у соответствующего поля
  формы без потери введённого значения; успешная операция ДОЛЖНА приводить на страницу созданного
  или обновлённого клуба.
- **FR-013**: Все даты и календарные части служебных отметок на новых SPA-страницах ДОЛЖНЫ
  отображаться цифрами в формате `YYYY-MM-DD`, без локализации названий месяцев. Год рождения
  персоны отображается отдельно четырьмя цифрами.
- **FR-014**: Старый Blade navbar ДОЛЖЕН направлять пункты клубов и соревнований соответственно на
  SPA-список клубов и SPA-список соревнований.
- **FR-015**: Все внутренние ссылки на заменённую страницу клуба ДОЛЖНЫ быть переведены на
  SPA-просмотр клуба до удаления старых клубных маршрутов.
- **FR-016**: После подтверждения полного покрытия старые Blade-страницы списка, создания и
  просмотра клубов, их actions, прежняя POST-операция создания, специфичные переводы и тесты
  ДОЛЖНЫ быть удалены. Старые GET-адреса ДОЛЖНЫ сохраняться только как перенаправления на
  соответствующие SPA-страницы и не ДОЛЖНЫ выполнять старую бизнес-логику.
- **FR-017**: Связанные legacy-сервисы, репозитории, методы, компоненты и DTO ДОЛЖНЫ удаляться
  только при отсутствии использований во всём репозитории. Используемые другими сценариями части
  ДОЛЖНЫ сохраняться; при конфликте имён допустимо обозначить сохраняемый старый класс префиксом
  `Legacy`.
- **FR-018**: Новые операции чтения и изменения ДОЛЖНЫ возвращать единообразные результаты для
  успеха, ошибок валидации, отсутствующих данных и отсутствия аутентификации, согласованные с уже
  перенесённым разделом соревнований.
- **FR-019**: Параметры постраничной выдачи и поля запросов нового версионированного интерфейса
  данных ДОЛЖНЫ следовать принятому в SPA соглашению `camelCase`, включая `perPage` и `clubId`.
- **FR-020**: Новые сервисы, экшены должны быть протестированны.

### Архитектурные и миграционные ограничения

- **AR-001**: Новые операции реализуются в целевых слоях Application, Domain, Bridge и
  Infrastructure. HTTP-слой принимает входные данные, передаёт их в Application use case, а наружу
  возвращается специализированное представление через assembler; бизнес-правила не размещаются в
  контроллерах или SPA.
- **AR-002**: Новые классы не добавляются в legacy `app/Services` и legacy-репозитории. Существующие
  доменные интерфейсы и инфраструктурные реализации расширяются только операциями, необходимыми
  целевым сценариям.
- **AR-003**: Новый компактный DTO персоны не ДОЛЖЕН наследовать лишние поля старого полного
  представления и ДОЛЖЕН называться `ViewPersonDto`. Существующий полный `ViewPersonDto` ДОЛЖЕН
  быть переименован в `LegacyViewPersonDto` с обновлением всех его фактических потребителей;
  связанные исключительно с полным представлением классы при необходимости также обозначаются
  префиксом `Legacy`.
- **AR-004**: Постраничные списки клубов и персонов загружают необходимые счётчики и связи без
  дополнительного запроса на каждую строку. Отсутствие N+1 проверяется для одной и нескольких
  строк; неограниченные выборки в новых операциях запрещены.
- **AR-005**: Изменение поведения покрывается request-тестами и frontend-тестами. Удаление legacy
  подтверждается поиском использований, проверками маршрутов и полным набором проектных гейтов.
- **AR-006**: Старые клубные страницы удаляются только после готовности SPA-замен и перевода всех
  внутренних ссылок; сохраняемые глубокие страницы персонов и общие сценарии других разделов не
  должны регрессировать.

### Ключевые сущности

- **Клуб**: активная организация с уникальным нормализованным названием, количеством связанных
  активных персонов и служебными сведениями о создании и обновлении.
- **Персона в клубе**: компактное представление активной персоны со стабильным идентификатором,
  именем, фамилией, годом рождения и закрытыми для посетителя служебными сведениями.
- **Фильтр клубов**: фрагмент названия и текущая страница постраничной выдачи.
- **Форма клуба**: общее представление создания и редактирования названия клуба с полевыми
  ошибками.
- **Legacy-артефакт**: старый маршрут, action, шаблон, перевод, сервис, репозиторий, метод,
  компонент или DTO, относящийся к заменённым страницам и подлежащий удалению только после
  подтверждения отсутствия других потребителей.

## Критерии успеха *(обязательный раздел)*

### Измеримые результаты

- **SC-001**: Посетитель может найти клуб по названию и открыть его страницу не более чем за три
  действия после открытия списка.
- **SC-002**: Во всех проверенных сценариях фильтр возвращает только клубы с совпадающей без учёта
  регистра подстрокой; значения короче трёх значимых символов не вызывают поиск и получают полевую
  обратную связь.
- **SC-003**: Страница клуба корректно показывает 100% его активных персонов через пагинацию;
  публичный пользователь не получает `created` и `updated`, а аутентифицированный получает их для
  каждой показанной записи.
- **SC-004**: Аутентифицированный пользователь создаёт или редактирует клуб полностью в SPA, а
  неаутентифицированный пользователь не может завершить ни одну из этих операций.
- **SC-005**: Все найденные внутренние ссылки на клубы и оба пункта клубов и соревнований в legacy
  navbar ведут на работающие SPA-страницы; ссылки на подробности персонов продолжают вести на
  работающие существующие страницы.
- **SC-006**: После завершения фичи ни один старый клубный адрес не отдаёт заменённую Blade-страницу:
  GET-адреса перенаправляют в SPA, а прежняя POST-операция недоступна; поиск по репозиторию не
  находит неиспользуемых артефактов, специфичных только для удалённых страниц.
- **SC-007**: Списки с одной и несколькими строками не выполняют отдельный запрос связанных данных
  для каждой строки и сохраняют ограниченный размер страницы.

## Предположения

- Просмотр списка клубов и страницы клуба публичный; любой аутентифицированный пользователь может
  создавать и редактировать клубы без дополнительных ролей и ownership-проверок.
- Удаление и восстановление клуба не входят в эту фичу. Существующий неиспользуемый сценарий
  отключения может быть удалён только после общего аудита использований.
- Список персонов клуба также постраничный: это сохраняет текущее пользовательское поведение и не
  допускает неограниченную новую выдачу.
- Поиск клубов повторяет принятые правила поиска соревнований: подстрока, минимум три значимых
  символа, trim, отсутствие зависимости от регистра и пауза около 300 миллисекунд.
- SPA-маршруты имеют вид `/app/clubs`, `/app/clubs/create`, `/app/clubs/{id}` и
  `/app/clubs/{id}/edit`; подробная ссылка персоны остаётся существующим legacy URL.
- Поле года рождения nullable и вычисляется из существующей даты рождения без изменения данных.
- Публичный ответ не содержит ключи impressions, а не возвращает их с пустыми или маскированными
  значениями, как в существующем SPA-разделе соревнований.
- Старые GET-адреса `/clubs`, `/clubs/create` и `/clubs/{id}/show` сохраняются как
  перенаправления на соответствующие SPA-страницы. Старый POST-адрес создания удаляется без
  совместимого обработчика.
