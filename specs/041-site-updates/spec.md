# Feature Specification: История обновлений сайта

**Feature Branch**: `master`

**Created**: 2026-10-04

**Status**: Implemented

**Input**: Страница обновлений для авторизованных пользователей: краткая хронология всех spec-kit фич с раскрываемыми подробностями и уместными примерами и ссылками на разделы сайта. Заменённые решения объясняются текстом без ссылок на GitHub. Правило публикации каждой новой спецификации закрепляется в архитектурном манифесте.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотреть историю изменений (Priority: P1)

Авторизованный пользователь открывает «Абнаўленні» из общего меню и видит даты, названия и короткие описания изменений от новых к старым. Гость при прямом переходе попадает на вход и затем возвращается к истории.

**Why this priority**: История должна быть доступна целевой аудитории и быстро отвечать на вопрос, что изменилось.

**Independent Test**: Открыть страницу под учётной записью и без неё, сверить порядок и переход после входа.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** он выбирает ссылку в меню, **Then** видит записи в обратном хронологическом порядке.
2. **Given** гость, **When** он открывает адрес страницы напрямую, **Then** попадает на вход с возвратом к истории.
3. **Given** гость, **When** он просматривает меню, **Then** ссылки на историю в нём нет.

---

### User Story 2 - Узнать детали и перейти к функции (Priority: P1)

Пользователь раскрывает запись и читает понятное описание. Пример и переход к разделу сайта показываются, когда они помогают воспользоваться функцией. Если прежнее решение заменено, запись объясняет замену текстом.

**Why this priority**: Короткого заголовка недостаточно, чтобы найти функцию или понять историю её замены.

**Independent Test**: Раскрыть текущую, заменённую и внутреннюю запись, проверить содержание и уместность ссылок.

**Acceptance Scenarios**:

1. **Given** запись об актуальной функции, **When** пользователь её раскрывает, **Then** видит подробность и, если это помогает, пример и ссылку на работающий раздел.
2. **Given** запись о заменённом решении, **When** пользователь её раскрывает, **Then** видит объяснение замены без ссылки на GitHub.
3. **Given** запись без отдельного пользовательского экрана, **When** пользователь её раскрывает, **Then** получает понятное описание эффекта без искусственного примера и ссылки.

---

### User Story 3 - Не потерять будущие изменения (Priority: P2)

Разработчик завершает spec-kit фичу и добавляет понятную запись в историю. Правило об этом видно в обязательном архитектурном манифесте.

**Why this priority**: История теряет смысл, если последующие фичи не появляются в ней.

**Independent Test**: Сверить все существующие каталоги спецификаций с записями и проверить требование манифеста.

**Acceptance Scenarios**:

1. **Given** текущий набор спецификаций, **When** проверяют историю, **Then** у каждой есть ровно одна запись, включая повторяющиеся номера с разными именами.
2. **Given** новая спецификация, **When** выполняют её финальные задачи, **Then** обязательная проверка требует записи истории с датой, кратким описанием и корректными ссылками.

### Edge Cases

- Несколько изменений в одну дату сохраняют устойчивый порядок.
- Ссылка на раздел, для которого нужен конкретный объект, ведёт к доступному списку, а пример объясняет дальнейший путь.
- Если дата выката неизвестна, интерфейс не выдаёт дату документации за дату выката.
- Если старый маршрут удалён, история не ведёт на него.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Страница обновлений MUST быть доступна через меню и прямой адрес только в авторизованном интерфейсе с существующим возвратом после входа.
- **FR-002**: История MUST показывать дату фиксации изменения, заголовок и описание в одну-две фразы, от новых записей к старым.
- **FR-003**: Каждая запись MUST раскрываться для подробностей; раскрытие MUST работать с клавиатуры.
- **FR-004**: История MUST включать по одной записи на каждую существующую spec-kit фичу и новую фичу этой страницы; идентификатором служит полное имя спецификации.
- **FR-005**: Пример и ссылка на работающий раздел MUST показываться только тогда, когда они помогают воспользоваться описанной функцией; для внутренних изменений достаточно описания.
- **FR-006**: Для заменённого решения запись MUST объяснять, чем оно заменено, без ссылки на GitHub.
- **FR-007**: История MUST быть статической, без запросов за записями или отдельного хранения пользовательских данных.
- **FR-008**: Архитектурный манифест MUST требовать запись на странице обновлений при завершении каждой новой spec-kit фичи и проверку устаревших ссылок при замене прежней функции.
- **FR-009**: Даты MUST быть обозначены честно: дата фиксации по истории проекта, если дата публикации на production неизвестна.

### Key Entities

- **Запись обновления**: полное имя спецификации, дата фиксации, заголовок, краткое описание, подробность, необязательный пример и необязательная ссылка на текущий раздел.
- **Спецификация**: источник происхождения записи и её уникальный идентификатор.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь находит последнее изменение и открывает его подробность не более чем за два действия после входа.
- **SC-002**: 100% существующих спецификаций имеют ровно одну запись в истории.
- **SC-003**: Все показанные ссылки ведут к существующему разделу сайта; ни одна не ведёт к GitHub или удалённому маршруту.
- **SC-004**: Гость не может открыть страницу через навигацию сайта или прямой адрес без входа.
- **SC-005**: При добавлении следующей spec-kit фичи требование обновить историю видно в обязательном манифесте и финальной проверке фичи.

## Assumptions

- Текущий язык SPA — белорусский; история использует его для согласованности интерфейса.
- Дату выката прежних фич нельзя достоверно восстановить из репозитория; используется дата последней фиксации соответствующей спецификации в истории Git, явно подписанная как дата фиксации.
- Сведения об обновлениях не секретны сами по себе; доступ ограничивается действующим правилом авторизованных SPA маршрутов.
