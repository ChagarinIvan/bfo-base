# План реализации: актуальный разряд и история разрядов

**Ветка**: `009-rank-projection` | **Дата**: 2026-09-01 | **Спецификация**: [spec.md](./spec.md)

## Краткое решение

Актуальный разряд становится материализованным состоянием `Person`; история разрядов —
детерминированная производная коллекция, строящаяся только из идентифицированных строк
протоколов. Единый сценарий пересчёта заменяет историю одного спортсмена и обновляет его
текущие поля в одной транзакции. Чтение списков, экспорт и карточек больше не запускает
расчёт и не пишет в базу.

## Технический контекст

**Язык/версия**: PHP 8.5, Laravel 13  
**Основные зависимости**: PHP 8.5 string-backed enum `App\Domain\Rank\Rank`, Laravel Queue и Scheduler, Eloquent, PHPUnit 13, PHPStan/Larastan, Rector
**Хранение**: MySQL 8.4; Redis для очереди  
**Тестирование**: PHPUnit; Domain/Application unit-тесты на фактах, моках и стабах; persistence/API — с реальной БД  
**Целевая платформа**: Laravel-монолит, SPA JSON API и переходные Blade-экраны  
**Тип проекта**: веб-приложение с JSON API  
**Цели производительности**: чтение страницы спортсменов не делает запросов, число которых зависит от числа спортсменов; пересчёт пакета протокола выполняется по уникальным спортсменам, а не по строкам  
**Индексы**: миграция добавляет только `(current_rank, active)`, `current_rank_finished_on` и индекс истории; существующий `(club_id, active)` обслуживает club+rank. `EXPLAIN` фиксируется integration-тестами, новый широкий индекс допускается лишь при доказанной необходимости
**Ограничения**: спортивные правила и наблюдаемые результаты текущей системы сохраняются; фича поставляется одним deploy без рабочего legacy rank-path; после deploy выполняется идемпотентный консольный полный refill; refill оставляет только данные, выведенные из protocol lines; `protocol_lines.activate_rank` — единственное место ручной даты активации; разряд из OrientBy игнорируется; истечение обновляется ежедневным Laravel Scheduler
**Масштаб/объём**: история может быть неограниченной, поэтому не загружается как полная коллекция при обычном чтении `Person`; перерасчёт работает по одному спортсмену или ограниченным пакетам

## Проверка конституции

*Гейт до исследования и после дизайна: пройден.*

- **Слои**: enum `Rank` и вычисление правил изолируются в Domain; Application оркестрирует транзакционный rebuild; Bridge запускает HTTP/queue/scheduler; Eloquent и bulk-запросы остаются в Infrastructure.
- **Legacy containment**: `app/Services/RankService`, `app/Repositories/RanksRepository` и разрозненные jobs/commands не расширяются и не сохраняются. Отдельный rank-репозиторий не создаётся: `PersonRepository` сохраняет owned state и историю, а узкий `RankFactsCollector` port читает protocol-derived факты через Infrastructure.
- **Зависимости**: новые классы получают зависимости через конструктор. Фасады и service locator в новом пути не используются.
- **Тестирование**: характеристические и Domain/Application unit-тесты не создают Eloquent-модели; реальные записи допустимы только в integration/API тестах. Полные гейты — один раз в конце фичи.
- **N+1**: list/export используют материализованные поля `Person`; история получает источники пакетно.

Нарушений, требующих исключения из конституции, нет. Существующий Eloquent aggregate `Rank`,
`app()` в `PersonResource`, legacy-сервисы и репозитории разрядов устраняются в области этой
фичи, а не воспроизводятся. Освободившееся имя `Rank` получает нативный PHP enum; история
называется `PersonRankHistory` и не конкурирует с типом разряда.

### Исходный код

```text

├── Application/Service/Rank/       # сценарии rebuild, ручной активации, справочника и планового обновления
├── Domain/Rank/                    # чистые правила и построитель истории
├── Domain/Person/                  # владелец текущего разряда
├── Bridge/Laravel/                  # actions, queue handlers, console/scheduler
└── Infrastructure/Laravel/Eloquent/ # persistence истории и выборки Person

tests/
├── Domain/Rank/
├── Application/Service/Rank/
├── Infrastructure/Laravel/Eloquent/
└── Feature/Api/V1/Person/
```

**Решение по структуре**: новый путь не добавляет классы в `app/Services` или
`app/Repositories` и не оставляет параллельный rank persistence. `PersonRepository` сохраняет
owned state и историю; `RankFactsCollector` — узкий целевой port для чтения фактов разрядов из protocol
lines. Прежняя самостоятельная модель `Rank` заменяется производной историей, принадлежащей
`Person`, с инфраструктурным хранением.

## Завершающий этап: очистка legacy

После переключения всех сценариев выполняется отдельный инвентаризационный и удаляющий этап.
Он охватывает `RankService`, `RanksRepository`, прежние Application-обёртки, jobs, Artisan
commands, обработчики событий, HTTP actions, routes, Blade views, DI bindings, тесты,
переводы и ссылки навигации. Для каждого элемента фиксируется одно из решений:

- **удалить** — целевой use case полностью заменил функцию;
- **перевести** — пользовательский путь остаётся, но использует новый read/use case;
- **сохранить временно** — существует необходимая совместимость, причина и срок снятия
  указаны в финальном отчёте.

Удаление выполняется только после проверки usages и контрактов. Поддерживаемая страница
истории не считается legacy-кандидатом на удаление, пока новый пользовательский эквивалент
не введён.
