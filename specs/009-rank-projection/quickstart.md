# Проверка фичи: актуальный разряд и история разрядов

## Подготовка

1. Применить миграции на пустой тестовой базе.
2. Подготовить спортсменов и protocol lines с датами, выполненными разрядами, статусом вне
   конкурса и датами ручной активации.
3. Для сценариев обработки протокола запустить worker очереди и Laravel Scheduler.

## Сценарии

### 1. Характеризация правил

Проверить чистыми Domain unit-тестами `Rank` enum: стабильные backed values и labels,
нормализацию внешних обозначений,
порядок силы, юношеские cases и правило автоматической активации. Затем проверить неизменность
каждого правила расчёта: нормализации разряда,
автоматической/ручной активации, продления, повышения, понижения после срока, IIIю и
возрастного ограничения. Тесты используют входные факты, а не Eloquent-модели.

### 2. Refill и история

На integration-тесте создать несколько protocol lines одного спортсмена, запустить rebuild
и убедиться, что сохранены все ожидаемые элементы истории и текущие поля `Person`. Повторить
rebuild без изменения исходных данных и сравнить результаты. Добавить запись без protocol
source и подтвердить, что refill её исключает. Передать разряд через OrientBy без protocol
line и подтвердить, что текущий разряд и история не меняются.

### 3. Обработка протокола

Создать или заменить протокол с несколькими строками одного спортсмена. После идентификации
дождаться обработки пакета и проверить один rebuild для уникального спортсмена, обновлённую
историю и текущий разряд. Повторить для перепривязки строки и её отвязки.

### 4. Ручная активация и истечение

Изменить `protocol_lines.activate_rank` и проверить согласованность источника, истории и
текущего состояния, включая сохранение этой даты после refill. Затем установить дату расчёта после `current_rank_finished_on`, выполнить
ежедневную задачу и убедиться, что результат совпадает с обычным rebuild.

### 5. API и отсутствие N+1

Запросить `GET /api/v1/ranks` и проверить полный отсортированный каталог `id/label`.
Запросить `GET /api/v1/persons?rankId=6` и
`GET /api/v1/persons?rankId=0`; проверить поле `rankId`, фильтр, пагинацию и
валидацию недопустимого значения. Проверить SPA-кэш справочника: hit, истечение часа и
некорректные данные `localStorage`. Интеграционный query-test подтверждает, что увеличение
размера страницы не добавляет обращений для определения ранга. Проверить `EXPLAIN` списка
с `rankId`, `clubId + rankId` и ежедневного запроса истёкших разрядов: первый и последний
используют новые индексы, а сочетание клуба и разряда — существующий индекс клуба без
неограниченного чтения.

### 6. Очистка legacy

Составить перечень всех прежних входов разрядов и проверить для каждого решение из плана:
удалённый элемент не имеет usages, route, ссылки, binding, перевода и теста; сохранённая
страница истории читает новый use case. Финальная проверка фиксирует только обоснованные
переходные точки.

## Финальные гейты

После завершения всей фичи один раз выполнить `composer cs`, `composer stan`,
`composer rector -- --dry-run` и `composer test`.

## Результат текущей реализации

- `composer cs` — OK.
- `composer stan` — OK, включая `app`, `tests` и `config`.
- `composer rector -- --dry-run` — OK.
- Узкий набор фичи — OK: 42 теста, 166 assertions, 2 PHPUnit notices.
- Полный `composer test` после PR-правок — OK: 368 тестов, 2798 assertions, 2 PHPUnit notices.
- `npm run ci` — OK: lint, typecheck, 69 Vitest-тестов и SPA build; SPA-файлы после этого не менялись.

Projection, enum, history persistence, `/api/v1/ranks`, `rankId`-фильтр,
rebuild-команда `persons:ranks:refill {userId}`, batch job и ежедневное истечение реализованы. Удалены
устаревшие rank services/repositories/aggregate, старый список/check/export и
веб-refill entry point; сохранены только history и ручная активация. Повторная
идентификация protocol lines отправляет одну batch-задачу на уникальных людей.

## Ретроспективная сверка после PR review (2026-09-02)

По замечаниям Copilot дополнительно зафиксированы и реализованы: `ShouldQueueAfterCommit`
для rebuild после ручной активации, запрет junior-разряда без birthday, включительная граница
продления периода и потоковое сохранение истории через несохранённые экземпляры
`PersonRankHistory::fromValues(...)->save()`.

Актуальные узкие проверки после этих изменений: Domain Rank — 14 тестов, 39 assertions;
PHPStan по изменённым Domain/Handler/model-файлам — OK. Интеграционный refill в текущем
окружении не запускался из-за недоступного MySQL (`Operation not permitted`), поэтому ранее
зафиксированный полный результат требует повторной проверки в окружении с БД.

Открытый технический долг: при замене протокола cleanup и последующая идентификация могут
последовательно отправить rebuild одного человека дважды. Данные после обработки корректны,
но оптимизация до одной объединённой batch-задачи остаётся отдельной задачей.
