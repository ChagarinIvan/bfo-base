# Исследование: актуальный разряд и история разрядов

## 1. Граница агрегата

**Решение**: `Person` — единственный владелец разрядного состояния спортсмена. Его
материализованные поля содержат текущий разряд и срок его действия. История — производная
коллекция дочерних записей `PersonRankHistory`, а не самостоятельный aggregate root `Rank`.

**Обоснование**: у прежнего `Rank` нет независимого пользовательского жизненного цикла:
он появляется только как результат строки протокола, его период меняется вследствие
пересчёта того же спортсмена, а ручная активация меняет факт-источник. Единственная
согласованная бизнес-граница — состояние конкретного человека.

**Рассмотренные альтернативы**:

- Самостоятельный aggregate root `Rank` — отклонён: он дробит одну инвариантную операцию
  «история + текущий разряд человека» на несколько событий и транзакций.
- Полностью загружать `Person` со всей историей как одну Eloquent-коллекцию — отклонён:
  история не ограничена и сделает обычные операции со спортсменом тяжёлыми.
- Не сохранять историю, а вычислять её при открытии экрана — отклонён: не выполняет
  требования к быстрому чтению и прозрачной истории.

## 2. Тип разряда

**Решение**: `App\Domain\Rank\Rank` — нативный string-backed PHP enum. Его backed value —
стабильный машиночитаемый ID, а отдельный метод enum возвращает отображаемую строку. Он
становится единственным доменным представлением разряда и владеет каталогом значений,
нормализацией обозначений строк протокола, порядком силы, признаками юношеского разряда и
автоматической активации. В persistence и HTTP на границах передаётся backed value; parser
преобразует обозначение из protocol line в case enum; разряд из OrientBy не становится входом
Domain; в Domain и Application используются только enum cases.

**Обоснование**: сейчас эти правила рассеяны по строковым константам Eloquent-модели,
массивам `RankService` и ручным проверкам parsers. Enum делает недопустимое значение
непредставимым внутри домена и освобождает имя `Rank` после удаления Eloquent aggregate.

**Рассмотренные альтернативы**:

- Оставить строки и статические helper-методы — отклонено: типовая безопасность остаётся
  только соглашением, а список допустимых значений продолжает дублироваться.
- Ввести отдельный `RankLevel` enum — отклонено: после удаления Eloquent-модели нет причины
  сохранять два имени для одного доменного понятия.

## 3. Справочник разрядов для клиента

**Решение**: публичный `GET /api/v1/ranks` возвращает прямой список `{id, label}` из
`Rank::cases()` в доменном порядке. V1 person response и параметр фильтра используют только
`rankId`. SPA получает справочник через отдельный API-клиент и кэширует его в памяти и
`localStorage` один час по тому же паттерну, что и годы.

**Обоснование**: frontend не хранит копию каталога, не зависит от строк `I`, `КМС` или
`б/р` и получает готовые options для select-фильтра. Backed values остаются стабильными при
изменении отображаемой строки или локализации.

**Рассмотренные альтернативы**:

- Отдавать label в каждом `ViewPersonDto` — отклонено: это дублирует справочные данные во
  всех строках списка и связывает API спортсмена с представлением.
- Захардкодить enum values и labels на SPA — отклонено: нарушает единый источник истины и
  требует фронтенд-релиза при изменении каталога.

## 4. Канонические и производные данные

**Решение**: единственный канонический источник спортивных достижений — идентифицированные
`protocol_lines`. При refill существующая разрядная история целевого спортсмена полностью
заменяется производными записями из этих строк; записи без источника исключаются. Ручная дата
активации берётся только из `protocol_lines.activate_rank`, поэтому также воспроизводится при
каждом refill.

**Обоснование**: это делает refill идемпотентным, исправляет последствия перепривязки
строки и исключает конкуренцию между legacy-импортом и протоколами.

**Рассмотренные альтернативы**:

- Сохранять произвольные legacy `Rank` вместе с расчётными — отклонён по решению продукта:
  полный пересчёт оставляет только protocol-derived данные.
- Использовать разряд, полученный из OrientBy, — отклонён: у него нет идентифицированной
  строки протокола, поэтому он не подтверждает спортивное выполнение.
- Неизменяемый event log — отклонён: protocol lines уже являются таким первичным журналом,
  а второй журнал дублировал бы данные и усложнил корректировку протоколов.

## 5. Модель расчёта и записи

**Решение**: чистый Domain-калькулятор принимает упорядоченные факты протоколов одного
спортсмена и дату расчёта, возвращает набор записей истории и актуальное состояние.
Application-сценарий в транзакции заменяет сохранённую историю и применяет новое состояние
к `Person`. Чтение ничего не пересчитывает и не записывает.

**Обоснование**: существующий `ActivePersonRankService` создаёт IIIю в read-path, а
`RankService` смешивает правила, legacy persistence и выборки. Чистая функция позволяет
сначала зафиксировать все текущие ветви характеристическими тестами, затем перенести их
без изменения результата.

**Рассмотренные альтернативы**:

- Продолжать дополнять `RankService` — отклонён конституцией: это legacy `app/Services`.
- Хранить только `person.current_rank` — отклонён: невозможно показать продления и
  понижения с источниками.

## 6. Запуск пересчёта

**Решение**: все входы вызывают один Application use case с набором уникальных person id.
После разбора протокола он запускается после идентификации; при замене/удалении протокола
в набор входят спортсмены из состояния до и после изменения; изменение связи строки или
даты активации запускает пересчёт затронутого спортсмена. Очередь обрабатывает пакет, не
создаёт один job на строку.

**Обоснование**: это убирает текущий fan-out из `ProtocolLineIdentService`, при котором
несколько строк одного человека запускают одинаковый refill.

**Рассмотренные альтернативы**:

- Один job на protocol line — отклонён: лишние повторные удаления/создания истории и
  гонки для одного человека.
- Синхронно пересчитывать в HTTP-запросе — отклонён: разбор и идентификация уже фоновые,
  а объём протокола непредсказуем.

## 7. Истечение по времени

**Решение**: ежедневная задача Laravel Scheduler после смены даты выбирает спортсменов,
чей сохранённый срок текущего разряда закончился, и передаёт их в тот же batch rebuild.

**Обоснование**: срок действия имеет дневную точность; такой механизм корректирует
проекцию без пользовательского чтения и не вводит отдельную логику понижения.

**Рассмотренные альтернативы**:

- Обновление только при чтении — отклонено: противоречит задаче.
- Полный ежедневный rebuild всей базы — отклонён: объём не нужен, есть срок текущего
  состояния для точной выборки кандидатов.

## 8. Совместимость и миграция

**Решение**: сохранить пользовательские правила и публичные строки разрядов, но заменить
внутреннюю самостоятельную модель `Rank` на историю спортсмена с однозначной ссылкой на
protocol line и прямыми ID competition/event/distance. Существующие Blade-страницы истории
работают через новый read use case; V1 persons API отдаёт текущий разряд и принимает фильтр.

**Обоснование**: потребители не должны узнать о внутреннем изменении модели, а новая
ссылка устраняет неоднозначность нескольких строк одного спортсмена на одном event. Прямые
ID делают историю удобной read model для ссылок и batch-loading без вложенной relation chain.

**Рассмотренные альтернативы**:

- Оставить `event_id` единственным источником — отклонён: он не указывает конкретное
  выполнение.
- Переписать все старые экраны разрядов в SPA — отложено: это отдельная UI-фича и не
  требуется для корректной модели.

## 9. Очистка legacy после миграции

**Решение**: cleanup — отдельный финальный этап фичи. Он начинается только после того, как
целевой путь покрывает расчёт, refill, ручную активацию, ежедневное обновление, историю и
список спортсменов. Инвентаризация охватывает все обращения к `RankService`,
`RanksRepository`, старым Application-обёрткам, jobs, Artisan-командам, контроллерам,
routes, Blade-шаблонам, bindings, переводам и тестам.

**Обоснование**: удаление до переключения приводит к регрессиям legacy UI, а сохранение
двух расчётных путей — к расхождению данных. Явная классификация каждого входа позволяет
удалить мёртвый код без потери поддерживаемого поведения.

**Рассмотренные альтернативы**:

- Оставить прежний код «на всякий случай» — отклонено: он остаётся рабочей, но неверной
  альтернативой новому алгоритму.
- Удалить все Blade-страницы разрядов сразу — отклонено: история должна оставаться
  доступной, пока ей не предоставлен новый пользовательский эквивалент.

## 10. Чистая persistence-граница

**Решение**: у разрядов не будет отдельного `RankRepository`. `PersonRepository` отвечает
за атомарное сохранение текущих полей `Person` и принадлежащей ему истории; узкий port
`RankFactsCollector` читает только необходимые protocol-derived факты через Eloquent adapter.
Domain-калькулятор не зависит ни от одного репозитория.

**Обоснование**: это отражает ownership истории человеком и не оставляет в целевом пути
legacy `app/Repositories` или искусственный persistence boundary для не-агрегата. `RankFactsCollector`
не расширяет общий `ProtocolLineRepository` и не создаёт второй domain aggregate.

**Рассмотренные альтернативы**:

- Оставить или переименовать `RankRepository` — отклонено: это продолжило бы выделять
  историю в ложный самостоятельный aggregate.
- Позволить Application работать с Eloquent напрямую — отклонено: нарушает границы слоёв
  и лишает калькулятор тестируемого чистого входа.
