# Feature Specification: Обновление технологического стека до latest

**Feature Branch**: `001-upgrade-stack`

**Created**: 2026-08-19

**Status**: Draft

**Input**: User description: "Обновить весь технологический стек проекта до последних версий («только вперёд»), без изменения бизнес-логики и поведения — чисто апгрейд. Инкрементально: фича = «обновить всё», внутри последовательные шаги, каждый шаг апгрейдит ровно одну вещь, после каждого — зелёные гейты (test/stan/cs/rector + локальный запуск) перед переходом дальше."

## User Scenarios & Testing *(mandatory)*

Фича инфраструктурная: «пользователи» здесь — команда сопровождения (получает современный
поддерживаемый стек и снятый техдолг) и конечные пользователи платформы (не должны заметить никаких
изменений в поведении). Каждый шаг апгрейда — самостоятельный, независимо проверяемый и откатываемый
срез: даже один выполненный шаг уже приносит ценность и оставляет систему работоспособной.

### User Story 1 - Безопасные обновления в рамках semver + снятие заброшенного пакета (Priority: P1)

Поднять все зависимости, которые обновляются в пределах текущих ограничений версий (минор/патч), и
заменить заброшенный `rector/rector-laravel` на поддерживаемый форк. Это фундамент: минимальный риск,
сразу убирает техдолг и заброшенную зависимость.

**Why this priority**: Наименьший риск, наибольшая отдача на единицу усилий; создаёт зелёную базу,
от которой отсчитываются последующие рискованные шаги. Уже сам по себе — жизнеспособный результат (MVP).

**Independent Test**: После обновления группы прогнать все гейты (тесты, статический анализ, стиль,
rector) — все зелёные; приложение поднимается локально и ведёт себя как раньше.

**Acceptance Scenarios**:

1. **Given** зелёная базовая линия, **When** обновлены dev-инструменты (php-cs-fixer, larastan,
   phpstan, phpunit, rector, mockery) и runtime-минор (horizon, sentry-laravel), **Then** все гейты
   зелёные, поведение не изменилось.
2. **Given** заброшенный `rector/rector-laravel`, **When** он заменён на `driftingly/rector-laravel`,
   **Then** rector-конфигурация работает, `composer` не сообщает об abandoned-пакетах в этой части.

---

### User Story 2 - Обновление фреймворка Laravel (Priority: P1)

Поднять Laravel по одному мажору: сначала 11 → 12, затем 12 → 13, с прохождением официальных upgrade
guide и применением rector-сетов Laravel. Каждый мажор — отдельный проверяемый шаг.

**Why this priority**: Laravel — ядро приложения; на его версии завязаны остальные пакеты. Пропускать
мажоры нельзя, поэтому шаг разбит на два независимых под-перехода.

**Independent Test**: После 11→12 все гейты зелёные и приложение работает; отдельно после 12→13 — то же.

**Acceptance Scenarios**:

1. **Given** приложение на Laravel 11 с зелёными гейтами, **When** выполнен переход на Laravel 12,
   **Then** все гейты зелёные, приложение поднимается локально, поведение не изменилось.
2. **Given** приложение на Laravel 12 с зелёными гейтами, **When** выполнен переход на Laravel 13,
   **Then** все гейты зелёные, приложение поднимается локально, поведение не изменилось.

---

### User Story 3 - Обновление и очистка библиотек (Priority: P2)

Привести библиотеки к целевому состоянию, по одному изменению за шаг: **удалить неиспользуемый**
doctrine/dbal (не нужен в Laravel 11+); **апгрейд predis** до 2.x/3.x — Redis-клиент стандартизирован
на predis (разворот исходного решения: predis реально используется в `.env`, phpredis не установлен —
см. research Decision 2 / T010); снять точечный пин guzzle; поднять phpoffice/phpspreadsheet (1→5 —
единственная с заметным код-импактом, и то Reader-only). Каждое изменение — отдельный шаг.

**Why this priority**: Требуется, чтобы «весь стек на latest», но зависит от обновлённого фреймворка;
несёт наибольший риск изменений API, поэтому идёт после ядра и делается по одной библиотеке.

**Independent Test**: После обновления каждой отдельной библиотеки все гейты зелёные и связанная с ней
функциональность (кэш/очереди для predis, HTTP-клиент для guzzle, выгрузки Excel для phpspreadsheet)
работает как раньше.

**Acceptance Scenarios**:

1. **Given** зелёная база, **When** за один шаг обновлён либо удалён ровно один пакет и внесены
   необходимые правки совместимости, **Then** все гейты зелёные, соответствующая функциональность не
   изменилась.
2. **Given** обновление phpspreadsheet до 5.x, **When** прогнаны сценарии генерации Excel-выгрузок,
   **Then** файлы формируются с тем же содержимым и структурой, что и до апгрейда.

---

### User Story 4 - Обновление рантайма PHP до 8.5 (Priority: P2)

Поднять PHP-рантайм до 8.5 (в Dockerfile и требованиях проекта), убедиться, что все зависимости
совместимы, гейты зелёные и приложение работает.

**Why this priority**: Даёт актуальный язык, но безопаснее выполнять после обновления пакетов, часть
которых может ограничивать поддерживаемую версию PHP.

**Independent Test**: На PHP 8.5 все гейты зелёные и приложение поднимается локально.

**Acceptance Scenarios**:

1. **Given** обновлённые пакеты, **When** рантайм переведён на PHP 8.5, **Then** зависимости
   устанавливаются без конфликтов, все гейты зелёные, поведение не изменилось.

---

### User Story 5 - Обновление инфраструктурных образов (Priority: P3)

Поднять docker-образы: MySQL 8.0.27 → 8.4 LTS (или новее), Redis 6.2 → 7/8, Nginx 1.21 → текущий
стабильный. Каждый образ — отдельный шаг, с бэкапом БД перед пересозданием контейнера MySQL.

**Why this priority**: Не влияет на код приложения напрямую; выполняется в последнюю очередь и
затрагивает окружение/деплой, где нужен отдельный аккуратный порядок (бэкап, downtime).

**Independent Test**: После обновления каждого образа приложение поднимается на новом образе локально,
данные MySQL сохранены, гейты зелёные.

**Acceptance Scenarios**:

1. **Given** снятый бэкап БД, **When** образ MySQL поднят до целевой версии и контейнер пересоздан,
   **Then** данные на месте, приложение работает, гейты зелёные.
2. **Given** образы Redis и Nginx, **When** каждый поднят до целевой версии по одному, **Then**
   кэш/очереди и веб-слой работают как раньше.

---

### Edge Cases

- Что делать, если пакет ещё не поддерживает PHP 8.5 или целевую версию Laravel? — шаг блокируется:
  фиксируем, ищем совместимую версию/альтернативу либо откладываем шаг, не ломая зелёную линию.
- Что делать, если после мажорного апгрейда падают тесты? — шаг изолирован в отдельном коммите и
  откатывается точечно, не затрагивая остальные.
- Что делать при мажорном прыжке MySQL «через версию» (например, 8.0 → 9.x) — понижение недопустимо;
  переход только вперёд, с бэкапом и проверкой апгрейда формата данных.
- Что делать, если недостаточно тестового покрытия, чтобы доказать «поведение не изменилось»? —
  на затронутом участке добавляется недостающая проверка перед апгрейдом (базовая линия).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Каждый апгрейд ОБЯЗАН выполняться отдельным шагом, затрагивающим ровно одну вещь (один
  мажорный пакет, одна группа безопасных обновлений или один инфраструктурный образ).
- **FR-002**: Перед переходом к следующему шагу ОБЯЗАНЫ быть зелёными все гейты качества:
  автотесты, статический анализ, проверка стиля, rector (с просмотром diff).
- **FR-003**: После каждого шага приложение ОБЯЗАНО запускаться и работать локально.
- **FR-004**: Каждый шаг ОБЯЗАН быть оформлен отдельным изолированным коммитом, допускающим точечный
  откат.
- **FR-005**: Фича НЕ ДОЛЖНА менять бизнес-логику, поведение или архитектуру — только версии.
- **FR-006**: Laravel ОБЯЗАН обновляться по одному мажору (11→12, затем 12→13), а не прыжком.
- **FR-007**: Заброшенный пакет `rector/rector-laravel` ОБЯЗАН быть заменён на поддерживаемый
  `driftingly/rector-laravel`.
- **FR-008**: Перед обновлением образа MySQL ОБЯЗАН быть снят бэкап БД; данные ОБЯЗАНЫ сохраниться
  после пересоздания контейнера.
- **FR-009**: Версии инфраструктурных образов ОБЯЗАНЫ быть зафиксированы в файлах репозитория
  (docker-compose/Dockerfile), а не браться как `latest`.
- **FR-010**: По завершении фичи весь стек ОБЯЗАН быть на актуальных поддерживаемых версиях из раздела
  Assumptions; неиспользуемые пакеты удалены; версии, ограниченные фреймворком (guzzle), подняты до
  максимально допустимой.
- **FR-011**: Если шаг заблокирован несовместимостью, он ОБЯЗАН быть зафиксирован и не должен ломать
  зелёную линию предыдущих шагов.

### Key Entities

Не применимо — фича не вводит и не меняет доменные сущности.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% шагов апгрейда завершаются с зелёными гейтами (тесты, стат-анализ, стиль, rector)
  до перехода к следующему шагу.
- **SC-002**: Ноль изменений наблюдаемого поведения приложения по сравнению с состоянием до апгрейда
  (все ранее проходившие тесты продолжают проходить; ключевые пользовательские сценарии работают
  идентично).
- **SC-003**: Каждый шаг представлен отдельным коммитом, который можно откатить, не затрагивая
  остальные шаги.
- **SC-004**: После завершения ноль зависимостей помечены как abandoned; ноль образов используют тег
  `latest` — все версии зафиксированы в репозитории.
- **SC-005**: Весь целевой стек на актуальных поддерживаемых версиях (PHP 8.5, Laravel 13.x и остальное
  из Assumptions); неиспользуемый doctrine/dbal удалён; используемый predis не «на latest», а поднят до
  актуального мажора (2.x/3.x) — Redis-клиент стандартизирован на predis (см. Assumptions / research
  Decision 2).
- **SC-006**: Данные БД полностью сохранены после обновления инфраструктурных образов.

## Assumptions

- Целевые версии на момент планирования (2026-08): PHP 8.5; laravel/framework 13.x;
  phpoffice/phpspreadsheet 5.x; **doctrine/dbal — удаляется** (не используется); **predis/predis —
  апгрейд** до 2.x/3.x, Redis-клиент стандартизирован на predis (исходное решение «удалить predis в
  пользу phpredis» развёрнуто: predis реально в `.env`, phpredis не установлен — см. research Decision 2 /
  T010); guzzlehttp/guzzle — максимум в рамках constraint фреймворка
  (снятие пина до `^7.10`, мажор 8 условен); phpunit 13.x; dev-инструменты (php-cs-fixer, larastan, phpstan, rector,
  mockery), horizon, sentry-laravel — последние совместимые; MySQL 8.4 LTS (или новее), Redis 7/8,
  Nginx — текущий стабильный. Конкретные патч-версии фиксируются на этапе plan/tasks по факту.
- «Поведение не изменилось» проверяется существующим набором автотестов + ручной проверкой ключевых
  сценариев локально; при нехватке покрытия на затронутом участке добавляется базовая проверка.
- Апгрейды инфраструктуры выполняются в окружении с Docker Compose; для MySQL допускается кратковременный
  downtime при пересоздании контейнера.
- Порядок шагов: безопасные обновления → Laravel (11→12→13) → мажорные библиотеки → PHP 8.5 →
  инфраструктурные образы. Порядок может уточняться, если ограничения совместимости этого потребуют.
- Фича соответствует конституции проекта (принцип «только вперёд», гейты качества CS/STAN/Rector/тесты,
  фиксация версий окружения в репозитории).
