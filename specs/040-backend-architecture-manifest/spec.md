## User Scenarios & Testing *(mandatory)*

### User Story 1 - Проверка новой фичи по единым правилам (Priority: P1)

Разработчик и AI-агент перед проектированием новой серверной фичи находят одно обязательное руководство. Оно объясняет границы слоёв, путь записи и чтения, работу доменных событий, фиксацию автора и времени изменения, удаление и проверку PR.

**Why this priority**: Без согласованной нормы новые изменения продолжают закреплять разные подходы.

**Independent Test**: По инструкциям агента и конституции можно найти руководство и оценить новый сценарий записи без устных пояснений.

**Acceptance Scenarios**:

1. **Given** агент начинает новую серверную фичу, **When** он читает обязательные инструкции проекта, **Then** он получает ссылку на актуальное руководство и применяет его к плану и ревью.
2. **Given** PR меняет агрегат, **When** ревьюер проходит проверочный список, **Then** он может проверить команду, транзакцию, доменный переход, `updated`, событие, сохранение, очередь и тесты.

---

### User Story 2 - Обоснованный обзор существующего бэкенда (Priority: P1)

Разработчик видит карту текущей архитектуры и конкретные расхождения с целевой моделью, каждое с указанием файлов, последствий и размера безопасного следующего шага.

**Why this priority**: Общий лозунг «привести к DDD» не помогает выбирать безопасные задачи.

**Independent Test**: Для каждого важного раздела бэкенда есть текущий путь, целевое правило и подтверждённый исходным кодом пример; найденные нарушения можно воспроизвести при чтении файлов.

**Acceptance Scenarios**:

1. **Given** разработчик ищет источник события, **When** он следует карте от входа до обработчика, **Then** он находит места записи, публикации, очереди и побочных эффектов.
2. **Given** команда выбирает следующий рефакторинг, **When** она читает реестр долга, **Then** она видит приоритет, зависимость, риск и проверяемый результат.

---

### User Story 3 - Согласованная политика жизненного цикла агрегатов (Priority: P2)

Команда принимает явные правила о мутациях, событиях, аудите и выключении объектов, включая исключения для технических записей и старой схемы.

**Why this priority**: Без границы между бизнес-переходом и техническим обновлением требование «каждая мутация создаёт событие» может породить шум и циклы обработчиков.

**Independent Test**: На примерах `Event`, `Group`, `Club`, `Competition`, `ProtocolLine` и `RankCheck` можно однозначно определить ожидаемый `updated`, событие и способ удаления.

**Acceptance Scenarios**:

1. **Given** метод изменяет состояние агрегата, **When** применяется политика, **Then** понятно, должен ли он обновить аудит и записать доменное событие.
2. **Given** команда удаляет объект, **When** применяется политика, **Then** понятно, требуется ли `disable()` или физическое удаление, и как сохранить существующие данные.

### Edge Cases

- Агрегат без полей аудита или с отключёнными timestamps, например `ProtocolLine`.
- Отмена транзакции после публикации события и повторная попытка фоновой задачи.
- Повторное сохранение одного объекта и повторная отправка старых событий.
- Массовая техническая переработка данных и импорт, где событие на каждую строку может быть ошибкой.
- Существующие исключения из целевой архитектуры и код, который эта документационная фича не переписывает.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Документация MUST описать фактические слои и направления зависимостей бэкенда с доказательствами из кода и отделить их от целевого состояния.
- **FR-002**: Документация MUST описать сценарии записи, чтения, транзакций, сериализации, ошибок, событий, очередей и кэша на конкретных примерах проекта.
- **FR-003**: Манифест MUST определить инвариант наблюдаемой бизнес-мутации агрегата: намеренный метод, аудит изменения, доменное событие, сохранение и тестирование. Для технического пересчёта без самостоятельного бизнес-смысла решение о событии принимается явно и обосновывается в спецификации сценария; изменение проекции или связанной записи не выдаётся за переход агрегата.
- **FR-004**: Манифест MUST определить политику удаления и видимости данных. Для бизнес-сущностей с `active` целевой способ — намеренный `disable()` с аудитом и событием. Физическое удаление допускается для временных/производных записей по документированному решению для типа данных.
- **FR-005**: Манифест MUST сохранить цель независимого от Eloquent Domain и описать постепенное выделение доменной модели из нынешних Eloquent-агрегатов без одномоментной переписи.
- **FR-006**: Обзор MUST содержать паттерны, антипаттерны и приоритетный реестр ограниченных по объёму рефакторингов с путём к коду, риском, зависимостями и критерием завершения.
- **FR-007**: Обязательные инструкции для AI-агентов и конституция MUST ссылаться на канонический манифест и требовать применения при новых фичах и PR review. При расхождении манифеста с конституцией приоритет у конституции.
- **FR-008**: Новые документы MUST различать обязательную норму, действующий переходный код и предложение к рефакторингу; прежние спецификации сохраняют роль исторических решений.
- **FR-009**: Этот цикл MUST завершить документацию и интеграцию инструкций без изменения поведения приложения и без массового рефакторинга выявленного долга.

### Key Entities

- **Архитектурное правило**: обязательное требование, источник решения, область действия, известные исключения.
- **Наблюдение**: конкретный путь в коде, наблюдаемое поведение, последствия, уверенность.
- **Задача рефакторинга**: приоритет, затрагиваемые компоненты, зависимости, безопасный шаг, критерий завершения.
- **Сценарий обработки события**: источник, сохранение, публикация, доставка, обработчик и эффект.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Все четыре целевых слоя, legacy-границы и минимум пять ключевых потоков бэкенда описаны с действующими ссылками на файлы.
- **SC-002**: Для каждого обнаруженного высокоприоритетного расхождения указаны путь к коду, риск, приоритет и проверяемый следующий шаг.
- **SC-003**: Не менее двух входных инструкций AI-агентов и конституция указывают на один канонический манифест.
- **SC-004**: Руководство позволяет определить аудит, событие и политику удаления для каждого перечисленного в обзоре агрегата либо отмечает ещё не принятое решение.
- **SC-005**: Ни один файл приложения, миграция или тест не меняется в этой документационной фиче.

## Assumptions

- Обзор фиксирует состояние текущей рабочей копии на 2026-09-26; найденный долг становится очередью будущих фич, а не скрытым объёмом этой работы.
- Под «манифестом» понимается каноническое руководство, на которое ссылаются конституция и инструкции AI-агентов.
- Правила для V1 API из действующей конституции сохраняются, если уточнения пользователя их прямо не меняют.

## Clarifications

### Session 2026-09-27

- Q: Какую модель Domain принять? A: Рабочее решение после просьбы продолжить: сохранить уже закреплённую в конституции цель чистого Domain; нынешние Eloquent-агрегаты считать переходным кодом. Это решение можно изменить отдельной поправкой к конституции.
- Q: Каждое ли изменение требует события? A: Рабочее решение: каждое наблюдаемое бизнес-изменение агрегата требует события и аудита. Технический пересчёт рассматривается по смыслу сценария, исключение документируется.
- Q: Какой soft delete принять? A: Рабочее решение: для бизнес-сущностей с `active` использовать `disable()`; для временных или производных записей физическое удаление допускается после явного решения по типу.
