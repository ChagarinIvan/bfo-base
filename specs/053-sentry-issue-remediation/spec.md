# Feature Specification: Разбор и исправление ошибок Sentry

**Feature Branch**: master, текущая ветка сохранена
**Created**: 2026-11-01
**Status**: Implemented and locally validated; production verification pending deployment
**Input**: Новый spec-kit, полный прогон. Посмотреть и разобраться с каждой ошибкой проекта https://chagarin.sentry.io/issues/?project=4509139044335616.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Учесть каждую ошибку проекта (Priority: P1)

Ответственный за приложение получает полный реестр ошибок из указанного списка,
их контекст, причину и решение по каждой записи.

**Why this priority**: Без полного реестра нельзя подтвердить разбор каждой ошибки.
**Independent Test**: Сверить все страницы списка Sentry с реестром issue IDs.

**Acceptance Scenarios**:

1. **Given** доступен список проекта, **When** выполнена инвентаризация,
   **Then** учтены все страницы, записаны фактические фильтры, период и время снимка.
2. **Given** issue из снимка, **When** выполняется разбор, **Then** есть ссылка,
   exception/message, стектрейс, release/environment, частота и даты появления
   в пределах доступных данных, затронутый сценарий и подтверждённая причина.
3. **Given** похожие issues, **When** найдена общая причина, **Then** решение может
   быть общим, но исходные IDs не исчезают из реестра и каждому присвоен результат.
4. **Given** нет доступа к исходным событиям, **When** готовится отчёт, **Then**
   отсутствие данных отмечено явно, причины и исправления не выдумываются.

### User Story 2 - Исправить подтверждённые дефекты (Priority: P1)

Пользователь может повторить проблемный сценарий без прежней ошибки, а разработчик
получает регрессионное покрытие каждого исправленного поведения.

**Why this priority**: Разбор должен завершаться конкретным решением, а не списком заголовков.
**Independent Test**: Для каждого изменения регрессия воспроизводит исходный дефект
и проходит после исправления; связь test/issue указана в реестре.

**Acceptance Scenarios**:

1. **Given** подтверждён текущий дефект кода, **When** он исправляется,
   **Then** сначала добавлена воспроизводящая регрессия, затем узкое исправление.
2. **Given** событие относится к старой версии, окружению или внешнему сбою,
   **When** выполнена проверка текущего кода и контекста, **Then** записаны evidence,
   классификация и конкретное необходимое действие, без фиктивного изменения кода.
3. **Given** ожидаемая пользовательская ошибка, **When** меняется обработка,
   **Then** сохраняется API-контракт, а неожиданные системные ошибки остаются наблюдаемыми.

### User Story 3 - Подтвердить полноту исправлений (Priority: P2)

Reviewer получает связанный комплект spec-kit и отчёт с результатом для каждой ошибки.

**Why this priority**: Исправления должны быть проверяемы и не ухудшать другие сценарии.
**Independent Test**: Сверить реестр с тестами, изменениями и итоговыми гейтами.

**Acceptance Scenarios**:

1. **Given** завершены исправления, **When** выполняется полный прогон,
   **Then** проходят CS, PHPStan, Rector dry-run, PHP tests и frontend CI.
2. **Given** реестр из N issues, **When** проводится converge, **Then** все N
   имеют подтверждённый результат либо конкретный нерешённый блокер.
3. **Given** локально прошла регрессия, **When** составляется отчёт, **Then**
   локальный результат отделён от факта выкладки и наблюдения production после неё.

### Edge Cases

- Список issues меняется во время работы; отдельно фиксируется снимок и новые поступления.
- Отсутствующий release, неполный стектрейс или удалённый event не подменяются догадкой.
- Стектрейсы могут содержать секреты и персональные данные; в specs входят только
  необходимые обезличенные факты и ссылки, без токенов, паролей и полного request payload.
- Ошибка повторной доставки, транзакции или N+1 требует проверки соответствующего инварианта.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: MUST быть получен полный снимок списка указанного проекта с пагинацией
  и фактическими параметрами отбора, без молчаливого сокращения списка.
- **FR-002**: Каждая issue MUST иметь отдельную запись в issue-inventory.md с evidence,
  классификацией причины, решением и проверкой результата.
- **FR-003**: Исправление поведения MUST иметь регрессионный тест до реализации.
- **FR-004**: Решения MUST соблюдать конституцию, целевые слои и существующие API-контракты.
- **FR-005**: Ошибки MUST не скрываться массовым ignore, снижением наблюдаемости
  или ручным закрытием issues без подтверждённого решения.
- **FR-006**: MUST быть выполнены полный spec-kit, review spec/plan, tasks, analyze,
  реализация и converge, включая итоговые гейты и запись updates.
- **FR-007**: Секреты и персональные данные MUST не попадать в артефакты репозитория.
- **FR-008**: Validation MUST явно перечислить нерешённые issues и непроверенные
  production-результаты; отсутствие доступа не считается отсутствием ошибок.

### Key Entities

- **Sentry issue**. Группа событий с ID, ссылкой, контекстом и метриками появления.
- **Evidence snapshot**. Зафиксированный список, условия отбора и доступные события.
- **Решение по issue**. Причина, код или действие окружения, regression evidence и результат.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% issues снимка присутствуют в реестре и имеют индивидуальный результат.
- **SC-002**: 100% исправленных дефектов поведения покрыты воспроизводящими регрессиями.
- **SC-003**: Все итоговые локальные quality gates проходят.
- **SC-004**: Ни один нерешённый issue не объявлен исправленным без evidence.

## Assumptions

- Полный прогон разрешён пользователем, дополнительные подтверждения фаз не требуются.
- Это новая фича 053. Ветка не переключается, серверное развёртывание не выполняется.
- Конкретные сценарии ошибок, границы затронутых агрегатов, commands, транзакций,
  Impression, событий и удаления уточняются по реальным событиям Sentry до плана.
- OAuth-доступ восстановлен. Снимок MCP за 90 дней содержит 9 issues, без фильтра статуса.
- Изменять статусы issues или настройки Sentry не требуется.

## Clarifications and concrete acceptance scenarios

Уточнение 2026-11-01 по реальным событиям, без дополнительных вопросов пользователю.

- FC/FD: один POST на неизвестный путь вызывает warning и вложенный fatal при
  отправке заголовков. Некорректный multipart локально воспроизводит ту же цепочку.
  При production-конфигурации startup warning должен попасть в лог, HTTP-ответ
  должен сохранить корректный статус и не содержать диагностического вывода.
  Точное содержимое исходного запроса недоступно, совпадение причины вероятное.
- F6: при импорте 1 и 50 различных существующих групп поиск groups выполняется
  одним SELECT на вызов фабрики. Новая группа создаётся один раз, inactive не
  переиспользуется, пустой импорт не читает groups. Кэши не переходят между импортами.
- FB: повторная доставка назначения со спортсменом, который уже выключен,
  не падает при очистке прежнего спортсмена и не публикует повторный PersonDisabled.
  Прямое выключение отсутствующего спортсмена сохраняет PersonNotFound;
  неожиданный сбой хранилища не проглатывается.
- F8/F9/FA: текущая миграция и реальные записи подтверждают наличие и применение
  next_rank_activation_on; инструкции выкладки требуют миграцию до возобновления workers.
- F7: текущие новые строки сохраняют delayed_rank_activation=false и реальный
  collector передаёт bool. Отсутствие колонки в старом deployment является
  гипотезой, а не установленным фактом. Null fallback, скрывающий проблему схемы, запрещён.
- F0: контейнер успешно собирает ParseEventProtocolHandler и ProtocolParser;
  после выкладки старые queue workers должны быть перезапущены.

## Architectural scope

Исправления сохраняют существующие commands, API и транзакции импорта/выключения.
Group и Distance создаются через имеющиеся factories/repositories. ProtocolLine
получает прежние Impression и события. Кэш действует только в пределах create().
Очистка Person после commit остаётся soft disable через DisablePersonService,
с Impression и PersonDisabled ровно для состоявшегося перехода. Повторный cleanup
отсутствующей активной записи является no-op только в этом обработчике.
ProtocolLine/Distance остаются производными данными при замене протокола.
Существующий Eloquent в Domain является переходным REF-13, новые framework
зависимости не добавляются; выделение чистых моделей остаётся отдельной задачей.
