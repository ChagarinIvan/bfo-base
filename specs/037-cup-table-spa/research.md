# Исследование: таблица кубка в SPA

## Наблюдения

- `CupViewPage` уже загружает карточку и список `CupEvent`, но кнопка таблицы
  ведёт в legacy `/cups/{id}/{group}/table`.
- `PersonLayoutPage` + child routes + `PersonInfoNavigation` дают нужный UX для
  вкладок без полного refresh.
- Blade `cup/table.blade.php` показывает номер, FIO, год, клуб, колонку каждого
  этапа, сумму, среднее и место. Этапные значения ссылаются на protocol line;
  зачётные значения выделяются.
- `ListCupEventPoints` API отдаёт строки одного этапа и не может собрать итоговую
  таблицу: для таблицы нужны все этапы, сортировка по месту и правила cup type.
- `CupEventsService::calculateCup()` — текущий источник поведения, но находится в
  legacy `app/Services`; новый V1 query должен изолировать его использование и
  не копировать scoring code в SPA или контроллер.
- `ListingTable` умеет скрывать колонки и хранить настройки, но для этапных
  колонок нужен отдельный запрет toggle.
- `ListCupEventPointsService` уже задаёт нужную семантику: обязательный group
  context, optional name, case-insensitive contains и отдельная проверка короткого
  имени на frontend/API boundary.

## Решения

1. Добавить отдельный агрегированный read endpoint вместо N запросов по этапам.
2. Использовать nested route layout, чтобы карточка не размонтировалась при
   переключении нижней части.
3. Передавать обязательный `groupId` из селекта группы и выполнять фильтр имени на
   backend после/вместе с расчётом, с минимальной длиной три символа на SPA и
   серверной валидацией того же правила.
4. Отдавать в контракте IDs для перехода к protocol line, а не строить URL в
   backend.

## Не выбранные варианты

- Собрать таблицу только на frontend из `getCupEventPoints`: потребует много
  запросов, дублирует расчёт cup type и ломает server pagination.
- Оставить Blade таблицу внутри SPA: это не даёт вкладок без reload и не является
  V1 data flow.
- Передавать все рассчитанные строки без pagination: нарушает API pagination и
  плохо масштабируется.
