# Feature Specification: SPA View Person

**Feature Branch**: \`017-persons-spa-view\`

**Created**: 2026-09-06

**Status**: Draft

**Input**: Перенести страницу View Person с Blade на SPA: сверху показать общий модуль Person Info, затем сохранить четыре действия из текущей страницы — редактирование персоны, оплаты, промпты и разряды — и показать таблицу соревнований, в которых участвовала персона. Таблица должна фильтроваться по году, названию соревнования и дате. Для таблицы добавить JSON API списка строк протокола с загрузкой данных соревнования и события через \`withCompetition\` и \`withEvent\`.

## User Scenarios & Testing

### User Story 1 - Просмотр страницы персоны (Priority: P1)

Авторизованный или неавторизованный пользователь открывает страницу конкретной персоны в SPA и видит её основные сведения в общем модуле Person Info, одинаковом с разделами оплат и промптов.

**Why this priority**: Это основной экран персоны и точка входа в её связанные разделы.

**Independent Test**: Открыть SPA-страницу существующей персоны и неизвестного идентификатора; проверить Person Info, loading/error/not-found состояния и отсутствие лишних запросов к данным персоны.

**Acceptance Scenarios**:

1. **Given** существует активная персона, **When** пользователь открывает её SPA-страницу, **Then** сверху отображается общий Person Info с фамилией, именем, датой рождения, разрядом, клубом и impressions.
2. **Given** идентификатор персоны неизвестен или персона неактивна, **When** страница загружается, **Then** отображается понятное not-found/error состояние без таблицы.
3. **Given** данные персоны ещё загружаются, **When** пользователь видит страницу, **Then** отображается loading-состояние, а содержимое не дублируется устаревшим ответом.

### User Story 2 - Переходы в разделы персоны (Priority: P1)

Пользователь использует действия на странице персоны, чтобы перейти к редактированию, оплатам, промптам или разрядам.

**Why this priority**: Эти действия являются существующими точками входа и не должны потеряться при миграции с Blade.

**Independent Test**: Проверить href/router destination каждой кнопки для авторизованного пользователя и публичную доступность ссылки на разряды.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован, **When** он видит страницу персоны, **Then** отображаются действия редактирования, оплат, промптов и разрядов.
2. **Given** пользователь не авторизован, **When** он видит страницу персоны, **Then** отображается публичное действие разрядов, а действия редактирования, оплат и промптов не позволяют обойти авторизацию.
3. **Given** пользователь нажимает действие, **When** переход выполняется, **Then** открывается существующий раздел с тем же \`personId\`.
4. **Given** пользователь переключается между SPA-разделами персоны, **When** открываются оплаты или промпты, **Then** переход выполняется как вкладка, общий Person Info с действиями остаётся смонтированным и повторно не загружает данные персоны.

### User Story 3 - Просмотр участия в соревнованиях (Priority: P1)

Пользователь видит таблицу строк протокола, связанных с персоной, с теми же данными и ссылками, что и на текущей Blade-странице.

**Why this priority**: История участия — основная содержательная часть страницы View Person.

**Independent Test**: API-запрос с \`personId\` возвращает строки протокола с данными competition/event, а SPA отображает их в таблице с пустым состоянием и пагинацией.

**Acceptance Scenarios**:

1. **Given** у персоны есть строки протокола, **When** таблица загружается, **Then** каждая строка показывает соревнование, событие, фамилию и имя, дату, группу, год рождения, результат, место и полный разряд.
2. **Given** строка содержит соревнование или событие, **When** пользователь нажимает название, **Then** ссылка ведёт на существующую SPA- или web-страницу соответствующего объекта с правильным идентификатором.
3. **Given** у персоны нет строк протокола, **When** загрузка завершена, **Then** отображается ясное empty state вместо пустой таблицы.
4. **Given** API возвращает строки для страницы, **When** загружается результат, **Then** необходимые данные competition и event доступны из одного API-контракта и не требуют N+1-запросов.

### User Story 4 - Фильтрация участия (Priority: P1)

Пользователь фильтрует таблицу участия по году, названию соревнования и дате.

**Why this priority**: Фильтры делают историю участия пригодной для поиска среди большого числа стартов.

**Independent Test**: Выполнить API-запросы с каждым фильтром и проверить, что SPA сбрасывает страницу пагинации и показывает только подходящие строки.

**Acceptance Scenarios**:

1. **Given** открыт список участия, **When** пользователь выбирает год, **Then** запрос ограничивается событиями этого года.
2. **Given** открыт список участия, **When** пользователь вводит название соревнования, **Then** запрос ограничивается соревнованиями, название которых соответствует поиску.
3. **Given** открыт список участия, **When** пользователь выбирает дату, **Then** запрос ограничивается событиями этой даты.
4. **Given** фильтр изменён во время предыдущего запроса, **When** ответы приходят в другом порядке, **Then** устаревший ответ не перезаписывает актуальный список.
5. **Given** фильтры имеют некорректный формат, **When** запрос отправляется, **Then** API возвращает стандартную validation error, а SPA показывает ошибку поля без потери остальных фильтров.

## Edge Cases

- Неизвестная или неактивная персона возвращает not-found состояние для Person Info, а список участия возвращает пустой результат.
- Неизвестный или недоступный \`personId\` не должен возвращать строки другого человека.
- Пустые значения фильтров не должны ограничивать выборку.
- Слишком короткий поиск по названию не отправляет лишние запросы, не блокирует поле и не сбрасывает введённое значение; используется общий debounce-паттерн списка соревнований.
- Ошибка API, отсутствие сети и validation error отображаются отдельно от empty state.
- Страница должна использовать общую пагинацию и загружать только текущую страницу строк протокола.

## Requirements

### Functional Requirements

- **FR-001**: Система MUST предоставлять SPA-маршрут просмотра активной персоны по \`/app/persons/{personId}\`.
- **FR-002**: Страница MUST использовать общий модуль Person Info, одинаковый с страницами оплат и промптов.
- **FR-003**: Страница MUST сохранять четыре действия текущей Blade-страницы: редактирование, оплаты, промпты и разряды; действия с существующей авторизацией MUST сохранять её ограничения. Действия MUST находиться внутри общего Person Info блока, а SPA-разделы оплат и промптов MUST открываться вложенными вкладками без размонтирования этого блока.
- **FR-004**: Система MUST предоставлять доступ к данным ровно в соответствии с текущими API-политиками просмотра персоны и строк протокола.
- **FR-005**: Система MUST предоставлять JSON API списка строк протокола конкретной персоны с обязательным \`personId\`, пагинацией и стабильным порядком по дате события и идентификатору строки.
- **FR-006**: API MUST поддерживать query-параметры \`withCompetition\` и \`withEvent\`; при их включении ответ MUST содержать данные, необходимые для названий и ссылок соревнования и события.
- **FR-007**: API MUST поддерживать фильтры \`year\`, \`competitionName\` и \`date\` и валидировать их форматы.
- **FR-008**: Ответ строки протокола MUST содержать идентификаторы и отображаемые поля: \`id\`, \`personId\`, \`firstname\`, \`lastname\`, \`distanceId\`, \`competitionId\`, \`competitionName\`, \`eventId\`, \`eventName\`, \`eventDate\`, \`groupName\`, \`year\`, \`time\`, \`place\`, \`completeRank\`.
- **FR-009**: SPA MUST отображать для таблицы колонки соревнования, события, имени участника, даты, группы, года рождения, результата, места и полного разряда.
- **FR-010**: SPA MUST предоставлять общие компоненты фильтра года, строки названия и даты внутри одного блока фильтров, а изменение фильтра MUST возвращать список на первую страницу. Поиск названия короче минимальной длины MUST оставаться в поле, не отправлять validation-запрос и не терять фокус.
- **FR-011**: SPA MUST отображать loading, error, not-found и empty состояния, а также блокировать устаревшим ответам изменение актуального списка.
- **FR-012**: API и SPA MUST загружать данные competition и event через typed resources \`withCompetition\` и \`withEvent\`, исключая N+1 при построении ответа.
- **FR-013**: Изменения поведения MUST быть покрыты application/unit, API/integration и SPA-тестами; новые тесты MUST проходить без новых deprecation/notices.

### Key Entities

- **Person**: существующая активная персона, являющаяся контекстом страницы и владельцем строк протокола.
- **ProtocolLine**: строка результата участника на дистанции; содержит участника, результат, место, год рождения, полный разряд и ссылки на distance/event.
- **Event**: старт с названием и датой, связанный с дистанцией и соревнованием.
- **Competition**: соревнование, название которого используется в таблице и фильтре.
- **ProtocolLineResources**: typed-настройки чтения связанных competition и event для API-ответа.
- **ProtocolLineSearch**: фильтры \`personId\`, \`year\`, \`competitionName\`, \`date\`, пагинация и флаги ресурсов.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Пользователь видит Person Info и действия страницы после одного перехода на SPA-маршрут без открытия Blade View Person.
- **SC-002**: Для персоны с участием таблица показывает данные первой страницы и фильтрацию по каждому из трёх фильтров без ручного обновления страницы.
- **SC-003**: При смене фильтра устаревший результат не отображается вместо актуального в 100% автоматизированных race-condition тестов.
- **SC-004**: API возвращает все данные первой страницы таблицы без дополнительных запросов на каждую строку; это подтверждается query-count тестом.
- **SC-005**: Все acceptance scenarios покрыты автоматизированными API и SPA тестами.

## Assumptions

- Существующий \`PersonPromptPersonInfo\` используется как общий Person Info-компонент; его переименование и визуальная переработка не входят в эту фичу.
- Общие SPA-компоненты \`FilterPanel\`, \`YearFilter\`, \`DateFilter\`, debounce и paginator переиспользуются без создания параллельных реализаций.
- Ссылка редактирования остаётся существующим web-route \`/persons/{personId}/edit\`, а ссылка разрядов — \`/ranks/person/{personId}\`; миграция этих разделов в SPA не входит в эту фичу.
- API просмотра и списка доступно с теми же auth-политиками, что и текущие публичные страницы просмотра; мутационные разделы продолжают защищаться SPA auth guard.
- `/app/persons/{personId}` является родительским SPA layout-маршрутом для View Person, оплат и промптов; общий Person Info и действия размещаются в нём, а контент раздела — во вложенном RouterView.
- Таблица использует серверную пагинацию; её порядок — дата события по убыванию, затем идентификатор строки по убыванию.
- Участие фильтруется по названию соревнования, а не по названию события или группы.

## Out of Scope

- Перенос страниц редактирования персоны и истории разрядов на SPA.
- Изменение доменных данных строк протокола, расчёта результатов или привязки персоны к строке.
- Удаление Blade View Person и связанных web routes до отдельного аудита потребителей.
- Новые действия над строками протокола из таблицы.
