# Feature Specification: Count-Free Slice Pagination

**Feature Branch**: `027-count-free-slice-pagination`

**Created**: 2026-09-17

**Status**: Draft

**Input**: User description: "Новый спек с полным флоу: сделать полноценный slice вместо pagination, не вызывать count в базе, проверить все listing-сервисы и фильтрации, добавить нужные индексы и join-ы для максимально быстрых запросов."

## Clarifications

### Session 2026-09-17

- Q: Где должен возвращаться признак `hasNext` для API-списков? → A: В pagination-заголовке `X-Pagination-Has-Next: true/false`; тело ответа остаётся массивом элементов.
- Q: Нужно ли полностью убрать заголовки `X-Pagination-Total` и `X-Pagination-Last-Page` из ответов? → A: Да; остаются `X-Pagination-Current-Page`, `X-Pagination-Per-Page` и `X-Pagination-Has-Next`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр списка без подсчёта общего количества (Priority: P1)

Авторизованный пользователь открывает любой поддерживаемый список и листает его по страницам. Список показывает доступные записи и позволяет понять, есть ли следующая страница, не требуя вычисления общего количества записей.

**Why this priority**: Подсчёт больших отфильтрованных наборов является основной причиной медленных listing-запросов и не даёт пользователю ценности, если ему нужно только продолжить или остановить просмотр.

**Independent Test**: На наборе данных, достаточно большом для медленного `COUNT`, запросить первую и последнюю доступную страницу каждого поддерживаемого списка, проверить состав элементов и признак следующей страницы, а отдельным регрессионным тестом Slice доказать, что система читает ровно `perPage + 1` запись без вызова `COUNT`.

**Acceptance Scenarios**:

1. **Given** список содержит больше записей, чем размер страницы, **When** пользователь запрашивает страницу, **Then** система возвращает не больше заданного размера страницы и сообщает, что следующая страница существует.
2. **Given** пользователь запрашивает страницу без последующих записей, **When** список формируется, **Then** система возвращает доступные записи и сообщает, что следующей страницы нет.
3. **Given** пользователь запрашивает страницу с фильтрами, **When** фильтры применяются, **Then** признак следующей страницы относится именно к отфильтрованному набору.
4. **Given** список пуст, **When** пользователь запрашивает первую страницу, **Then** система возвращает пустой результат без ошибки и сообщает, что следующей страницы нет.
5. **Given** `perPage` равен 20 и выборка содержит 21 запись, **When** Slice получает страницу, **Then** он запрашивает 21 запись, возвращает первые 20, устанавливает `hasNext = true` и не вызывает `COUNT`.

### User Story 2 - Единый контракт для API и SPA (Priority: P1)

Пользователь получает одинаково понятное поведение пагинации во всех экранах и API-списках: текущая страница и размер страницы сохраняются, а навигация использует только наличие следующей страницы, не отображая выдуманные total/last page.

**Why this priority**: Единый контракт предотвращает разные правила на отдельных экранах и позволяет перевести существующие списки без скрытых зависимостей от общего количества.

**Independent Test**: Проверить все API-действия, возвращающие paginated listings, и соответствующие SPA-компоненты на первой, промежуточной и последней страницах, включая смену фильтра и размера страницы.

**Acceptance Scenarios**:

1. **Given** API-список поддерживает постраничный вывод, **When** клиент запрашивает страницу и размер страницы, **Then** ответ содержит элементы, заголовки `X-Pagination-Current-Page`, `X-Pagination-Per-Page` и `X-Pagination-Has-Next: true/false`, но не содержит `X-Pagination-Total` или `X-Pagination-Last-Page`.
2. **Given** клиент открывает страницу, для которой предыдущие данные больше не актуальны после изменения фильтра, **When** фильтр меняется, **Then** список начинается с первой страницы и получает новый признак следующей страницы.
3. **Given** клиент находится на странице без следующей страницы, **When** он использует навигацию списка, **Then** переход вперёд недоступен, а уже загруженные элементы не исчезают из-за отсутствия total.
4. **Given** запрос содержит недопустимый номер страницы или размер страницы, **When** API обрабатывает запрос, **Then** система возвращает существующую согласованную ошибку валидации и не выполняет тяжёлый listing-запрос.

### User Story 3 - Быстрые списки с фильтрами и связями (Priority: P1)

Оператор открывает списки людей, событий, групп, соревнований, клубов, платежей, prompts, строк протоколов, проверок разрядов и их строк с доступными фильтрами. Результаты приходят быстро и не меняют смысл фильтрации, сортировки или связанных данных.

**Why this priority**: Оптимизация только базового списка не решит проблему: самые тяжёлые запросы возникают на фильтрах, `join`, `distinct`, подсчётах связанных записей и eager-loading.

**Independent Test**: Составить матрицу всех listing-сервисов и их критериев, выполнить каждый поддерживаемый фильтр отдельно и в комбинациях, проверить результат, порядок, дубликаты, связи и план/количество SQL-запросов.

**Acceptance Scenarios**:

1. **Given** фильтр по полю основной сущности, **When** пользователь применяет его, **Then** возвращаются только подходящие записи в стабильном порядке.
2. **Given** фильтр требует связанной сущности, **When** пользователь применяет его, **Then** результат не содержит дубликатов основной сущности и связь загружается только когда она нужна представлению.
3. **Given** список отображает агрегат связанной сущности, **When** пользователь открывает страницу, **Then** агрегат остаётся корректным, но не запускает отдельный запрос на каждую строку.
4. **Given** фильтр не задан, **When** пользователь запрашивает список, **Then** система не добавляет лишние join-ы, фильтры и связи, не нужные для базового результата.
5. **Given** несколько записей имеют одинаковые значения сортировки, **When** пользователь переходит между страницами, **Then** порядок остаётся детерминированным и записи не повторяются и не пропускаются в рамках неизменившегося набора данных.

### User Story 4 - Безопасное улучшение схемы данных (Priority: P2)

Команда сопровождает систему и может применять улучшения производительности без потери данных или изменения бизнес-результатов списков.

**Why this priority**: Индексы и изменения запросов должны снижать стоимость чтения, но не создавать риск для существующих данных и записей.

**Independent Test**: Применить миграции на копии актуальной схемы, проверить обратимость там, где это возможно, сравнить результаты до и после для матрицы списков и измерить планы запросов на репрезентативном объёме данных.

**Acceptance Scenarios**:

1. **Given** база содержит существующие записи, **When** применяются изменения схемы, **Then** записи и их связи сохраняются, а миграция завершается без ручного исправления данных.
2. **Given** индекс не используется ни одним поддерживаемым listing-критерием, **When** проводится аудит схемы, **Then** он не добавляется только ради формального покрытия.
3. **Given** индекс или join улучшает один список, но ухудшает другой, **When** сравниваются планы и время запросов, **Then** решение принимается по измеряемому совокупному результату и фиксируется в артефактах фичи.

### Edge Cases

- Если число найденных записей ровно кратно размеру страницы, система проверяет одну дополнительную запись, чтобы отличить последнюю полную страницу от страницы с продолжением.
- Если клиент запрашивает страницу после удаления или изменения записей, система возвращает пустую страницу или доступные записи с корректным `hasNext`; ошибка из-за отсутствия total не возникает.
- Если во время чтения записи добавляются или удаляются, результат должен сохранять детерминированную сортировку; абсолютная консистентность полного набора между запросами не гарантируется.
- Если `join` по фильтру создаёт несколько совпадений для одной основной записи, запись возвращается один раз.
- Если фильтр содержит пустое значение, слишком короткий поиск или неизвестное поле сортировки, применяется существующая валидация/нормализация и не строится неконтролируемый запрос.
- Если связанная запись отключена или отсутствует, основная запись не должна исчезать, кроме случаев, когда это прямо определено критерием.
- Если размер страницы превышает допустимый предел, используется существующее безопасное ограничение.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставить полноценный count-free Slice-контракт для всех поддерживаемых paginated listing-сценариев.
- **FR-002**: Система MUST формировать страницу одним чтением ровно `perPage + 1` записи; наличие дополнительной записи MUST означать `hasNext = true`, а дополнительная запись MUST быть удалена из результата до его возврата клиенту.
- **FR-003**: Система MUST возвращать не более `perPage` элементов и заголовок `X-Pagination-Has-Next: true/false` для текущего набора критериев; при этом MUST NOT выполнять общий подсчёт совпадений или иной отдельный запрос для получения pagination-метаданных.
- **FR-004**: Система MUST сохранить поддержку текущей page/perPage-модели запросов в пределах фичи; переход на cursor-token pagination не входит в scope.
- **FR-005**: Система MUST удалить из count-free ответов заголовки `X-Pagination-Total` и `X-Pagination-Last-Page`, сохранив `X-Pagination-Current-Page`, `X-Pagination-Per-Page` и `X-Pagination-Has-Next`.
- **FR-006**: Система MUST сохранить действующие права доступа, состав DTO, значения фильтров, сортировку и семантику soft/inactive записей, если иное не указано отдельным контрактом.
- **FR-007**: Система MUST провести инвентаризацию всех Application listing-сервисов, Bridge listing-действий и Infrastructure query-адаптеров, включая списки людей, событий, групп, соревнований, клубов, платежей, prompts, protocol lines, rank checks и rank-check rows.
- **FR-008**: Для каждого инвентаризированного списка система MUST задокументировать поддерживаемые критерии, сортировку, required relations, join-ы, возможные дубликаты и требуемые индексы.
- **FR-009**: Система MUST проверять каждую комбинацию фильтров из контракта списка на корректность результата, стабильность порядка и отсутствие пропущенных/повторных элементов при переходе между страницами.
- **FR-010**: Система MUST добавлять только обоснованные индексы, покрывающие фактические условия фильтрации, join-ы и сортировку; миграции MUST сохранять данные и быть обратимыми, где это поддерживается текущей схемой.
- **FR-011**: Система MUST выбирать join, eager-loading или агрегирование связей так, чтобы фильтры работали корректно, ненужные связи не загружались, а listing не создавал N+1-запросы.
- **FR-012**: Система MUST сохранять детерминированный порядок каждой страницы с уникальным tie-breaker и явно фиксировать поведение для фильтров по связанным сущностям и `distinct`.
- **FR-013**: Система MUST валидировать page/perPage и неизвестные параметры до выполнения запроса, возвращая согласованный формат ошибки.
- **FR-014**: Система MUST предоставить один обязательный регрессионный тест Slice, который проверяет отсутствие `COUNT`, чтение ровно `perPage + 1`, обрезание дополнительной записи и вычисление `hasNext`; unit-, integration/API- и SPA-тесты также MUST покрывать фильтры, связи, пустые и граничные страницы.
- **FR-015**: Система MUST зафиксировать базовые и итоговые измерения производительности по каждому тяжёлому списку на репрезентативном наборе данных, включая latency, количество SQL-запросов и план выполнения.

### Key Entities

- **Slice result**: Упорядоченная порция элементов с текущим page, perPage и признаком наличия следующей порции; не содержит обязательного общего количества.
- **Listing criteria**: Набор нормализованных фильтров и правил сортировки конкретного списка.
- **Listing resource set**: Явно заявленный набор связей и полей, необходимых для отображения результата.
- **Listing query profile**: Зафиксированная связь между критерием, join/eager-loading, сортировкой, индексом, количеством запросов и измеренным временем.

## Success Criteria *(mandatory)

### Measurable Outcomes

- **SC-001**: 100% инвентаризированных paginated listing-сценариев формируют навигацию без обязательного общего количества и корректно сообщают наличие следующей страницы.
- **SC-002**: Обязательный регрессионный тест Slice подтверждает, что страница формируется одним чтением `perPage + 1` без общего `COUNT`, а дополнительная запись не попадает в ответ.
- **SC-003**: Не менее 95% запросов к тяжёлым спискам на согласованном репрезентативном наборе данных укладываются в 500 мс для первой страницы и 750 мс для страницы с фильтрами.
- **SC-004**: Ни один поддерживаемый фильтр не изменяет количество уникальных основных записей из-за join-ов, а переход между соседними страницами не создаёт повторов или пропусков при неизменном наборе данных.
- **SC-005**: Каждый список с отображаемыми связями выполняет не более согласованного базового числа запросов, не создавая N+1; целевое число и обоснование фиксируются в query profile.
- **SC-006**: Все существующие API/SPA acceptance-сценарии списков проходят без регрессии состава данных, доступа, фильтрации и сортировки; изменения UI ограничены отказом от недоступных total/last-page значений.
- **SC-007**: Применение миграций на копии production-подобной схемы не приводит к потере записей, связей или недоступности списков после миграции.

## Assumptions

- В фичу входят API и SPA listing-сценарии, которые уже используют page/perPage и Slice-подобный ответ; непагинированные `all()`/справочные выборки и batch/console-операции не переводятся автоматически.
- Page/perPage сохраняются как внешний способ навигации; count-free Slice использует внутреннюю дополнительную запись для вычисления `hasNext`, но не раскрывает её клиенту.
- Авторизация, DTO и бизнес-фильтры уже определены действующими контрактами и меняются только для устранения зависимости от total/lastPage.
- Изменения индексов выполняются отдельными миграциями с проверкой существующей схемы; удаление неиспользуемых индексов не является обязательной частью первой итерации без измерений.
- Производительность измеряется на данных, отражающих реальный масштаб и распределение фильтров; абсолютные результаты зависят от окружения, поэтому сравнение baseline/after обязательно.
- Полная атомарная выдача неизменяемого snapshot между несколькими page-запросами не входит в scope; стабильный порядок и отсутствие count-запроса входят.
