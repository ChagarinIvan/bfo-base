# Implementation plan. Обновление безопасности BFO Base и Lightsail

**Фича** `057-security-remediation`
**Дата** 2026-11-23
**Спецификация** [spec.md](spec.md)

## Summary

Два независимых потока. В репозитории обновляем Laravel и PHP в пределах поддерживаемых веток, проверяем зависимости и исправляем подтверждённые риски. В Lightsail определяем реальную конфигурацию, применяем доступные исправления, проверяем запущенные версии и при необходимости переносим Ubuntu 20.04 на Ubuntu 24.04.

## Technical context

- PHP 8.5, Laravel 13, MySQL 8.4, Redis 8, Nginx 1.28, Node.js 22 и SPA на Vue.
- Исходные версии Laravel 13.39.0 и PHP 8.5.12 для CI и Dockerfile. Целевые версии Laravel не ниже 13.43.0 и PHP 8.5.13. Поставщики и обоснование описаны в [research.md](research.md).
- В тестовом стеке обновляются Vitest до 5.1.1+ и Happy DOM до 21.0.4+. Минимальный Node.js 22.12, Vite остаётся в совместимой ветке 6.
- Изменения зависимостей минимальны и воспроизводимы по lock-файлам. CI сохраняет проверку advisories. Production-инвентарь хранится в обезличенном виде.
- Проверки включают `composer validate --strict`, `composer check-platform-reqs`, `composer audit --locked --no-dev --no-interaction`, npm audit, штатные PHP и frontend quality gates и проверку запуска в изменённом окружении.

## Constitution check

До и после проектирования границы Application, Domain, Bridge и Infrastructure сохраняются. Новый сценарий API или изменение публичного контракта не запланированы. Для обнаруженного риска импорта сетевой ввод ограничивается на границе Infrastructure с регрессиями на заглушках. Если исправление меняет поддерживаемые источники или контракт, сначала согласуется поведение. Изменений схемы и запросов данных обновление стека не требует. Перед завершением проверяются штатные гейты, запуск и отсутствие новых N+1.

## Последовательность работ

1. Записать baseline зависимостей и репозитория, обновить Laravel и PHP. Сверить итоговый аудит и совместимость.
2. Параллельно с локальными работами получить инвентарь Lightsail. Закрыть критические CVE на фактическом текущем хосте, если затронут. При необходимости отдельно подготовить миграцию на Ubuntu 24.04.
3. Провести аудит и задокументировать доказательства, устранить подтверждённые High/Critical, выполнить повторную проверку.
4. После разрешения на рабочие изменения применить выкат и подтвердить хостовые результаты. Проверить сценарии использования. Закрыть задачи только при наличии доказательств.

## Приёмка и зависимости

[Контракт](contracts/security-verification.md) определяет доказательства для каждой среды. [Quickstart](quickstart.md) описывает проверки. Production-инвентарь, окно, подтверждённый способ восстановления и доступ к управлению экземпляром нужны для серверной части. Они не блокируют обновления и проверки репозитория.
