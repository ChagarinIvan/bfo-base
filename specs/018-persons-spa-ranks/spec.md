# Feature Specification: SPA Person Rank History

**Feature Branch**: `018-persons-spa-ranks`

**Created**: 2026-09-06

**Status**: Draft

**Input**: Перенести страницу разрядов персоны на SPA как вкладку View Person. Сохранить просмотр истории и авторизованное активирование разряда, получать историю отдельным запросом без пагинации, группировать по разряду и показывать обратную хронологию внутри раскрытой группы, а связанные события и соревнования получать отдельным запросом по ID. Использовать API каталога возможных разрядов с кэшем на один час. Удалить старые Blade-шаблоны, web-роуты и неиспользуемый legacy-код страницы.

## User Scenarios & Testing

### User Story 1 - Просмотр истории разрядов во вкладке персоны (Priority: P1)

Пользователь открывает вкладку «Разряды» в карточке активной персоны и видит историю её разрядов, не покидая общий SPA-модуль Person Info.

**Why this priority**: История разрядов — основной пользовательский результат этой миграции и должна заменить существующую Blade-страницу без потери данных.

**Independent Test**: Открыть `/app/persons/{personId}/ranks` для персоны с историей и без неё; проверить общий Person Info, свёрнутые группы разрядов, обратную хронологию внутри группы, локализованные типы выполнений, ссылки на соревнования и состояния loading/empty/not-found/error.

**Acceptance Scenarios**:

1. **Given** существует активная персона с историей разрядов, **When** пользователь открывает вкладку «Разряды», **Then** общий Person Info остаётся сверху, вкладка подсвечена, а история показана свёрнутыми периодами разрядов; свёрнутая строка показывает границы периода, а раскрытая группа — записи от новых достижений к старым с датой выполнения и типом. Выполнение более низкого разряда всегда показывается в группе этого разряда; отложенный период низшего разряда остаётся отдельной группой.
2. **Given** пользователь переключается между соревнованиями, разрядами, оплатами и промптами, **When** меняется вложенный раздел, **Then** Person Info и кнопки вкладок остаются смонтированными, а данные персоны не загружаются повторно.
3. **Given** у персоны нет истории разрядов, **When** загрузка завершена, **Then** отображается понятное empty state вместо пустой таблицы.
4. **Given** идентификатор персоны неизвестен или персона неактивна, **When** открыта вкладка разрядов, **Then** API не возвращает чужие данные, а SPA показывает not-found или пустое состояние согласно политике списка.
5. **Given** строка истории связана с соревнованием и событием, **When** пользователь нажимает ссылку, **Then** он переходит к соответствующему соревнованию или старту с правильным идентификатором строки протокола.

### User Story 2 - Активация и изменение даты активации (Priority: P1)

Авторизованный пользователь активирует разряд или изменяет/снимает дату активации непосредственно из строки истории.

**Why this priority**: Активация — существующая бизнес-функция, которую нельзя потерять при удалении форм и роутов Blade.

**Independent Test**: Через защищённый JSON API активировать неактивный protocol line, изменить дату активированного line и передать пустую дату; проверить доменное событие, protocol line и person rank history.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован и строка ещё не активирована, **When** он вводит корректную дату и подтверждает активацию, **Then** дата сохраняется в protocol line и истории, а строка становится активированной.
2. **Given** пользователь авторизован и строка уже активирована, **When** он сохраняет новую дату, **Then** существующая дата активации заменяется в protocol line и истории.
3. **Given** пользователь авторизован и редактирует активацию, **When** он очищает дату, **Then** активация снимается и история отражает отсутствие даты.
4. **Given** пользователь не авторизован, **When** он просматривает историю, **Then** он видит только чтение и не видит действий активации/изменения.
5. **Given** protocol line не существует, **When** отправлена mutation-команда, **Then** API возвращает стандартный not-found ответ без изменения данных.

### User Story 3 - Каталог возможных разрядов (Priority: P2)

SPA получает список возможных разрядов для подписей в таймлайне из общего каталога и повторно использует результат в течение часа на клиенте.

**Why this priority**: Каталог нужен для локализованных подписей разрядов, но не должен добавлять лишние запросы при навигации по страницам.

**Independent Test**: Запросить каталог без авторизации, проверить полный список в порядке доменного перечисления, повторный запрос в течение часа и истечение кэша.

**Acceptance Scenarios**:

1. **Given** каталог разрядов доступен, **When** SPA запрашивает его, **Then** API возвращает идентификатор и локализованное название каждого возможного разряда.
2. **Given** каталог уже запрошен в течение часа, **When** выполняется повторный запрос, **Then** ответ берётся из кэша и не пересчитывает каталог.
3. **Given** кэш каталога истёк, **When** приходит новый запрос, **Then** каталог строится заново и снова кэшируется на час.

## Edge Cases

- Неизвестный или неактивный `personId` не должен возвращать историю другой персоны.
- Дата активации принимает только дату в согласованном API-формате; для снятия активации разрешено явно передать `null` или пустое значение только в update-сценарии.
- Активация требует дату; запрос без даты или с некорректной датой отклоняется до изменения данных.
- Одновременные изменения одной строки сериализуются существующим lock/transaction-потоком.
- Ошибка API, отсутствие сети, validation error и empty state отображаются раздельно.
- Для анонимного пользователя строки created/updated и mutation-действия не отображаются, если контракт их предоставляет только в authenticated group.

## Requirements

### Functional Requirements

- **FR-001**: Система MUST предоставлять вложенный SPA-маршрут `/app/persons/{personId}/ranks` внутри общего Person Info layout.
- **FR-002**: Навигация MUST показывать разряды как вкладку View Person; при переходе между вкладками Person Info и кнопки навигации MUST оставаться смонтированными.
- **FR-003**: API MUST предоставлять публичный запрос `/persons/{personId}/rank-histories`, возвращающий всю историю активной персоны без пагинации; неизвестная или неактивная персона возвращает пустой список.
- **FR-004**: Запись истории MUST содержать только собственные поля `id`, идентификаторы персоны/protocol line/дистанции/события/соревнования, `rankId`, тип изменения и даты достижения/активации/начала/окончания.
- **FR-005**: SPA MUST получать названия событий и соревнований отдельным запросом `/events?withCompetition=1&ids[]=...`; API событий MUST поддерживать выборку по массиву ID.
- **FR-006**: API MUST возвращать историю в детерминированном порядке `achievedOn DESC, id DESC`, а SPA MUST отображать свёрнутые периоды разрядов в обратной хронологии. Каждый элемент MUST принадлежать группе собственного разряда, сохраняя существующий локализованный тип; отложенный период низшего разряда MUST оставаться отдельной группой. Для авторизованного пользователя отображается действие активации либо изменения даты.
- **FR-007**: API активации MUST требовать авторизацию и дату; API изменения MUST требовать авторизацию, принимать новую дату или пустое значение для снятия активации.
- **FR-008**: Мутации MUST сохранять существующую доменную семантику, lock/transaction-поведение, domain events и обновление protocol line/person rank history.
- **FR-009**: SPA MUST показывать loading, error, not-found и empty состояния, защищать загрузку истории от устаревших ответов и скрывать mutation-действия от анонимных пользователей.
- **FR-010**: API каталога разрядов MUST быть публичным и возвращать все возможные разряды в доменном порядке; SPA MUST кэшировать результат на один час.
- **FR-011**: Старые Blade-шаблоны страницы истории разрядов и форм активации, их web-роуты и контроллеры MUST быть удалены после переноса поведения в SPA/JSON API; фоновые расчёты разрядов и доменная история MUST сохраниться.
- **FR-012**: Изменения поведения MUST быть покрыты application/unit, API/integration и SPA-тестами без новых deprecation/notices.

### Key Entities

- **Person Rank History**: факт получения/изменения разряда персона с датами достижения, активации, начала и окончания действия.
- **Protocol Line**: результат спортсмена, через который выполняется и активируется разряд.
- **Rank**: возможный доменный разряд с числовым идентификатором и локализованным названием.
- **Person**: активная персона, являющаяся контекстом истории и общего SPA layout.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Пользователь открывает историю разрядов как вкладку View Person без перехода на старую Blade-страницу.
- **SC-002**: Группы разрядов упорядочены по последней записи, а записи в раскрытой группе содержат разряд, тип выполнения и период действия в обратной хронологии.
- **SC-003**: Авторизованный пользователь может выполнить активацию, изменить дату и снять активацию без потери существующего доменного поведения; каждый сценарий подтверждён API-тестом.
- **SC-004**: Загрузка истории не выполняет запросы к связанным сущностям на каждую строку; названия событий и соревнований получаются одним пакетным запросом по ID.
- **SC-005**: Повторный запрос каталога в течение одного часа не обращается к API благодаря клиентскому кэшу.
- **SC-006**: Все acceptance scenarios покрыты автоматизированными backend и SPA тестами, а полный quality gate проходит без новых notices/deprecations.

## Assumptions

- Каталог возможных разрядов продолжает использовать существующее доменное перечисление `Rank`; отдельная таблица справочника не создаётся.
- История разрядов доступна для чтения без авторизации, как старая страница, а операции активации доступны только авторизованным пользователям.
- Вкладка разрядов использует существующий общий `PersonPromptPersonInfo` и `PersonInfoNavigation`, без второго Person Info-компонента.
- Существующие application services активации переиспользуются через новые JSON API actions; если transport DTO или endpoint требует адаптации, доменная семантика не меняется.

## Out of Scope

- Перерасчёт правил квалификации, импорт результатов и изменение RankCalculator.
- Изменение формата или бизнес-правил Person Rank History.
- Перенос административных legacy-инструментов перерасчёта разрядов, не связанных с просмотром и активацией строки.
