# Research: SPA Person Rank History

## Decisions

1. View Person остаётся компактным. История запрашивается отдельным публичным list endpoint по активному personId и возвращается целиком без пагинации.
2. DTO истории содержит только поля persisted-объекта и не обращается к event/competition relations. SPA получает уникальные event IDs и одним batch-запросом `/events?withCompetition=1&ids[]=...` получает отображаемые названия.
3. SPA получает всю историю одним запросом без фильтров и без пагинации. API сортирует её от нового достижения к старому; SPA группирует факты по разряду, а раскрытая группа сохраняет эту обратную хронологию.
4. Активация и изменение даты продолжают использовать существующие Application services и отдельные защищённые JSON actions.
5. Каталог GET /api/v1/ranks остаётся публичным без серверного кэша; SPA кэширует ответ на час.
6. Ранги остаются вложенной вкладкой существующего Person Info layout; старые Blade entry points удаляются.

Отдельный list service нужен как граница API истории, но он использует существующий PersonRepository и `PersonResources`, без нового repository и без пагинации.
