# Спецификация фичи: единые SPA-таблицы и навигация результатов

**Ветка фичи**: `024-unify-spa-tables`  
**Создано**: 2026-09-13  
**Статус**: Draft

## Контекст и границы

SPA-листинги используют сходные, но разрозненные таблицы и панели фильтров. Пользователь
должен получать одинаковый способ выбрать столбцы и пользоваться фильтрами, не теряя
настройки после возвращения на страницу. Одновременно ссылки на этапы, привязанные к
результату спортсмена, должны открывать нужную строку протокола из каждого контекста,
а в истории разрядов должна быть доступна ручная актуализация данных спортсмена.

В область входят все SPA-листинги результатов и сущностей, использующие табличное
представление. Карточки «ключ–значение» и timeline истории разрядов не являются
листингами и не переводятся в таблицы. Изменение не заменяет старые cup-страницы на SPA;
оно исправляет их ссылки, когда у ссылки известна строка протокола.

## Пользовательские сценарии и тестирование

### История 1 — настроить состав столбцов (приоритет: P1)

Посетитель выбирает только нужные столбцы в любом табличном листинге и при следующем
посещении видит тот же состав.

**Почему P1**: это базовая ценность единого табличного интерфейса и снижает перегруженность
больших списков.

**Независимая проверка**: component-тесты проверяют рендер выбора, запрет отключить
последний столбец, раздельные наборы доступных столбцов и восстановление настройки для
одного ключа таблицы.

**Сценарии приёмки**:

1. **Дано** открыт табличный листинг, **когда** посетитель открывает блок настройки,
   **тогда** перед фильтрами показан горизонтальный набор переключателей доступных столбцов.
2. **Дано** выбраны несколько столбцов, **когда** посетитель выключает один из них и
   возвращается на страницу, **тогда** отключённый столбец не показан и выбор восстановлен.
3. **Дано** открыт список анонимным или аутентифицированным посетителем, **когда**
   показывается настройка столбцов, **тогда** доступны только столбцы, разрешённые для
   текущего состояния доступа.
4. **Дано** включён единственный столбец, **когда** посетитель пытается выключить его,
   **тогда** интерфейс сохраняет как минимум один видимый столбец.
5. **Дано** два разных листинга, **когда** посетитель меняет состав столбцов в одном,
   **тогда** настройка второго листинга не меняется.

### История 2 — использовать фильтры во время просмотра длинного списка (приоритет: P1)

Посетитель прокручивает длинный список и продолжает менять его фильтры без возврата к
началу страницы.

**Почему P1**: фильтры остаются рабочим инструментом при просмотре результатов и списков.

**Независимая проверка**: component-тесты проверяют, что листинг с фильтрами использует
единый layout, а CSS-контракт закрепляет прилипающую панель; тест перехода по якорю
подтверждает совместимость sticky-фильтра и прокрутки к строке результата.

**Сценарии приёмки**:

1. **Дано** листинг имеет фильтры, **когда** пользователь прокручивает страницу ниже
   панели, **тогда** панель остаётся у верхней границы окна, а строки продолжают
   прокручиваться под ней.
2. **Дано** листинг не имеет фильтров, **когда** он отображается, **тогда** общий шаблон
   не создаёт пустой блок фильтров.
3. **Дано** открыта ссылка на строку протокола, **когда** загрузка завершена,
   **тогда** нужная строка видима и не скрыта прилипающей панелью.

### История 3 — открыть этап на нужном результате (приоритет: P1)

Пользователь переходит к этапу из страницы спортсмена, истории разрядов или старых
cup-представлений и попадает на связанный результат.

**Почему P1**: без привязки к строке переход на большой этап теряет контекст спортсмена.

**Независимая проверка**: unit/component-тесты URL-builder-а и существующего event view
подтверждают канонический якорь для всех ссылок, имеющих строку протокола.

**Сценарии приёмки**:

1. **Дано** ссылка из участия спортсмена, **когда** пользователь открывает этап,
   **тогда** адрес содержит идентификатор строки протокола и строка подсвечивается/видна.
2. **Дано** ссылка из истории разрядов или cup-результата, **когда** пользователь открывает
   этап, **тогда** адрес использует тот же формат якоря и открывается связанная строка.
3. **Дано** у ссылки нет строки протокола, **когда** пользователь открывает этап,
   **тогда** открывается сам этап без фиктивного якоря.

### История 4 — вручную пересчитать разряды спортсмена (приоритет: P2)

Аутентифицированный пользователь из вкладки «История разрядов» запускает пересчёт
разрядов текущего спортсмена и видит актуальную историю.

**Почему P2**: действие заменяет прежнюю возможность из legacy-интерфейса и сокращает
время ожидания исправления данных.

**Независимая проверка**: API request-тест проверяет auth, передачу текущего спортсмена и
запуск существующего сценария пересчёта; SPA-тест проверяет кнопку, состояние ожидания,
успех и повторную загрузку истории.

**Сценарии приёмки**:

1. **Дано** аутентифицированный пользователь открыл историю разрядов, **когда** он
   нажимает «Перерасчёт», **тогда** запускается пересчёт только текущего спортсмена.
2. **Дано** пересчёт завершён, **когда** ответ получен, **тогда** история и отображаемый
   текущий разряд обновляются без ручной перезагрузки страницы.
3. **Дано** пользователь не аутентифицирован, **когда** он открывает историю разрядов,
   **тогда** кнопка не показана, а вызов операции отклонён стандартной защитой доступа.
4. **Дано** пересчёт выполняется или завершается ошибкой, **когда** пользователь пытается
   повторить действие, **тогда** повторная отправка предотвращена либо показана понятная ошибка.

### Граничные случаи

- Некорректная или устаревшая настройка столбцов не ломает таблицу: используются допустимые
  значения по умолчанию.
- Настройки одного листинга не применяются к другому, включая тот же листинг в ином
  состоянии авторизации.
- Изменение статуса авторизации не открывает анонимному посетителю служебные столбцы из
  сохранённой настройки.
- Указанная в ссылке строка находится на другой дистанции этапа: переход сохраняет
  информацию, необходимую для загрузки правильной дистанции.
- Ошибка пересчёта не стирает уже загруженную историю разрядов.

## Требования

### Функциональные требования

- **FR-001**: Система ДОЛЖНА использовать единый табличный шаблон для каждого SPA-листинга.
- **FR-002**: Табличный шаблон ДОЛЖЕН показывать перед фильтрами отдельный блок выбора
  видимых столбцов, если листинг передал доступные столбцы.
- **FR-003**: Посетитель ДОЛЖЕН иметь возможность включать и выключать доступные столбцы,
  при этом видимым остаётся как минимум один столбец.
- **FR-004**: Система ДОЛЖНА сохранять состав видимых столбцов локально отдельно для
  каждого листинга и восстанавливать его при новом посещении.
- **FR-005**: Доступный набор столбцов ДОЛЖЕН зависеть от текущего состояния авторизации;
  скрытые для анонимного посетителя столбцы не могут появиться из сохранённого выбора.
- **FR-006**: Табличный шаблон ДОЛЖЕН принимать фильтры как необязательный блок; при его
  наличии панель фильтров ДОЛЖНА оставаться доступной при вертикальной прокрутке.
- **FR-007**: Переход по якорю на строку результата ДОЛЖЕН работать вместе с прилипающей
  панелью фильтров.
- **FR-008**: Все ссылки на этап, у которых доступна строка протокола, ДОЛЖНЫ использовать
  единый канонический якорь результата; ссылки без строки протокола сохраняют обычный адрес этапа.
- **FR-009**: Аутентифицированный пользователь ДОЛЖЕН видеть во вкладке истории разрядов
  кнопку ручного пересчёта с иконкой и защищённым состоянием выполнения.
- **FR-010**: Операция ручного пересчёта ДОЛЖНА пересчитывать только выбранного спортсмена
  через существующие правила расчёта и после успеха обновлять данные страницы.
- **FR-011**: API ручного пересчёта ДОЛЖЕН требовать аутентификацию и возвращать стандартный
  успешный ответ либо стандартную ошибку доступа/неизвестного спортсмена.
- **FR-012**: Все новые пользовательские тексты ДОЛЖНЫ быть локализованы.

### Ключевые сущности

- **Конфигурация таблицы**: сохранённый набор ключей видимых столбцов для конкретного
  листинга и состояния доступа.
- **Описание столбца**: стабильный ключ, локализуемая подпись и правило доступности.
- **Якорь результата**: идентификатор строки протокола в адресе этапа.
- **Ручной пересчёт разрядов**: запрос аутентифицированного пользователя пересчитать
  производные разрядные данные одной персоны.

## Критерии успеха

- **SC-001**: каждый SPA-листинг на момент поставки использует общий табличный шаблон.
- **SC-002**: автоматические тесты подтверждают независимое восстановление настройки
  минимум для двух листингов и сохранение хотя бы одного видимого столбца.
- **SC-003**: автоматические тесты подтверждают канонический якорь для участия,
  истории разрядов и cup-результата.
- **SC-004**: автоматические API и SPA-тесты подтверждают успешный пересчёт одного
  спортсмена и запрет неаутентифицированного вызова.
- **SC-005**: фильтры всех затронутых листингов используют один CSS-контракт sticky-панели
  без создания дополнительной сетевой загрузки строк.

## Допущения

- Настройки видимых столбцов являются локальными предпочтениями браузера, не синхронизируются
  между устройствами и не требуют серверного хранения.
- Общим табличным шаблоном считаются SPA-листинги на табличном компоненте; таблицы свойств
  карточек и интерактивная история разрядов остаются специализированными представлениями.
- Ручной пересчёт выполняется синхронно существующим use case, как и другие точечные операции
  изменения разрядов.
