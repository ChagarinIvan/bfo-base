# Feature Specification: Асинхронная проверка разрядов по списку

**Feature Branch**: `026-rank-list-check`

**Created**: 2026-09-16

**Status**: Implemented

**Input**: User description: "Вернуть административную проверку разрядов по стандартизированному CSV-списку спортсменов. Добавить кнопку в навигацию и форму загрузки, заменить долгий синхронный запрос асинхронной обработкой с pending-состоянием и обновлением результата через API. Использовать сохранившийся список-парсер; рассмотреть сущность RankCheck/ProtocolParsing со статусами PARSING, READY и FAILED."

## Контекст и границы

Ранее администратор мог открыть страницу проверки разрядов, загрузить CSV-список и получить сравнительную таблицу в одном HTTP-запросе. Запрос включал разбор файла, поиск спортсменов в базе и получение их актуальных разрядов, поэтому на больших списках завершался по таймауту.

Фича возвращает этот административный инструмент как отдельный асинхронный запуск проверки. Сохранившийся парсер стандартизированного списка остаётся источником входных строк. Результат показывает администратору расхождения между файлом и базой, но сама проверка не изменяет спортсменов, клубы, группы или разрядную историю.

### Исторический baseline

В прежнем сервисе обработка выполнялась последовательно: список разбирался через `parserRankList`,
для каждой строки строилась идентификационная строка из ФИО и года, затем выполнялся поиск
спортсмена, загрузка найденных спортсменов и получение их актуальных разрядов через
`getActualRanks`. Новый фоновый запуск должен сохранить эту бизнес-последовательность, изменив
только способ выполнения и представления результата.

Ожидаемый входной файл имеет разделитель `;` и первую строку-заголовок. Базовый вариант содержит
шесть полей:

```text
group;name;club;rank;number;year
М21;Иванов Иван;СК Олимп;I;42;1990
Ж18;Петрова Анна;Динамо;IIю;7;2008
```

Поддерживается также вариант из пяти полей без стартового номера:

```text
group;name;club;rank;year
М21;Иванов Иван;СК Олимп;I;1990
```

Заголовок не становится строкой результата. Пустые строки и строки, где имя равно «Вакансия»,
не попадают в результат. Для каждой принятой строки сохраняется исходный порядок и исходные
значения `group`, `name`, `club`, `rank`, `number` (если передан) и `year`.

Исторический экран показывал таблицу из семи колонок: «Группа», «ФИО», «Клуб», «Разряд»,
«Год рождения», «Совпадает» и «Есть в базе». Если спортсмен найден, совпадающие значения
выделялись, а отличающиеся показывались парой «значение из файла → значение из базы». В колонке
«Совпадает» отображалось положительное состояние только когда совпадали ФИО, клуб, год и разряд;
в колонке «Есть в базе» — когда спортсмен был найден. Если спортсмен не найден, показывались
только исходные значения файла. Новый экран обязан сохранить эту информацию, но может сделать
состояния и фильтрацию более явными.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Запустить проверку списка (Priority: P1)

Администратор открывает пункт «Проверка разрядов» в навигации, видит историю запусков и через кнопку «Добавить проверку» выбирает стандартизированный CSV-файл.

**Why this priority**: Без запуска проверки администратор не может заранее обнаружить устаревшие данные спортсменов.

**Independent Test**: Авторизованный администратор открывает пункт навигации, загружает корректный CSV и получает созданную проверку с идентификатором и статусом обработки.

**Acceptance Scenarios**:

1. **Given** администратор находится в приложении, **When** он выбирает «Проверка разрядов», **Then** открывается белая страница со стандартным paginated-списком запусков без фильтров и зелёной кнопкой добавления.
2. **Given** администратор нажал кнопку добавления, **When** он отправляет корректный файл стандартизированного списка, **Then** система быстро подтверждает создание запуска и возвращает пользователя в список, где новый запуск имеет статус `PARSING`.
3. **Given** посетитель не имеет административного доступа, **When** он открывает форму или пытается создать проверку, **Then** доступ запрещён стандартной политикой авторизации.

### User Story 2 - Видеть ход и завершение обработки (Priority: P1)

Администратор понимает, что проверка ещё выполняется, и автоматически получает результат, когда она завершена.

**Why this priority**: Пользователь не должен принимать пустую или неполную таблицу за готовый результат и не должен вручную перезагружать страницу.

**Independent Test**: Создать проверку с задержанной обработкой, открыть её страницу и проверить отображение `PARSING`, периодическое обновление, затем переход в `READY` с результатами.

**Acceptance Scenarios**:

1. **Given** проверка имеет статус `PARSING`, **When** администратор открывает страницу результата, **Then** показываются понятное сообщение об обработке и индикатор ожидания, а итоговая таблица не представляется готовой.
2. **Given** страница открыта и статус остаётся `PARSING`, **When** проходит очередной интервал обновления, **Then** фронтенд запрашивает актуальное состояние через API.
3. **Given** фоновая обработка завершилась успешно, **When** API возвращает `READY`, **Then** форма ожидания исчезает, показывается полная таблица проверки, а дальнейшее автоматическое обновление прекращается.
4. **Given** администратор ушёл со страницы до завершения, **When** компонент страницы размонтирован, **Then** последующие автоматические запросы этой страницы не выполняются.

### User Story 3 - Разобрать расхождения с базой (Priority: P1)

Администратор просматривает каждую строку списка и видит исходные значения, найденного спортсмена и его значения в базе, чтобы исправить данные до соревнования.

**Why this priority**: Ценность инструмента — не только в факте запуска, а в понятном сравнении списка с актуальной базой.

**Independent Test**: Для файла с совпадающими, отличающимися и отсутствующими спортсменами проверить все типы строк в готовой таблице.

**Acceptance Scenarios**:

1. **Given** строка файла соответствует найденному спортсмену по идентификационным данным, **When** результат готов, **Then** таблица показывает исходные группу, ФИО, клуб, разряд и год, значения найденного спортсмена и признак наличия в базе.
2. **Given** спортсмен найден, но одно или несколько значений отличаются, **When** администратор просматривает строку, **Then** отображается явный признак расхождения и видны оба значения.
3. **Given** спортсмен не найден в базе, **When** результат готов, **Then** строка сохраняется в таблице с исходными данными и признаком «нет в базе», без выдуманных данных спортсмена.
4. **Given** файл содержит строки с одинаковыми идентификационными данными, **When** результат готов, **Then** каждая входная строка отображается отдельно и не теряется из-за группировки.
5. **Given** найденный спортсмен имеет актуальный разряд, **When** значение разряда в файле совпадает с базой, **Then** строка помечается как совпадающая, а значение разряда может вести в историю разрядов спортсмена.
6. **Given** найденный спортсмен не имеет актуального разряда, **When** в файле указан вариант без разряда, **Then** разряд считается совпадающим; если в файле указан разряд, отображается расхождение с отсутствующим значением базы.
7. **Given** найденный спортсмен имеет отличия в ФИО, клубе, годе или разряде, **When** администратор смотрит таблицу, **Then** общий признак «Совпадает» отрицательный даже если остальные поля совпали.

### User Story 4 - Понять ошибку обработки (Priority: P2)

Администратор получает конечное объяснение, если файл нельзя разобрать или проверка завершилась ошибкой, вместо бесконечного ожидания.

**Why this priority**: Ошибка должна быть диагностируема и не должна маскироваться статусом pending.

**Independent Test**: Передать неподдерживаемый или повреждённый файл, дождаться `FAILED` и проверить остановку обновлений и сообщение об ошибке.

**Acceptance Scenarios**:

1. **Given** обработка завершилась ошибкой, **When** API возвращает `FAILED`, **Then** страница показывает понятное локализованное сообщение, прекращает polling и не показывает неполный результат как готовый.
2. **Given** временный запрос статуса завершился сетевой ошибкой, **When** запуск всё ещё имеет статус `PARSING`, **Then** пользователь видит предупреждение, а следующая попытка выполняется по обычному интервалу.

### Edge Cases

- Отправлен пустой файл, файл с неподдерживаемым расширением или файл с некорректной структурой: запуск завершается `FAILED` с безопасным сообщением без технического стектрейса.
- Входной файл содержит поддерживаемый заголовок как с номером, так и без номера спортсмена; обе формы обрабатываются согласно контракту существующего парсера.
- В файле есть пустые строки или строки вакансий: они не создают ложные результаты.
- В списке отсутствует клуб, год рождения или разряд: исходное пустое значение сохраняется и сравнивается с соответствующим отсутствующим значением базы.
- Пользователь дважды отправляет одну форму: каждый принятый запуск имеет собственный ID и не смешивает результаты; повторная отправка не дублирует строки внутри одного запуска.
- После `READY` или `FAILED` результат доступен при повторном открытии страницы без повторной постановки в обработку.
- Сбой фоновой задачи после создания запуска переводит его в `FAILED`; статус не остаётся `PARSING` навсегда.
- Ошибка статуса не раскрывает содержимое файла или персональные данные постороннему пользователю.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА показывать авторизованному пользователю пункт «Проверка разрядов» в навигационной панели и вести его на paginated-список запусков без фильтров.
- **FR-002**: Форма ДОЛЖНА принимать стандартизированный список спортсменов в поддерживаемом формате и отклонять отсутствующий, пустой или неподдерживаемый файл до запуска обработки.
- **FR-003**: После принятия файла система ДОЛЖНА создать отдельный запуск `RankCheck` с уникальным идентификатором и статусом `PARSING`, вернуть его идентификатор без ожидания полного результата и поставить обработку в фоновый исполнитель.
- **FR-004**: Запуск `RankCheck` ДОЛЖЕН иметь ровно три пользовательских статуса: `PARSING`, `READY` и `FAILED`; переход из `PARSING` в `READY` или `FAILED` фиксируется один раз.
- **FR-005**: Фоновая обработка ДОЛЖНА использовать существующий парсер списка и сохранять его правила: пропуск заголовка, пустых строк и строк «Вакансия», поддержку шести полей с `number` и пяти полей без `number`, а также исходный порядок принятых строк.
- **FR-006**: Для каждой принятой строки фоновая обработка ДОЛЖНА построить идентификационные данные из ФИО и года, найти соответствующего спортсмена существующими правилами идентификации и получить его актуальный разряд, не изменяя доменные данные спортсменов.
- **FR-007**: Успешный запуск ДОЛЖЕН сохранять полный результат проверки, включая исходные поля `group`, `name`, `club`, `rank`, `number` и `year`, найденного спортсмена (если он есть), значения базы, признаки наличия и совпадения по ФИО, клубу, году и разряду.
- **FR-008**: `RankCheck` ДОЛЖЕН хранить `updated` Impression с временем изменения; значение ДОЛЖНО изменяться при создании запуска и каждом подтверждённом изменении его статуса или результата.
- **FR-009**: Система ДОЛЖНА предоставлять защищённые paginated API списка запусков без фильтров, создания запуска, просмотра запуска по его идентификатору и отдельный paginated API строк; DTO списка и просмотра возвращает как минимум `id`, `status`, `created`/`updated` и безопасную ошибку, а строки загружаются отдельным запросом только для `READY`.
- **FR-010**: В текущей модели доступа любой аутентифицированный API-пользователь считается администратором инструмента; гость получает `401`, а отдельная RBAC-модель для этой фичи не вводится.
- **FR-011**: Страница проверки ДОЛЖНА показывать `PARSING` как pending-состояние и автоматически запрашивать API просмотра с интервалом не более 5 секунд, пока статус переходный.
- **FR-012**: При статусе `READY` API и страница ДОЛЖНЫ предоставлять серверно пагинируемый результат по сохранённым `RankCheckRow` с понятными признаками «совпадает», «отличается» и «нет в базе», сохраняя исторический набор семи основных колонок.
- **FR-012a**: API строк ДОЛЖЕН фильтровать строки по статусу `READY` на уровне repository criteria; для `PARSING` и `FAILED` неполные строки не возвращаются.
- **FR-013**: В готовой строке ДОЛЖНЫ быть отдельно доступны исходные значения файла и значения найденного спортсмена из базы; при отличии интерфейс ДОЛЖЕН визуально показать оба значения, а при отсутствии спортсмена — только исходные значения.
- **FR-014**: При статусе `FAILED` страница ДОЛЖНА показать локализованное сообщение об ошибке, не выдавать неполный результат и прекратить автоматические запросы.
- **FR-015**: Автоматические запросы ДОЛЖНЫ прекращаться при `READY`, `FAILED`, уходе со страницы и смене запуска; временная ошибка отдельного запроса не должна сама переводить запуск в `FAILED`.
- **FR-016**: Повторное открытие существующего запуска ДОЛЖНО восстанавливать его сохранённый статус и результат, не запускать обработку повторно и не создавать дубликаты строк.
- **FR-017**: Все новые подписи, статусы, ошибки и инструкции ДОЛЖНЫ быть локализованы.
- **FR-018**: Необработанная ошибка фоновой обработки, которая приводит к HTTP/worker failure, ДОЛЖНА передаваться стандартному exception handler и Sentry с привязкой к запуску без записи содержимого файла и персональных данных в пользовательский лог. Ожидаемые ошибки проверки переводятся в `FAILED` с безопасным сообщением.
- **FR-019**: Жизненный цикл `RankCheck` ДОЛЖЕН быть спроектирован так, чтобы общий механизм статусов и просмотра можно было повторно использовать для будущих асинхронных импортов, включая обработку протоколов, без смешивания результатов разных типов запуска.
- **FR-020**: Ежедневная плановая очистка ДОЛЖНА удалять `RankCheck` и связанные `RankCheckRow`, созданные более 24 часов назад, вместе с исходными файлами. Это включает зависшие `PARSING`-запуски, которые старше retention и считаются неисправными.

### Key Entities

- **RankCheck**: отдельный запуск административной проверки; имеет идентификатор, владельца, статус `PARSING`/`READY`/`FAILED`, время создания и последнего обновления, безопасную ссылку на входной файл, сообщение об ошибке (только для администратора) и набор строк результата.
- **RankCheckRow**: сохранённая строка результата; содержит исходные значения группы, ФИО, клуба, разряда, стартового номера и года, ссылку на найденного спортсмена при наличии, значения ФИО/клуба/года/актуального разряда из базы и независимые признаки наличия/совпадения. Строка хранится отдельно для серверной пагинации и удаляется вместе с истёкшим запуском.
- **RankCheckStatus**: ограниченный набор состояний жизненного цикла запуска.
- **Стандартизированный список спортсменов**: входной файл, который разбирается существующим списковым парсером; строки вакансий и пустые строки не становятся результатами.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Администратор может начать проверку файла и получить экран ожидания с ID запуска не позднее чем через 2 секунды после отправки запроса, независимо от времени обработки файла.
- **SC-002**: Для каждого запуска 100% входных строк, не являющихся пустыми или вакансиями, находятся в готовом результате ровно один раз.
- **SC-003**: При штатной обработке администратор видит переход `PARSING` → `READY` или `FAILED` не позднее чем через 5 секунд после фиксации финального статуса, без ручной перезагрузки.
- **SC-004**: После финального статуса или ухода со страницы polling прекращается; для завершённого запуска не выполняются дополнительные автоматические запросы.
- **SC-005**: В результате администратор может однозначно отличить совпадающие строки, расхождения и спортсменов, отсутствующих в базе; это подтверждается тестами для всех трёх случаев.
- **SC-006**: Обработка файла, которая раньше выполнялась в одном долгом запросе, не удерживает HTTP-запрос до завершения и не приводит к таймауту из-за длительности проверки.
- **SC-007**: Неавторизованный пользователь не получает форму, статус, входной файл или результат проверки и получает стандартный `401`.
- **SC-008**: Серверная пагинация позволяет открыть любую страницу результата без загрузки всех строк запуска в один ответ.
- **SC-009**: Ежедневная очистка удаляет запуски, строки и исходные файлы старше 24 часов; зависшие `PARSING`-запуски старше retention считаются неисправными и также удаляются.

## Assumptions

- Администратор в рамках этой фичи — любой аутентифицированный API-пользователь; отдельная RBAC-модель и делегирование права не входят в scope.
- Поддерживаемый входной формат — текущий формат `createListParser`, первоначально CSV; изменение правил стандартизированного списка и создание новых parser-ов не входят в фичу.
- Проверка является read-only аудитом: найденные расхождения исправляются администратором отдельными существующими инструментами.
- Результат нужен для просмотра в приложении; экспорт отдельного отчёта и уведомления по email не входят в первую версию.
- Retention запусков составляет 24 часа; ежедневная cron-задача очищает истёкшие `RankCheck`, их `RankCheckRow` и исходные файлы. Старый `PARSING`-запуск считается зависшим и удаляется.
- Polling с интервалом до 5 секунд является достаточным способом доставки финального состояния; push-уведомления не требуются.
- Для нового механизма применяются целевые слои Application / Domain / Bridge / Infrastructure, а существующие parser-ы и правила идентификации используются через адаптеры без расширения legacy-слоя.

## Реализованный flow

`CreateRankCheckAction` принимает стандартный file DTO и вызывает `CreateRankCheckService`.
Сервис сохраняет файл, создаёт `RankCheck` через доменную фабрику и добавляет его в repository;
`RankCheckCreated` затем запускает queued handler, поэтому HTTP-запрос не ждёт парсинг. `ProcessRankCheckService`
блокирует aggregate в transaction и вызывает `RankCheck::process()`. Доменный processor оборачивает
ошибки в `ProcessError`, а aggregate переводит запуск в `READY` или `FAILED` и обновляет Impression.

Строки создаются через `RankCheckRowFactory`, сохраняются как `RankCheckRow` и читаются отдельным
`GET /rank-checks/{rankCheckId}/rows`, который возвращает стандартный `Slice` с pagination headers.
`GET /rank-checks/{rankCheckId}` возвращает только `ViewRankCheckDto` с обычными `created` и `updated`
через `AuthAssembler`; frontend polling выполняется только пока статус `PARSING`. Очистка удаляет
старые запуски через repository delete и исходный файл.

Для retention это осознанное правило: `PARSING` старше 24 часов считается зависшим. Отдельный
cleanup regression test отложен; текущий приоритет покрытия — API-контракты запуска, статуса и строк.
