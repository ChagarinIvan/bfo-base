# Feature specification: Шесть специализированных PR-ревьюеров

**Feature Branch**: `055-agent-pr-review`, создана по запросу пользователя
**Created**: 2026-11-08
**Status**: Implemented locally; live GitHub smoke pending credentials and rollout
**Input**: Автоматическое ревью PR шестью агентами: архитектура, EventDriven DDD,
security, качество тестов, frontend bugs, UI/UX и консистентность проекта.

## User scenarios & testing

### User story 1: Независимые проверки, P1

Автор PR получает специализированное ревью изменений с учётом правил BFO Base.
Приоритет объясняется необходимостью обнаруживать ошибки за пределами статических проверок.

Independent test: PR с подготовленными дефектами в каждой области получает
соответствующие замечания с доказательствами из кода.

1. Given PR открыт или обновлён, when начинается ревью, then шесть независимых
   ревьюеров проверяют один и тот же зафиксированный commit и diff относительно base.
2. Given область не затронута, when ревьюер завершает работу, then он явно сообщает
   «не применимо», не выдумывает замечаний и не ревьюит несвязанный legacy-долг.
3. Given применимые правила проекта, when агент обнаруживает нарушение, then
   замечание содержит файл, строки, приоритет, сценарий и последствия.

### User story 2: Отчёт в PR, P1

Автор видит общий результат без шести конкурирующих комментариев.
Приоритет объясняется необходимостью быстро оценить замечания и состояние проверки.

Independent test: собрать результаты всех ролей, затем обновить PR и проверить отчёт.

1. Given результаты шести ролей, when сборка завершена, then в PR есть один
   обновляемый отчёт с разделами ролей и указанием проверенного commit.
2. Given повторяющиеся замечания, when строится отчёт, then они объединяются
   с сохранением ролей-источников; различающиеся дефекты не теряются.
3. Given ошибка, таймаут или отсутствие ключа, when результат опубликован, then
   неполная проверка явно отличается от «замечаний нет».
4. Given новый commit во время старого ревью, when старый запуск завершается,
   then он не заменяет отчёт для более нового commit.

### User story 3: Управляемые правила и доступ, P2

Владелец репозитория изменяет инструкции ролей в репозитории и контролирует запуск.
Приоритет объясняется поддержкой правил и ограничением доступа автоматизации.

Independent test: проверить конфигурацию запуска, права ролей и инструкции подключения.

1. Given настроенные credentials и разрешённый PR, when запускается workflow,
   then агенты читают код, а публикация результата выполняется отдельно.
2. Given внешний PR без доверенного разрешения, when происходит событие,
   then содержимое PR не выполняется с доступом к секретам или правам записи.
3. Given инструкции изменены внутри проверяемого PR, when выполняется ревью,
   then PR не может сам ослабить доверенные правила текущей проверки.

### Edge cases

- Draft PR: автоматический запуск после ready-for-review; повторный запуск поддерживается.
- Большой diff: ограничение времени и явная отметка неполного покрытия вместо успеха.
- Удалённые и переименованные файлы, изменения только документации.
- Частичный отказ модели или публикации, отмена устаревшего запуска.
- Комментарии и файлы PR содержат инструкции для агента: это проверяемые данные.
- UI без скриншотов: ограничения визуальной проверки сообщаются явно.

## Requirements

### Functional requirements

- **FR-001**: Ревью MUST включать ровно шесть независимых ролей с отдельными
  редактируемыми инструкциями. Общие требования к доказательствам едины.
- **FR-002**: Architecture MUST проверять конституцию, направление зависимостей,
  Application/Domain/Bridge/Infrastructure, commands/DTO, repository ports,
  транзакции, after-commit и N+1. Переходный долг из манифеста не является образцом.
- **FR-003**: EventDriven DDD MUST отдельно проверять границы агрегатов и инварианты,
  намеренные domain methods, факт события и payload, аудит Impression,
  сохранение/публикацию, rollback, повторную доставку, идемпотентность и soft disable.
  Event sourcing и отдельный message broker не требуются сами по себе.
- **FR-004**: Security MUST проверять auth/authz, доступ к объектам, authenticated
  serialization groups, инъекции/XSS, загрузку файлов, секреты, зависимости и CI-права.
  Замечание об уязвимости MUST содержать конкретный путь и условия эксплуатации.
- **FR-005**: Tests MUST проверять полезность assertions, соответствие acceptance
  scenarios, регрессионное покрытие, детерминизм, изоляцию, хрупкость, моки и стиль.
  Application/Domain unit tests не создают Eloquent. Не требовать тесты ради покрытия строк.
- **FR-006**: Frontend bugs MUST проверять Vue/TypeScript, API-контракты, реактивность,
  гонки запросов, loading/error/empty состояния, маршруты, формы, auth и пагинацию.
- **FR-007**: UI/UX MUST сравнивать изменения с существующими общими компонентами,
  PrimeVue, таблицами/формами, темами и белорусской локализацией; проверять доступность,
  мобильные сценарии, иерархию действий и консистентность. Субъективный вкус без
  проектного основания не является дефектом. Проверка исходников не выдаётся за
  визуальную проверку в браузере.
- **FR-008**: Каждый finding MUST содержать роль, priority, путь и диапазон строк,
  описание дефекта, условия проявления и обоснование. Только новые или усугублённые
  изменения PR; разрешён просмотр окружающего кода и связанных контрактов.
- **FR-009**: Общий отчёт MUST содержать SHA, статусы всех ролей, ограничения и
  замечания без дублей; повторный запуск обновляет тот же отчёт данного PR.
- **FR-010**: Ревью MUST быть рекомендательным: найденные проблемы сами по себе
  не блокируют merge. Сбой автоматизации MUST быть видимым. Текущие CI-гейты сохраняются.
- **FR-011**: Ревьюеры MUST работать с минимальными правами чтения без изменения
  кода, commit/push или merge. Публикация отделена от анализа. Доверенные правила
  и orchestration не берутся из изменяемого PR; секреты не передаются коду PR.
- **FR-012**: Настройка MUST документировать необходимые credentials, разрешения,
  триггеры, модель, ограничения времени/расходов и ручную проверку первого запуска.
  Отсутствие credentials не представляется завершённым ревью.

### Key entities

- Review run: PR, base/head SHA, запуск и статус выполнения.
- Role report: роль, статус, findings, ограничения покрытия.
- Finding: приоритет, место, сценарий, последствия и роли-источники.
- PR report: объединённые findings и полнота проверки конкретного commit.

## Success criteria

- **SC-001**: Каждый разрешённый запуск учитывает все шесть ролей, включая явные
  статусы неприменимости и сбоя.
- **SC-002**: 100% публикуемых замечаний содержат место и проверяемое обоснование;
  одинаковые замечания не размножаются между ролями и повторными запусками.
- **SC-003**: Автор отличает завершённую проверку от частичной по одному отчёту;
  отчёт указывает проверенный commit и не перезаписывается устаревшим результатом.
- **SC-004**: Подготовленные проверки подтверждают объединение результатов,
  обработку отказов и ограничения запуска без платных вызовов модели.
- **SC-005**: Первый реальный запуск на GitHub подтверждает выполнение шести ролей
  и публикацию отчёта после подключения credentials.

## Assumptions

- Используем Codex в GitHub Actions, как обсуждено; отдельный внешний SaaS не нужен.
- Автоматическое ревью запускается для недрафтовых PR в master и при обновлении;
  внешний недоверенный PR не получает автоматического доступа к секретам.
- Роли могут использовать одну модель с разными инструкциями. Модель и лимиты
  определяются при планировании; обязательного выбора шести разных моделей нет.
- Начальный UI/UX reviewer анализирует исходники и проектные образцы. Автоматический
  запуск приложения, браузерные скриншоты и visual regression suite вне первого этапа.
- Анализ может читать контекст вне diff, но findings привязаны к изменению PR.
- Ветка сохраняется. Commit, push и подключение секретов не входят в создание
  артефактов и требуют отдельного действия; секреты не записываются в репозиторий.
- Существующий spec-kit review gate применяется до планирования и реализации.
