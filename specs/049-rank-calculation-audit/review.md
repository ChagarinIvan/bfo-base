# Пересмотр 049 по ревью PR #175

Источник: [общее ревью и комментарии](https://github.com/ChagarinIvan/bfo-base/pull/175#pullrequestreview-5639075665), 2026-10-24. Прочитан общий текст ревью и все 19 комментариев к коду.

## Основное решение

Person владеет журналом применений разряда, доступным как rankAudit. При успешном updateRanks добавляется действие с причиной, Impression и теми полями, которые присваиваются спортсмену: current_rank, current_rank_started_on, current_rank_activated_on, current_rank_finished_on, next_rank_activation_on. Применённое состояние сохраняется одним объектом. В коде его поля типизированы; JSON является форматом хранения.

У каждого сохранённого действия есть результат. Ошибок, nullable результата, RankRebuildFailure и recordFailure в этой модели нет. Повторный вызов updateRanks тоже фиксируется, даже если установлены те же значения. Это следует из общего комментария «добавлять ещё одну запись ... каждый раз» и заменяет прежнее требование о подавлении no-op.

Прежние RankSnapshot/RankHistorySnapshot, полные before/after и сравнение копий всей истории не нужны. Журнал объясняет цепочку установленных разрядов и дат; спортивные выполнения остаются в существующей истории. Отдельный repository аудита не собирает состояние спортсмена и не рассчитывает изменения.

Application управляет транзакцией и сохранением. Существующий расчёт и updateRanks остаются понятными; отдельный сервис не вводится только ради оборачивания ошибок или подготовки снимков. Новая связь Person с журналом следует принятой в проекте переходной модели агрегатов и обязательным правилам сохранения/событий. Конкретный механизм сохранения связи определяется при пересмотре плана.

## Предыдущее уточнение о ProtocolLine

Миграция заполняет created/updated старых строк из events через distances, затем делает поля обязательными. Новые строки используют Impression импорта. NullableImpressionCast удаляется, общий ImpressionCast остаётся прежним. Сведения события являются ретроспективным основанием, а не точной историей изменения протокольной строки.

## Выполнение цикла spec-kit

Уточнение выполнено без новых вопросов: решения уже даны в ревью и переписке. План, модель данных, контракт и quickstart пересмотрены. Старые задачи сохранены в tasks-history.md, новая последовательность T029–T046 находится в tasks.md. Анализ перед реализацией подтвердил покрытие 14/14 требований и отсутствие блокирующих архитектурных проблем.

Реализация использует чистый pending-список rankAudit у Person; historical list читается отдельно постранично. Это не eager relation на Infrastructure model. Каждое успешное updateRanks создаёт action; обычный save после сохранения не повторяет action и не теряет историю. Форма applied содержит только пять присваиваемых значений. Запись ошибок и снимки удалены.

Полный пересчёт использует существующий refill. Перестройка проекции/истории выполняется отдельно на каждого спортсмена в обычной транзакции; глобальной очистки перед запуском нет. Рабочие данные этим циклом не пересчитываются.

Дополнительно финальный набор обнаружил путь создания строк через replicate при объединении событий. Он теперь задаёт Impression нового события; регрессия добавлена в UniteEventsTest. Это выполнение FR-012, без расширения спортивных правил объединения.
