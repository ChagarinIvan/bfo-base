# План реализации: Единая нормализация названий клубов

**Ветка**: 008-club-name-normalization | **Дата**: 2026-09-01 | **Спецификация**: [spec.md](spec.md)

**Вход**: спецификация из specs/008-club-name-normalization/spec.md.

## Резюме

Убрать дублирующий NormalizedNameClubFinder и его интерфейс ClubFinder. Единственный
ClubNameNormalizer становится доменной политикой для создания, обновления, импорта и
сопоставления клубов. Семантический запрос по уже нормализованному имени остаётся
ответственностью существующего ClubRepository. Все точки использования Finder переходят
на normalizer и repository. Конвейер разбора протокола централизованно обрезает внешние
пробелы у поля club, а исторические записи продолжают сопоставляться через normalizer.

## Технический контекст

**Язык/версия**: PHP 8.5, Laravel 13.

**Основные зависимости**: Eloquent, Illuminate Collections, PHPUnit 13; существующий SymbolNormalizer.

**Хранение**: MySQL 8.4; изменяется только способ чтения существующего поля club и поиска по существующему normalize_name. Миграция не нужна.

**Тестирование**: PHPUnit: изолированные Domain/Application-тесты с моками репозитория; интеграционные тесты для Eloquent-поиска и конвейера разбора при необходимости.

**Целевая платформа**: веб-монолит Laravel, CLI-команды и фоновая синхронизация.

**Тип проекта**: серверное веб-приложение.

**Цели производительности**: не добавлять запросов при сопоставлении клуба; один семантический lookup остаётся одним запросом. Рендер legacy-протокола сохраняет существующую предварительную загрузку клубов без N+1.

**Ограничения**: не создавать сервисы или репозитории; не расширять legacy app/Services новыми классами; не изменять публичные HTTP-контракты; правила символов и известных вариантов названий сохраняются.

**Масштаб**: один доменный normalizer, один существующий repository contract/implementation, четыре runtime-потребителя устаревшего Finder, единая точка конвейера разбора протоколов и их тесты.
