# Исследование: Единая нормализация названий клубов

## Решение 1: сделать ClubNameNormalizer единственной доменной политикой

**Решение**: вынести существующий ClubNameNormalizer из подпространства Factory в
подпространство Club и использовать его во всех сценариях, где текстовое название
сравнивается с клубом.

**Обоснование**: нормализация нужна не только при создании агрегата, но и для
редактирования, импорта, идентификации и legacy-рендера. У класса нет обязанностей
фабрики, а SymbolNormalizer уже инкапсулирует преобразование аналогов символов.

**Рассмотренные альтернативы**:

- Оставить normalizer в Factory и использовать его вне фабрики — сохраняет неверную
  границу и маскирует общий доменный смысл.
- Оставить оба normalizer — повторение EDIT_MAP и двух разных правил trim снова
  приведёт к расхождению.

## Решение 2: удалить Finder и оставить семантический lookup в ClubRepository

**Решение**: удалить ClubFinder и NormalizedNameClubFinder. Дополнить существующий
ClubRepository семантическим методом поиска по уже нормализованному имени и реализовать
его в Eloquent-репозитории. Потребители сначала вызывают ClubNameNormalizer, затем
передают результат repository.

**Обоснование**: Finder не добавляет самостоятельного доменного поведения: он только
нормализует вход и передаёт generic Criteria в repository. Явный repository method
устраняет распространение строкового ключа normalizedName и оставляет один источник
нормализации. Finder фактически используют четыре runtime-пути: legacy PersonsService,
IdentProtocolLineCommand, OrientBySyncService и RendersEventDistance.

**Рассмотренные альтернативы**:

- Передавать Criteria из каждого потребителя — удаляет класс, но дублирует детали
  persistence query и строковый ключ.
- Создать новый application service — это лишняя оркестрация для одного lookup и
  противоречит цели упрощения.
- Оставить Finder как thin wrapper — не устраняет лишнюю абстракцию.

## Решение 3: очищать club централизованно в ParserService

**Решение**: после выбора конкретного parser в ParserService обрезать внешние пробелы
поля club у каждой распознанной строки.

**Обоснование**: ParserService — единственная общая точка, через которую протокол
передаётся в persistence и идентификацию. Это покрывает все поддерживаемые форматы
одним правилом и гарантирует, что следующие шаги конвейера видят очищенное значение.
Исторические строки не мигрируются: общий normalizer продолжает обрезать пробелы при
сопоставлении на чтении.

**Рассмотренные альтернативы**:

- Добавить trim в каждый format-specific parser — потребует параллельных правок и
  оставит риск пропустить следующий parser.
- Очищать значение только перед сохранением ProtocolLine — идентификация всё ещё
  увидит неочищенные parser results.
- Мигрировать исторические строки — не требуется для корректного runtime
  сопоставления и увеличивает риск.

## Решение 4: тестировать границы поведения, а не удалённые классы

**Решение**: удалить тест Finder и добавить/обновить тесты единого normalizer,
repository lookup, parser pipeline и затронутых legacy consumers по их observable
результату.

**Обоснование**: тесты должны защищать правила имени, lookup и trim, а не
несуществующую обёртку. Domain-тесты используют моки ClubRepository; integration
тесты создают записи только для Eloquent/persistence поведения.

**Рассмотренные альтернативы**:

- Оставить тест удалённого Finder — он закрепляет технический долг.
- Проверить только компиляцию потребителей — не защитит правила соответствия и
  регрессию внешних пробелов.
