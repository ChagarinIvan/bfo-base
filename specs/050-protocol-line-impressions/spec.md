# Feature Specification: Impressions строк протокола

**Feature Branch**: `master`, текущая ветка сохранена

**Created**: 2026-10-27

**Status**: Implemented and validated

**Input**: User description: "новый спеккит, добавляем импрешшены на протоколл лайны.. старые заполняем миграцией, берём с ивентов, новые ставим в фэктори используя клок"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Заполнить аудит существующих строк (Priority: P1)

Администратор обновляет систему и получает сведения о создании и последнем
изменении старых строк протоколов. Источником служит связанное событие.

**Why this priority**: Старые данные должны оставаться доступными после появления
обязательного аудита, без повторного импорта протоколов.

**Independent Test**: Выполнить миграцию на строках нескольких событий с разными
авторами и датами создания и обновления. Сравнить аудит строк с аудитом их событий.

**Acceptance Scenarios**:

1. **Given** строка связана с событием через дистанцию, **When** выполняется
   миграция, **Then** `created` строки получает время и автора из `created`
   события, а `updated` получает время и автора из `updated` события.
2. **Given** несколько строк относятся к разным событиям, включая неактивные
   события и события с незавершённой обработкой, **When** выполняется миграция,
   **Then** каждая строка получает аудит своего события независимо от его статуса.
3. **Given** старый протокол содержит результаты и связи со спортсменами,
   **When** выполняется миграция, **Then** количество строк, результаты, связи
   и состояние обработки событий сохраняются; бизнес-события не публикуются.

### User Story 2 - Фиксировать создание новых строк (Priority: P1)

При импорте протокола система фиксирует фактическое время создания каждой новой
строки и автора операции. Дата создания события не подменяет время импорта.

**Why this priority**: После миграции новые строки должны сразу иметь полный
аудит, в том числе при повторной загрузке протокола старого события.

**Independent Test**: Зафиксировать время системы и импортировать протокол события,
созданного раньше. Проверить аудит строк до сохранения и после повторного чтения.

**Acceptance Scenarios**:

1. **Given** событие создано в момент T0, а источник времени возвращает T1,
   **When** фабрика создаёт строку, **Then** её `created` и начальный `updated`
   содержат T1 и одного и того же автора операции импорта.
2. **Given** протокол загружается повторно в момент T2, **When** создаются строки
   нового импорта, **Then** они получают T2, а не дату события или старых строк.
3. **Given** фабрика не получила ни одной строки входных данных, **When**
   выполняется импорт, **Then** система не создаёт строк и фиктивных записей аудита.
4. **Given** строка создана фабрикой с заполненным аудитом, **When** система
   сохраняет и читает её, **Then** время и автор обоих impressions сохраняются.

5. **Given** пользователь объединяет события, **When** создаются производные
   строки нового события, **Then** они получают created и updated операции
   объединения, время которой задаёт фабрика нового Event через Clock.

### User Story 3 - Сохранять аудит существующих переходов строки (Priority: P2)

При назначении спортсмена или изменении активации разряда система сохраняет
автора и время операции в самой строке протокола.

**Why this priority**: Добавленные сведения об изменении должны отражать операции,
для которых строка уже принимает Impression и публикует доменное событие.

**Independent Test**: Выполнить назначение спортсмена и активацию разряда с новым
Impression, сохранить строку и проверить аудит после повторного чтения.

**Acceptance Scenarios**:

1. **Given** строка имеет `created` и `updated`, **When** `assignPerson`,
   `setPerson` или `activateRank` успешно меняет её состояние, **Then** `updated`
   равен Impression операции, `created` сохраняется, существующее доменное
   событие содержит тот же Impression.
2. **Given** активация разряда недопустима по действующим правилам, **When**
   операция отклоняется, **Then** аудит и сохранённое состояние строки не меняются.
3. **Given** строка сохранена после успешного перехода, **When** её сохраняют
   повторно без нового перехода, **Then** аудит сохраняется и прежнее событие
   не публикуется повторно.

### Edge Cases

- Пустая таблица строк протокола допускает применение и откат миграции.
- Отсутствующая дистанция, событие или неполный аудит источника не допускают
  успешного завершения заполнения с пустыми или вымышленными impressions.
  Ошибка должна позволять найти повреждённую связь и исправить данные.
- Исторические `created` и `updated` события могут различаться по времени
  и автору. Миграция переносит обе пары без объединения и исправления истории.
- Импорт из фонового обработчика использует автора операции, переданного в
  существующем сценарии обработки. Системная операция использует установленного
  в проекте системного пользователя.
- Изменение события после миграции не переписывает аудит его строк.
- Очистка и замена импортного протокола сохраняют существующую политику
  физического удаления производных строк вместе с их аудитом.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Каждая строка протокола MUST хранить полный `created` и `updated`.
  Каждый Impression содержит время `at` и идентификатор автора `by`.
- **FR-002**: Миграция MUST заполнить аудит всех существующих строк из связанного
  Event через Distance: `created` из `Event.created`, `updated` из `Event.updated`.
- **FR-003**: Миграция MUST переносить исходные значения точно, независимо от
  активности и статуса обработки события, без изменения результатов и связей.
- **FR-004**: Миграция MUST выявлять строки без доступного источника полного
  аудита и не сообщать об успешном заполнении таких данных. Подстановка текущего
  времени или произвольного пользователя для старых строк запрещена.
- **FR-005**: Фабрика новых строк MUST задавать оба impressions до сохранения,
  используя внедрённый Clock для времени и автора текущей операции импорта.
  Начальные `created` и `updated` одной строки MUST совпадать по времени и автору.
  Производные строки объединённого Event получают его новый Impression создания.
- **FR-006**: Хранение и повторное чтение MUST сохранять обе пары значений;
  автоматическое изменение времени без автора не должно подменять Impression.
- **FR-007**: Успешные изменения через `assignPerson`, `setPerson` и `activateRank`
  MUST обновлять `updated` переданным Impression и сохранять `created`.
  Существующие правила допустимости и доменные события сохраняются.
- **FR-008**: Отклонённая операция MUST сохранять прежнее состояние и аудит.
  Повторное сохранение без нового перехода MUST не изменять impressions
  и не дублировать прежние события.
- **FR-009**: Историческое заполнение MUST быть технической операцией без
  публикации бизнес-событий, запуска идентификации и пересчёта разрядов.
- **FR-010**: Добавление аудита MUST сохранять действующие границы транзакций
  импорта и изменений строки, сохранение через repository и доставку обработчиков,
  читающих записанное состояние, после commit.
- **FR-011**: Откат миграции MUST удалять добавленный аудит, сохраняя строки,
  результаты и их связи. Повторное применение после отката восстанавливает
  исторический аудит по актуальным на тот момент значениям событий.

### Key Entities *(include if feature involves data)*

- **ProtocolLine**. Строка результата, владеет своим `created` и `updated`.
  Назначение спортсмена и активация разряда являются её существующими переходами.
- **Impression**. Пара времени и автора создания или последнего изменения.
- **Event**. Источник исторического аудита при миграции существующих строк.
- **Distance**. Связывает строку протокола с её событием.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После успешной миграции 100% существующих строк имеют полный аудит,
  совпадающий с соответствующими парами связанного события на момент переноса.
- **SC-002**: 100% новых строк получают время фактического создания и автора
  операции; начальные сведения о создании и изменении совпадают.
- **SC-003**: Для каждого из трёх существующих переходов строки проверено
  сохранение нового аудита изменения при неизменном аудите создания.
- **SC-004**: Миграция сохраняет количество строк и все прежние результаты
  и связи; количество вызванных ею бизнес-событий равно нулю.
- **SC-005**: Проверки отклонённой операции, повторного сохранения, пустого
  протокола и отката подтверждают отсутствие потери исходных результатов.

## Assumptions

- Запрос развивает проблему REF-05 из архитектурного манифеста и сценарии
  обработки протокола фичи 025. Для него создаётся отдельная фича 050.
- Под impressions понимаются оба значения `created` и `updated` по существующей
  модели проекта. Для старых строк аудит события является приближённой историей,
  поскольку отдельной истории операций строк раньше не сохранялось.
- Автор новых строк берётся из текущей операции импорта, которая уже несёт
  Impression. Он может отличаться от автора создания Event.
- Изменения ограничены хранением аудита, историческим заполнением, фабрикой
  и тремя существующими переходами строки. Новые экраны, поля публичных ответов,
  полная история изменений и изменение смысла EventParsed не требуются.
- Строка остаётся владельцем своего аудита и производными импортными данными.
  Создание при техническом импорте не требует нового события создания строки.
  Физическое удаление при очистке протокола сохраняется.
- Существующая Eloquent-модель в Domain является переходным долгом REF-13.
  Эта фича не добавляет framework-зависимостей в бизнес-правила. Выделение чистой
  модели и mapper выполняется отдельным ограниченным шагом с проверкой фабрики,
  трёх переходов и сохранения аудита; legacy services/repositories не расширяются.
- План должен предусмотреть миграционные и integration-проверки сохранения,
  проверки времени фабрики с управляемым Clock, отсутствие новых N+1,
  актуализацию REF-05 и запись о завершённой фиче на странице обновлений.
