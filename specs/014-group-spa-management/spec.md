# Спецификация фичи: управление группами в SPA

**Ветка фичи**: `014-group-spa-management`

**Создано**: 2026-09-03

**Статус**: In progress

**Входные данные**: запрос пользователя: «Перенести на SPA страницы групп: публичный
постраничный список с поиском по названию, просмотр группы со списком стартов, действия
редактирования, удаления и объединения; использовать подход страницы клубов и спецификации
007-club-spa-management; в конце удалить legacy. Для стартов использовать существующий API с
фильтром `groupId` и `withCompetition=1`, добавить пагинацию и фильтры по названию, году и дате
соревнования, без колонки действий».

## Контекст и границы

Раздел групп сейчас обслуживается Blade-маршрутами `/groups`, `/groups/{id}`, `/groups/{id}/unit`
и операциями изменения через legacy-сервис. Фича переносит пользовательские страницы групп в
общий Vue SPA, сохраняя существующие данные и единообразные паттерны страницы клубов:
пагинацию, состояния загрузки/ошибки/пустого результата, auth-aware служебные поля и действия.

Список и просмотр группы доступны публично. Редактирование, удаление и объединение доступны только
аутентифицированному пользователю. Поля `created` и `updated` передаются и отображаются только
аутентифицированному пользователю.

Страница группы показывает сверху информацию о группе, а снизу — постраничный список стартов
(дистанций с событиями), используя существующий `events` API с расширением критериев. В выдачу
стартов включается название соревнования только при `withCompetition=1`; действия над строками не
показываются.

Удаление legacy выполняется после проверки всех usages. Удаляются заменённые Blade-страницы,
контроллеры и действительно неиспользуемые group-only артефакты. Общие зависимости групп,
которые нужны кубкам, парсерам или другим разделам, сначала переводятся на целевые интерфейсы и
адаптеры либо явно сохраняются до отдельной фичи; удаление работающего общего сценария без замены
не допускается.

## Уточнения

### Session 2026-09-03

- Список групп и просмотр отдельной группы публичны; служебные сведения `created`/`updated` и
  операции изменения требуют аутентификации.
- Список сортируется по `distancesCount` по убыванию. Для стабильной пагинации при равных значениях
  используется идентификатор группы по возрастанию.
- Непустой поиск по названию принимает от одного значимого символа; внешние пробелы удаляются.
  Клиент отправляет поиск с debounce около 300 мс, а пустой запрос восстанавливает полный список.
- Объединение означает перенос всех дистанций исходной группы в выбранную целевую группу с
  последующим soft-delete исходной группы (`active=false`). Целевая группа сохраняется. Исходная группа не может быть
  выбрана как цель.
- Legacy-страница объединения заменяется отдельным SPA-маршрутом с таблицей целевых групп,
  пагинацией и действием «Объединить»; поиск по названию на этой таблице использует тот же контракт,
  что и список групп.
- Удаление группы является soft-delete: группа получает `active=false`, а связанные дистанции и
  строки протокола сохраняются. Перед операцией SPA показывает подтверждающий popup.
- В текущей схеме `groups` нет полей аудита; добавляются Laravel timestamps, `created_by` и
  `updated_by` с DB defaults `CURRENT_TIMESTAMP` и system user ID `10`. Historical rows получают
  `normalize_name`, после чего это поле становится `NOT NULL`.
- Для стартов используются существующие поля строки события: название соревнования, название
  старта/события, дата и количество участников. Год соревнования является годом даты соревнования;
  название и дата соревнования должны быть доступны для фильтрации на сервере.
- Старые group-only web routes и Blade actions удаляются полностью. Пользовательский вход в группы
  существует только через SPA-маршруты. Старые POST/GET mutation-операции не обслуживаются.

### Session 2026-09-04

- Поиск групп выполняется по `normalize_name`: входное значение проходит `GroupNameNormalizer`,
  одинаковый для сохранения, duplicate-check, поиска и parser/import comparison. Для исторических
  строк добавляется отдельная миграция повторного пересчёта нормализованных значений.
- Страница объединения использует общий `GroupListingTable`, тот же компонент, фильтр, колонки и
  paginator, что и `/app/groups`; отличается только action slot с кнопкой объединения.
- Вверху merge-страницы отображается info table исходной группы с `distancesCount`, `created` и
  `updated` impressions.
- Кнопка объединения и action подтверждения используют success-стиль. Popup подтверждения показывает
  названия исходной и целевой групп.
- Фильтры этапов переиспользуют API годов и Select со страницы соревнований, общий `DateFilter`, а
  поиск по названию соревнования отправляется после debounce только начиная с 3 символов.

## Пользовательские сценарии и тестирование

### Пользовательская история 1 — найти и открыть группу (приоритет: P1)

Посетитель открывает публичный SPA-список групп, видит группы с количеством дистанций, ищет группу
по названию и открывает страницу нужной группы.

**Почему этот приоритет**: список является основным входом в раздел и необходим для всех действий
просмотра и управления.

**Независимая проверка**: открыть `/app/groups` без авторизации, проверить пагинацию и сортировку,
ввести один символ и затем фрагмент названия, дождаться debounce, перейти на другую страницу и
открыть группу.

**Сценарии приёмки**:

1. **Given** посетитель открывает список групп, **When** данные загружены, **Then** отображается
   постраничная таблица групп с названием, `distancesCount`, общим количеством результатов и
   переходами пагинации.
2. **Given** список содержит группы с разным количеством дистанций, **When** он загружен, **Then**
   группы упорядочены по `distancesCount` от большего к меньшему, а при равенстве — по id без
   повторов и пропусков между страницами.
3. **Given** пользователь вводит один или более значимых символов, **When** проходит debounce около
   300 мс, **Then** отправляется один актуальный запрос и отображаются только группы, в названии
   которых есть фрагмент без учёта регистра.
4. **Given** фильтр очищен или изменён на другой странице, **When** поиск выполняется, **Then** текущая
   страница сбрасывается на первую; очистка возвращает полный список.
5. **Given** посетитель не аутентифицирован, **When** список загружен, **Then** `created` и `updated`
   отсутствуют в ответе и в таблице.
6. **Given** посетитель нажимает название группы, **When** маршрут открывается, **Then** он попадает
   на SPA-страницу группы, а не на Blade-страницу.

### Пользовательская история 2 — просмотреть группу и её старты (приоритет: P1)

Посетитель открывает страницу группы и видит её основные сведения и постраничный список стартов,
связанных с этой группой.

**Почему этот приоритет**: просмотр группы и её истории стартов — основной пользовательский смысл
раздела после поиска.

**Независимая проверка**: открыть существующую группу публично, проверить информационную таблицу,
список стартов, пагинацию, фильтры по названию/году/дате соревнования и пустое состояние.

**Сценарии приёмки**:

1. **Given** открыта существующая активная группа, **When** страница загружена, **Then** сверху
   отображаются название и `distancesCount`, а ниже — первая страница стартов.
2. **Given** API получает `groupId=<int>&withCompetition=1`, **When** список стартов загружен,
   **Then** каждая строка содержит название соревнования, название старта, дату и количество
   участников; переход по соревнованию остаётся SPA-ссылкой, если такой маршрут доступен.
3. **Given** пользователь задаёт название соревнования от 3 символов, год или точную дату, **When** фильтр
   применён, **Then** сервер возвращает только соответствующие старты, пагинация сбрасывается на
   первую страницу, а запросы не загружают данные сверх текущей страницы.
4. **Given** пользователь не аутентифицирован, **When** страница загружена, **Then** `created` и
   `updated` группы не раскрываются; строки стартов не содержат колонок действий.
5. **Given** группа не существует или не имеет стартов, **When** загрузка завершена, **Then** SPA
   показывает понятное состояние «не найдена» или явное пустое состояние без необработанной ошибки.
6. **Given** стартов больше размера страницы, **When** пользователь переходит между страницами,
   **Then** строки не дублируются и не пропускаются, а порядок стабилен.

### Пользовательская история 3 — отредактировать и удалить группу (приоритет: P2)

Аутентифицированный пользователь редактирует название группы или удаляет группу с явным
подтверждением.

**Почему этот приоритет**: эти операции заменяют административные действия старой страницы групп.

**Независимая проверка**: открыть действия после входа, сохранить новое уникальное название,
отправить дубликат, затем проверить popup удаления и итоговое отсутствие группы и её зависимых
данных.

**Сценарии приёмки**:

1. **Given** пользователь аутентифицирован и открыл группу, **When** он выбирает «Редактировать»,
   **Then** SPA открывает заполненную форму и после успеха возвращает на обновлённую страницу группы.
2. **Given** новое название пустое, слишком длинное или совпадает с другой группой после
   нормализации, **When** форма отправлена, **Then** данные не меняются, ошибка валидации показана
   у поля, а duplicate-конфликт возвращён единообразным HTTP 409-кодом.
3. **Given** посетитель не аутентифицирован, **When** он открывает edit URL или mutation API,
   **Then** форма/операция недоступна и данные не меняются.
4. **Given** аутентифицированный пользователь нажал «Удалить», **When** он отменяет popup, **Then**
   группа и старты остаются без изменений.
5. **Given** пользователь подтвердил удаление, **When** операция завершена, **Then** группа,
   получает `active=false`, больше не попадает в read-модели, а SPA возвращает пользователя к списку групп.

### Пользовательская история 4 — объединить группы (приоритет: P2)

Аутентифицированный пользователь открывает отдельную страницу объединения исходной группы,
просматривает постраничную таблицу групп и выбирает целевую группу.

**Почему этот приоритет**: объединение является существующей операцией очистки дублей и должно
сохраниться при удалении legacy UI.

**Независимая проверка**: открыть `/app/groups/{sourceId}/merge`, найти цель через поиск и
пагинацию, подтвердить объединение и проверить, что дистанции исходной группы отображаются у цели,
а исходная группа исчезла.

**Сценарии приёмки**:

1. **Given** пользователь аутентифицирован и открыл merge URL, **When** данные загружены, **Then**
   отображается info table исходной группы с impressions и общий paginated listing доступных целевых
   групп с названием и `distancesCount`; исходная группа в списке отсутствует.
2. **Given** пользователь фильтрует целевые группы по названию или переходит по страницам, **When**
   запрос завершён, **Then** применяется тот же min-length/debounce/search-контракт, что и в списке.
3. **Given** пользователь выбрал другую целевую группу и подтвердил popup с названиями обеих групп,
   **When** объединение
   завершено, **Then** все дистанции исходной группы привязаны к цели, исходная группа soft-deleted, а
   пользователь переходит к списку групп с актуальными счётчиками.
4. **Given** исходная или целевая группа не найдена, операция уже выполняется, либо source равен
   target, **When** запрос обработан, **Then** сервер атомарно не меняет данные и возвращает понятную
   ошибку; SPA не показывает ложный успех.
5. **Given** пользователь не аутентифицирован, **When** он открывает merge URL или отправляет
   mutation API, **Then** операция отклоняется стандартным auth-ответом.

### Пользовательская история 5 — завершить миграцию групп (приоритет: P3)

Пользователь может попасть в группы из navbar и внутренних ссылок, но не видит удалённые Blade-
страницы и не сталкивается с поломанными shared-сценариями.

**Почему этот приоритет**: удаление legacy безопасно только после сохранения всех поддерживаемых
переходов и общих backend-потребителей.

**Независимая проверка**: проверить navbar, все найденные ссылки на `/groups`, старые GET-адреса,
отсутствие заменённых Blade-обработчиков и usages удаляемого кода; отдельно проверить кубки,
парсер и другие потребители групп.

**Сценарии приёмки**:

1. **Given** пользователь находится в SPA или legacy-разделе, **When** он выбирает группы, **Then**
   открывается `/app/groups`.
2. **Given** существующая внутренняя ссылка указывает на группу, **When** она открыта, **Then** она
   ведёт на `/app/groups/{id}` или корректно перенаправляется туда.
3. **Given** запрошен старый group-only GET `/groups`, `/groups/{id}` или `/groups/{id}/unit`, **When** маршрут
   обработан, **Then** route отсутствует и Blade-контент не рендерится.
4. **Given** выполнен аудит репозитория, **When** артефакт group-only больше не имеет потребителей,
   **Then** legacy-контроллер, Blade-шаблон, маршрут, сервисный метод, перевод или компонент удалён;
   shared-код удаляется только после миграции его потребителей.
5. **Given** проверяются кубки, парсер и связанные расчёты, **When** фича завершена, **Then** они
   продолжают работать на целевой реализации групп без новых обращений к удалённым web-артефактам.

## Требования

### Функциональные требования

- **FR-001**: Система ДОЛЖНА предоставлять публичный версионированный JSON API постраничного списка
  групп.
- **FR-002**: Элемент списка и просмотра ДОЛЖЕН сериализоваться как `ViewGroupDto` с полями `id`,
  `name`, `distancesCount`, `created`, `updated`; `created` и `updated` должны отсутствовать в
  неаутентифицированном ответе. Для этого backend должен хранить время и пользователя создания/
  обновления группы.
- **FR-003**: Список ДОЛЖЕН фильтроваться по подстроке `name` без учёта регистра после удаления
  внешних пробелов; непустой фильтр должен содержать минимум один значимый символ.
- **FR-004**: SPA ДОЛЖНА применять debounce около 300 мс к поиску названия, не отправлять запросы
  для пустого ввода до немедленной очистки и сбрасывать страницу на первую при изменении/очистке
  фильтра.
- **FR-005**: Сервер ДОЛЖЕН валидировать `name`, `page` и `perPage`, возвращать стандартную ошибку
  422 для невалидных параметров и передавать pagination metadata в том же формате, что клубы и
  соревнования.
- **FR-006**: Список ДОЛЖЕН сортироваться по `distancesCount DESC`, затем по `id ASC`; запрос
  должен считать количество дистанций на стороне БД и не создавать N+1.
- **FR-007**: Страница группы ДОЛЖНА быть публичной и показывать информационную таблицу группы и
  постраничный список её стартов через тот же `events` API.
- **FR-008**: `events` API ДОЛЖЕН поддерживать `groupId` как положительный integer и `withCompetition`
  как явный флаг; при `groupId` выборка должна включать только активные события, имеющие дистанцию
  этой группы, а при `withCompetition=1` DTO должен включать название соревнования.
- **FR-009**: Выдача стартов ДОЛЖНА поддерживать фильтры по подстроке названия соревнования, году
  даты соревнования и точной дате соревнования; фильтры должны работать совместно, валидироваться
  сервером и участвовать в сбросе пагинации на клиенте.
- **FR-010**: В таблице стартов ДОЛЖНЫ отображаться название соревнования, название события/старта,
  дата и количество участников; колонка действий и mutation-кнопки для строк стартов не должны
  отображаться.
- **FR-011**: Редактирование названия группы ДОЛЖНО быть доступно только аутентифицированному
  пользователю, использовать общую форму и доменное правило предотвращения дубликатов.
- **FR-012**: Название группы при create/update ДОЛЖНО быть обязательным, непустым после trim и не
  длиннее 255 символов; duplicate-проверка должна применять ту же нормализацию к новой и имеющейся
  записи, исключая текущую группу при update.
- **FR-013**: Duplicate-конфликт группы ДОЛЖЕН быть HTTP 409 с уникальным кодом
  `group_name_already_exists`; неаутентифицированная mutation — стандартный 401/redirect-контракт.
- **FR-014**: Удаление группы ДОЛЖНО требовать аутентификацию и подтверждение в popup; успешная
  операция должна атомарно удалить группу, её дистанции и связанные protocol lines.
- **FR-015**: Объединение ДОЛЖНО быть отдельным аутентифицированным маршрутом и API-операцией,
  принимать source и target group ids, запрещать одинаковые ids и атомарно переводить все дистанции
  source в target с последующим удалением source.
- **FR-016**: Merge-страница ДОЛЖНА показывать source и переиспользовать постраничный group list для
  целей, исключая source; каждая доступная цель должна иметь действие «Объединить» и подтверждение.
- **FR-017**: Все новые сценарии ДОЛЖНЫ использовать Application/Domain/Bridge/Infrastructure;
  новые классы в `app/Services` и новые legacy-репозитории добавлять нельзя.
- **FR-018**: Все изменения поведения ДОЛЖНЫ быть покрыты unit-тестами Application/Domain без
  Eloquent-сущностей и API/frontend integration-тестами с реальной БД только там, где проверяется
  HTTP или persistence.
- **FR-019**: После переноса navbar и найденные внутренние ссылки ДОЛЖНЫ вести в SPA; старые GET
  group-адреса должны быть удалены, а заменённые Blade-страницы, маршруты,
  контроллеры и неиспользуемые group-only legacy-классы должны быть удалены.
- **FR-020**: Перед завершением фичи ДОЛЖНЫ быть проверены запросы списка/стартов на отсутствие N+1;
  индекс или иная оптимизация для сортировки по числу дистанций добавляется только по результатам
  анализа фактического SQL/плана выполнения, а не автоматически.

### Архитектурные и миграционные ограничения

- Контракт списка групп принадлежит Domain, use cases — `app/Application`, HTTP actions/resources —
  `app/Bridge`, Eloquent query adapters — `app/Infrastructure`.
- Существующий `GroupsRepository`/`GroupsService` используется shared-сценариями; перед удалением
  нужно найти все usages, перенести необходимые операции на целевые интерфейсы и не удалять рабочие
  зависимости кубков/парсера без замены.
- DTO serialization groups должны повторять поведение уже мигрированных клубов: служебные поля
  доступны только группе `authenticated`.
- SPA использует существующие `api` client, pagination helpers, auth store, PrimeVue components и
  i18n; отдельная UI-библиотека не добавляется.

### Ключевые сущности

- **Group**: именованная группа дистанций; имеет id, name и связи с дистанциями.
- **ViewGroupDto**: публично сериализуемое представление группы с количеством дистанций и auth-only
  impressions.
- **Event/Start**: активное событие, имеющее дистанцию выбранной группы; содержит сведения для
  таблицы стартов и опциональное название соревнования.
- **GroupMerge**: атомарная операция переноса дистанций от source к target с удалением source.

## Критерии успеха

### Измеримые результаты

- **SC-001**: Неаутентифицированный посетитель может открыть список и страницу группы через SPA;
  ни один проверенный публичный сценарий не отдаёт заменённый Blade-контент.
- **SC-002**: При проверке минимум 20 групп список сохраняет сортировку `distancesCount DESC, id ASC`
  и не показывает повторов/пропусков при переходе между всеми страницами.
- **SC-003**: В 100% проверенных поисковых сценариев от одного значимого символа и после debounce
  выдаются только совпадающие по названию группы; очистка возвращает полный список.
- **SC-004**: Страница группы показывает 100% её активных стартов через пагинацию, а комбинации
  фильтров название соревнования + год + дата возвращают корректное подмножество.
- **SC-005**: Аутентифицированный пользователь может завершить edit, delete и merge в SPA; duplicate,
  auth и validation ошибки не меняют исходные данные.
- **SC-006**: Каждый API-запрос списка групп или стартов выполняет не более четырёх DB-запросов,
  независимо от количества строк текущей страницы, и не содержит новых N+1.
- **SC-007**: После legacy-аудита не остаётся неиспользуемых group-only Blade-страниц, web actions,
  mutation-маршрутов и связанных переводов; shared-потребители продолжают проходить тесты.

## Предположения

- Существующая API-аутентификация, сериализация DTO и pagination headers переиспользуются без смены
  протокола.
- В базе группа является активной сущностью с флагом `active`; отсутствие активной группы после
  удаления означает 404. Audit columns для `created`/`updated` добавляются этой фичей, а старые
  строки получают безопасное backfill-значение.
- Фильтр даты соревнования — точное значение `YYYY-MM-DD`; фильтр года — четырёхзначный год,
  извлечённый из даты соревнования.
- В v1 не добавляются создание группы, массовое объединение нескольких целей, undo merge или
  редактирование отдельного старта.
- При потребности в индексе сначала проверяется существующая схема и SQL-план; изменение схемы
  допускается только как обоснованная оптимизация с миграцией и тестом отката. Audit migration
  является обязательной частью фичи.
- Ссылки на ещё не перенесённые legacy-страницы событий/персон сохраняются как внешние href, если
  это требуется существующим пользовательским потоком.
