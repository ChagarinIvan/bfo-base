# Feature Specification: Статусы обработки протокола этапа

**Feature Branch**: `025-protocol-processing-status`

**Created**: 2026-09-13

**Status**: In progress, revised after merge with master on 2026-09-27

**Input**: User description: "После создания или редактирования этапа с протоколом или ссылкой на него обработка выполняется асинхронно. Пользователь должен видеть ход обработки, предупреждение о ещё нераспознанных спортсменах и автоматически получать итоговое состояние без ручного обновления страницы."

## Clarifications

### Session 2026-10-04

- Ошибка любой из трёх стадий публикует единое событие `EventProcessingFailed`. Его обработчик удаляет дистанции и строки неудачного протокола и пересчитывает разряды затронутых спортсменов.
- Ошибка завершает текущий запуск. Пользователь видит сообщение, исправляет протокол или ожидает исправления обработчика, затем загружает протокол заново через обновление Event. Только обновление протокола создаёт новый токен и запускает цепочку повторно.
- Запоздавшее событие ошибки с прежним токеном не удаляет данные нового протокола.
- После очистки Event решает, нужно ли сбросить кеш кубков: для связанного с кубком этапа вызывает доменный порт инвалидации кеша. Только активный Event в состоянии `parsing` публикует `EventProtocolCleaned` и продолжает разбор.
- Объединение этапов выполняется синхронно: `UniteFactory` создаёт Event сразу в `ready`, сохранение не публикует `EventCreated` и не запускает стадии обработки. Производные строки не содержат выполненного и активированного разряда; объединённый протокол не участвует в присвоении разрядов.

### Session 2026-10-02

- Видимость Event сохраняет разделение по авторизации: авторизованный пользователь видит активные этапы во всех стадиях обработки, гость только `ready`. Application передаёт гостевой фильтр через `EventResources::readyOnly`, чтобы фронтенд продолжал получать текущий статус обработки.
- Обычные чтения Distance и ProtocolLine через repository ДОЛЖНЫ скрывать результаты Event со статусом, отличным от `ready`, независимо от авторизации. Фильтр действует вместе с существующими условиями `active`; отдельные проверки гостя в Application и `readyOnly` в ProtocolLineResources удаляются.
- Методы repository `lock*` используются внутренними операциями обработки и сохраняют доступ к активным Event и их результатам до готовности. Для поиска Distance во время parsing используется `lockOneByCriteria`.
- Авторизованные list/detail-запросы Event сохраняют отображение переходных статусов и ошибок и используются для polling обработки.

### Session 2026-09-13

- Q: Что пользователь должен видеть и иметь возможность сделать, если разбор протокола завершился ошибкой? → A: Авторизованный пользователь видит сообщение «Ошибка парсинга протокола. Свяжитесь с администратором»; отдельная команда повтора не входит в фичу, новый запуск начинается после обновления протокола. Гости видят только этапы с полностью завершённой обработкой протокола. Формулировка для других стадий уточнена в ревизии 2026-09-28.
- Q: Должны ли гости видеть этапы, у которых протокол вообще не добавлялся? → A: Нет. Это прежнее допущение заменено уточнением от 2026-09-30: такой этап не создаётся.
- Q (2026-09-30): Может ли этап существовать без протокола? → A: Нет. При создании обычного этапа источник протокола обязателен. Объединённый этап получает производный протокол из исходных этапов и сразу готовые результаты.
- Q (2026-09-30): Когда фиксировать ошибку разбора? → A: Разбор выполняется один раз; при ошибке сразу сохраняется `parsingError`.
- Q: Когда распознавание спортсменов считается завершённым? → A: Только после идентификации всех строк протокола; если спортсмен не найден, система создаёт его. Финальный статус также требует завершённого зависимого пересчёта разрядов.
- Q: Как обновляется статус после отложенной идентификации? → A: Завершённая идентификация и пересчёт разрядов передают этапу подтверждённый сигнал о завершении; этап сам фиксирует переход жизненного цикла и публикует его событие.
- Q: Где живёт жизненный цикл одной загрузки протокола? → A: Исторический ответ про отдельный `EventProtocol` отменён решением пользователя в ревизии ниже; жизненный цикл принадлежит этапу.

### Session 2026-09-27

- Q: Сохранять отдельные стадии после возобновления фичи или свести их к трём статусам RankCheck? → A: Сохранить шесть стадий, упростить внутреннюю цепочку по образцу RankCheck.

### Revision 2026-09-28

- Решение пользователя: жизненный цикл не выделяется в отдельный `EventProtocol`. Владельцем статуса обработки и переходов является сам этап (`Event`). Создание этапа с протоколом сразу начинает `parsing`; после разбора `Event` переходит в `identifying` и публикует событие для следующей фоновой стадии. Это решение отменяет ответ о хранении отдельного run из сессии 2026-09-13.
- Идентификация и пересчёт разрядов выполняются каждый одним фоновым процессом последовательно по строкам и спортсменам, без отдельных заданий для каждой строки или спортсмена. Результат идентификации каждой строки сохраняется по мере обработки; очередь нераспознанных строк `IdentLine` в этом процессе не используется. Отдельная команда ручного возобновления в 025 не входит.
- В течение идентификации и пересчёта один обработчик удерживает блокировку этапа, независимую от транзакции базы. Разбор файла остаётся атомарным. При зафиксированной ошибке любой стадии данные неудачного протокола очищаются.
- По решению пользователя `Event` выполняет циклы идентификации и пересчёта через доменные сервисы, которые сохраняют обработанные строки и спортсменов через repository ports. Eloquent остаётся только в Infrastructure.
- Ошибка каждой стадии получает отдельный статус: `parsingError`, `identifyingError` или `rebuildingRanksError`. `Event.errorMessage` хранит безопасное для показа сообщение; авторизованный интерфейс показывает статус и сообщение, а новый протокол очищает прежнюю ошибку.
- Внешняя блокировка имеет длительный срок действия и освобождается в конце обработки. Этот срок выбирается больше максимального времени выполнения задания; проверка владения остаётся защитой при потере блокировки.
- Текущая реализация `EventProtocol` и её статус `failed` ещё не применялись. Новая схема сразу содержит только три статуса ошибок по стадиям; перенос старого `failed` не нужен.
- Доменный сервис может сохранять строки и спортсменов через доменные интерфейсы репозиториев. Прямой доступ к Eloquent из нового доменного кода запрещён. Общее правило конституции об Application-оркестрации persistence будет пересмотрено отдельно позднее.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Видеть обработку нового протокола (Priority: P1)

Пользователь создаёт этап с файлом протокола или ссылкой на него и после перехода на страницу этапа понимает, что протокол ещё обрабатывается, а не принимает пустой список результатов за конечный результат.

**Why this priority**: создание этапа с протоколом — основной путь появления результатов; отсутствие статуса создаёт ложное впечатление, что данные потерялись.

**Independent Test**: Создать этап с протоколом, вернуть переходное состояние и убедиться, что страница показывает статус и индикатор ожидания, затем автоматически обновляет данные до следующего состояния.

**Acceptance Scenarios**:

1. **Given** пользователь создал этап с протоколом или ссылкой, **When** он попадает на страницу этапа до окончания разбора, **Then** он видит понятное сообщение «протокол в обработке», визуальный индикатор ожидания и не видит пустой результат как окончательный.
2. **Given** обработка протокола ещё идёт, **When** состояние меняется, **Then** страница обновляет статус и результаты самостоятельно не реже одного раза в 5 секунд.
3. **Given** протокол разобран, **When** система ещё определяет спортсменов, **Then** пользователь видит предупреждение, что распознавание спортсменов не завершено, а страница продолжает ожидать итог.
4. **Given** все строки протокола сопоставлены со спортсменами, **When** зависимый пересчёт разрядов ещё выполняется, **Then** пользователь видит статус обновления разрядов и страница продолжает ожидать итог.
5. **Given** фоновая идентификация завершилась ошибкой после сохранения части строк, **When** обработчик получает `EventProcessingFailed`, **Then** строки и дистанции этого протокола удаляются, этап показывает ошибку, а новый запуск возможен после обновления протокола.

---

### User Story 2 - Понимать итог и сбой обработки (Priority: P1)

Пользователь открывает этап с ранее добавленным протоколом и сразу понимает, готовы ли результаты к использованию, либо обработка завершилась ошибкой.

**Why this priority**: состояния должны быть понятны не только сразу после редактирования, иначе пользователь не может отличить задержку фоновой задачи от ошибки.

**Independent Test**: Открыть этапы в готовом и ошибочном состояниях и проверить, что готовый этап не показывает ожидание, а ошибка не маскируется бесконечной загрузкой.

**Acceptance Scenarios**:

1. **Given** протокол разобран, все его строки сопоставлены со спортсменами и пересчёт разрядов завершён, **When** пользователь открывает этап, **Then** он видит готовые результаты без индикатора ожидания и без дальнейших автоматических обновлений.
2. **Given** разбор, идентификация или пересчёт завершились ошибкой, **When** авторизованный пользователь открывает этап, **Then** он видит статус ошибки именно этой стадии и безопасное сообщение из `errorMessage` (при его отсутствии — локализованное сообщение стадии), а автоматическое ожидание прекращается.
3. **Given** этап имеет переходное или ошибочное состояние обработки, **When** гость открывает адрес этапа либо просматривает список этапов, **Then** этап недоступен и не раскрывает причину его отсутствия.
4. **Given** фоновый пересчёт разрядов завершился ошибкой, **When** пользователь обновляет протокол, **Then** Event получает новый токен и повторно проходит разбор, идентификацию и пересчёт до готовности.

---

### User Story 3 - Контролировать обработку в списке этапов (Priority: P2)

Авторизованный пользователь просматривает список этапов и видит состояние обработки каждого этапа, не открывая его карточку.

**Why this priority**: это позволяет контролировать несколько загруженных протоколов и быстро заметить ошибку.

**Independent Test**: Открыть список этапов как авторизованный пользователь и проверить отдельные подписи для обработки, распознавания, готовности и ошибки.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь открывает список этапов, **When** у этапа есть протокол, **Then** список показывает его актуальное состояние обработки.
2. **Given** в списке есть этап с ошибкой обработки, **When** авторизованный пользователь просматривает его, **Then** список показывает ошибочное состояние без бесконечного индикатора ожидания.
3. **Given** в открытом списке есть этап с переходным состоянием, **When** его состояние меняется, **Then** список обновляет статус не реже одного раза в 5 секунд и прекращает опрос, когда переходных этапов больше нет или пользователь ушёл со страницы.

---

### User Story 4 - Не тратить запросы после ухода со страницы (Priority: P3)

Пользователь покидает страницу этапа, пока обработка ещё идёт; приложение не продолжает обновлять невидимую страницу.

**Why this priority**: фоновое обновление должно помогать пользователю, не создавая лишнюю нагрузку.

**Independent Test**: Открыть обрабатываемый этап, убедиться в периодических обновлениях, перейти на другую страницу и подтвердить прекращение обновлений.

**Acceptance Scenarios**:

1. **Given** открыта страница этапа с переходным статусом, **When** пользователь переходит на другую страницу, **Then** последующие автоматические обновления не выполняются.
2. **Given** автоматическое обновление временно не удалось, **When** страница остаётся открытой и статус переходный, **Then** пользователь получает понятное сообщение, а следующая попытка обновления выполняется по обычному интервалу.

### Edge Cases

- Обработка меняет состояние между двумя обновлениями: следующее обновление показывает актуальное состояние и набор результатов без необходимости действия пользователя.
- Повторная доставка фоновой стадии не должна повторно создавать строки, спортсменов или преждевременно переводить этап в готовность.
- Повторная доставка события разбора после перехода этапа в другую стадию не меняет его состояние и не создаёт новые строки.
- Позднее событие завершения предыдущей стадии после замены файла не меняет состояние новой обработки.
- В одном ответе протокол уже разобран, но распознавание спортсменов либо пересчёт разрядов ещё не завершён: показывается соответствующее переходное состояние, а не статус готовности.
- Если после разбора остаётся строка протокола без определённого спортсмена, этап не может перейти в готовность; обработка продолжает стадию распознавания до идентификации всех строк.
- Если идентификация завершилась ошибкой после сохранения части строк, `EventProcessingFailed` запускает очистку строк и дистанций; статус остаётся `identifyingError` до обновления протокола.
- Если пересчёт разрядов завершился ошибкой, `EventProcessingFailed` запускает ту же очистку; новый запуск начинается только после обновления протокола.
- Фоновая задача сообщает ошибку после ранее показанного переходного состояния: авторизованный пользователь видит ошибку, ожидание прекращается, а гости не получают доступ к этапу.
- Пользователь вручную обновляет страницу: состояние этапа и правила автоматического ожидания определяются заново.
- Старые этапы без сведений о процессе считаются готовыми, если у них есть доступные результаты; они не остаются в бесконечном ожидании.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Каждый этап ДОЛЖЕН хранить одно из состояний `parsing`, `identifying`, `rebuildingRanks`, `ready`, `parsingError`, `identifyingError`, `rebuildingRanksError` и идентификатор поколения обработки. Обычный этап создаётся только с источником протокола и начинает обработку в `parsing`; объединённый этап получает производные результаты и создаётся в `ready`.
- **FR-002**: Система ДОЛЖНА возвращать состояние обработки вместе с данными этапа, достаточными для отображения его на странице этапа и в списке этапов для авторизованного пользователя.
- **FR-003**: Страница этапа ДОЛЖНА показывать переходные состояния как сообщение с визуальным индикатором ожидания, не представляя неполные результаты как окончательные.
- **FR-004**: Страница этапа ДОЛЖНА показывать предупреждение, когда разбор протокола завершён, но определение спортсменов ещё не завершено.
- **FR-004a**: Страница этапа ДОЛЖНА показывать переходный статус, когда все строки протокола определены, но зависимый пересчёт разрядов ещё не завершён.
- **FR-005**: Пока состояние переходное, страница этапа ДОЛЖНА автоматически обновлять состояние и результаты с интервалом 5 секунд; при готовности, ошибке или уходе со страницы обновление ДОЛЖНО прекращаться.
- **FR-006**: Система ДОЛЖНА показывать готовый этап без индикатора ожидания и без автоматических обновлений.
- **FR-007**: При окончательной ошибке Event ДОЛЖЕН сохранить статус ошибки соответствующей стадии и безопасное для показа `errorMessage`. Авторизованный пользователь ДОЛЖЕН видеть статус и сообщение; если сообщение отсутствует, интерфейс ДОЛЖЕН показать локализованный текст для этой стадии. Автоматическое ожидание ДОЛЖНО прекращаться для всех трёх статусов ошибки. Новый протокол ДОЛЖЕН очищать прежний `errorMessage`.
- **FR-008**: Гость ДОЛЖЕН получать доступ только к этапам с полностью завершённой обработкой протокола; этапы с переходным или ошибочным состоянием не ДОЛЖНЫ появляться в публичном списке, открываться по прямому адресу или раскрывать частичные результаты через связанные публичные запросы.
- **FR-008a**: Ошибка разбора протокола ДОЛЖНА сразу переводить этап в `parsingError`; автоматический повтор разбора не выполняется.
- **FR-009**: При временной ошибке автоматического обновления страница ДОЛЖНА сообщить о проблеме и продолжить обновление, пока состояние остаётся переходным.
- **FR-010**: Список этапов для авторизованного пользователя ДОЛЖЕН показывать актуальное состояние обработки каждого этапа с протоколом.
- **FR-011**: Все новые пользовательские сообщения о состоянии, ошибках и ожидании ДОЛЖНЫ быть локализованы.
- **FR-012**: Этап ДОЛЖЕН перейти в готовность только после того, как каждая строка текущего протокола связана со спортсменом и завершён зависимый пересчёт разрядов.
- **FR-013**: Состояние обработки ДОЛЖНО меняться по подтверждённому завершению разбора, идентификации и пересчёта разрядов, а не по предположению, основанному на времени ожидания.
- **FR-014**: Завершение устаревшей фоновой стадии не ДОЛЖНО менять состояние этапа после замены его протокола.
- **FR-015**: Пересчёт разрядов ДОЛЖЕН выполняться последовательно для каждого затронутого спортсмена в одной фоновой стадии; готовность этапа ДОЛЖНА фиксироваться только после успешного завершения всей стадии. Повторная доставка стадии ДОЛЖНА быть безопасной.
- **FR-016**: Повторная доставка события разбора ДОЛЖНА быть безопасна: этап, который уже покинул состояние разбора, не создаёт повторные строки и не возвращается в разбор.
- **FR-017**: После замены протокола результаты прежнего файла не ДОЛЖНЫ появляться в текущих результатах этапа.
- **FR-017a**: Перед разбором нового протокола система ДОЛЖНА удалить дистанции и строки прежнего протокола и пересчитать разряды затронутых спортсменов по оставшимся результатам. Записи спортсменов и общие группы сохраняются. Устаревшая задача с прежним токеном не ДОЛЖНА удалять результаты нового поколения.
- **FR-017b**: После очистки результатов старого протокола Event ДОЛЖЕН публиковать отдельное событие завершения очистки; только оно запускает разбор заменяющего протокола после commit. Первичное создание этапа продолжает запускать разбор через `EventParsingStarted`.
- **FR-018**: Повторное сохранение состояния без нового перехода не ДОЛЖНО повторно запускать обработку протокола.
- **FR-019**: Идентификация ДОЛЖНА сохранять связь каждой обработанной строки со спортсменом до перехода к следующей строке. При `EventProcessingFailed` система ДОЛЖНА удалить результаты неудачного протокола; повторный запуск ДОЛЖЕН требовать обновления протокола.
- **FR-020**: Для строк текущего протокола ДОЛЖНЫ последовательно выполняться быстрое сопоставление и полное сопоставление оставшихся спортсменов без промежуточной очереди нераспознанных строк. Этап переходит к пересчёту разрядов только после проверки всех строк.
- **FR-021**: Ошибка любой стадии ДОЛЖНА публиковать `EventProcessingFailed`; после commit узкий обработчик ДОЛЖЕН запускать Application-сервис очистки дистанций и строк текущего протокола и пересчёта разрядов затронутых спортсменов. Ошибка с прежним токеном не ДОЛЖНА очищать данные нового запуска.

### Key Entities

- **Состояние обработки этапа**: стадия текущего протокола, определяющая сообщение, предупреждение, индикатор ожидания и необходимость автоматического обновления.
- **Этап**: соревнование, которое владеет текущим протоколом, статусом его обработки и текущими результатами.
- **Распознавание спортсмена**: фоновая стадия сопоставления строк разобранного протокола с зарегистрированными спортсменами.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В каждом из семи состояний обработки пользователь видит соответствующее состояние страницы не позднее чем через 5 секунд после его появления.
- **SC-002**: Пользователь, создавший или изменивший этап с протоколом, может отличить разбор, незавершённое распознавание, обновление разрядов, готовность и ошибку каждой стадии без ручного обновления страницы.
- **SC-003**: После готовности, ошибки или ухода пользователя со страницы этапа автоматические обновления не выполняются.
- **SC-004**: Гость не может получить переходный либо ошибочный этап через публичный список или прямой адрес.
- **SC-005**: Открытый список этапов с переходным статусом показывает его изменение не позднее чем через 5 секунд и прекращает запросы после готовности всех видимых этапов или ухода пользователя.
- **SC-006**: После ошибки идентификации результаты неудачного протокола очищены; обновление протокола запускает все стадии с новым токеном и доводит этап до готовности.

## Assumptions

- Переход к следующей стадии подтверждается завершением предыдущей; наличие фоновой задачи или истечение времени само по себе не означает завершение.
- Для первого выпуска не добавляется отдельная команда повтора обработки: авторизованный пользователь видит ошибку и может обновить протокол после исправления причины.
- Отдельная команда ручного возобновления идентификации не входит в фичу; после ошибки новый запуск возможен только через обновление протокола.
- Авторизованные пользователи могут видеть все этапы и их состояние обработки в карточке и списке; гостям доступны только этапы с завершённой обработкой протокола.
