## Контекст и границы

Спек закладывает технический фундамент для постепенного, страница за страницей, перехода фронтенда
BFO Base с Blade-шаблонов на современный SPA. Существующий Blade-сайт продолжает работать без
изменений; новые страницы добавляются по одной в SPA-слой. Полная миграция — за рамками этого спека;
здесь поставляется только фундамент: инструменты, соглашения, стратегия сосуществования, базис
аутентификации и два пилотных экрана.

**Выбранный стек** (решения, принятые в рамках этого спека):

| Область | Выбор | Обоснование |
|---|---|---|
| UI-фреймворк | Vue 3 (Composition API) | Уже есть задел на Vue 3; Composition API + TypeScript — современный стандарт |
| Сборщик | Vite | Официальный инструмент Vue; заменяет laravel-mix/webpack |
| Язык | TypeScript (strict) | Типобезопасность с первого дня |
| Библиотека компонентов | PrimeVue 4 | Богатые data-centric компоненты (DataTable, Paginator и т.д.) — хорошо подходит для спортивной платформы |
| SPA-роутинг | Vue Router 4 | Стандарт для Vue 3 |
| API-контракт | Laravel API Resources, префикс `/api/v1/*`, стандартный envelope | Без внешних библиотек; версионирование и envelope с первого дня |
| Аутентификация SPA | Laravel Sanctum — API-токены (Bearer) | Понятная модель; расширяется на мобильный клиент в будущем; нет сложности CSRF |
| URL-пространство SPA | Подпуть `/app/*` | Чёткое разделение от Blade-маршрутов |
| Тестирование фронта | Vitest + Vue Test Utils | Нативно для Vite; быстро |
| Тестирование API | PHPUnit (новый неймспейс `Tests\Feature\Api\V1\`) | Единый стандарт тестирования проекта |
| Агрегат пилота | Соревнования | Два экрана: публичный список + приватное создание; оба уровня доступа; Application-слой уже готов |

## Clarifications

### Session 2026-08-28

- Q: Должен ли `POST /api/v1/competitions` быть доступен любому аутентифицированному пользователю или только пользователю с отдельной ролью администратора? → A: Любой аутентифицированный пользователь; отдельные роли и permissions пока не вводятся.
- Q: Должен ли Bearer-токен сохраняться только в текущей вкладке, или после открытия новой вкладки пользователь тоже должен оставаться авторизованным? → A: Токен сохраняется между вкладками; Sanctum-токен имеет ограниченный срок жизни (ориентир — 1 день).
- Q: Как SPA должен получать новый access-токен после истечения его срока действия? → A: Refresh-токены не используются; после истечения Sanctum-токена пользователь выполняет обычный login заново.
- Q: Должен ли `GET /api/v1/competitions` возвращать поля `created` и `updated`, если запрос публичный, но содержит валидный Bearer-токен? → A: Да; анонимный запрос получает базовые поля, а запрос с валидным Bearer — базовые поля плюс `created` и `updated`.
- Q: Должна ли дата окончания соревнования быть не раньше даты начала, включая возможность соревнования в один день? → A: Да; `to` должно быть больше или равно `from`, однодневные соревнования разрешены.

## Архитектурные ограничения бэкенда

Эти ограничения вытекают из конституции проекта и ОБЯЗАТЕЛЬНЫ к соблюдению:

- **Новые API-контроллеры** живут в `App\Bridge\Laravel\Http\Controllers\Api\V1\` — новый
  подпространство имён, визуально и структурно отделённый от легаси-контроллеров
  `App\Bridge\Laravel\Http\Controllers\Api\`.
- **Новые API-маршруты** регистрируются в отдельном новом провайдере
  (`ApiV1RoutesServiceProvider`) — отдельный файл от существующего `ApiRoutesServiceProvider`.
  Старый провайдер и его маршруты (`/api/…`) не трогаем.
- **Domain- и Application-слои не модифицируются** — никаких новых сервисов, репозиториев или
  доменных классов. V1-контроллеры обращаются к существующим Application-layer сервисам напрямую.
- **Никаких новых Services или Repositories** — новый код следует слоям
  Application/Domain/Bridge/Infrastructure; Services/Repositories — легаси.
- **Sanctum** уже доступен в Laravel 13; новых Composer-пакетов для аутентификации не нужно.

## Пользовательские сценарии и тестирование *(обязательный раздел)*

### User Story 1 — Посетитель просматривает список соревнований (Приоритет: P1)

Незарегистрированный посетитель открывает `/app/competitions` в SPA и видит список
ориентировочных соревнований за текущий год. Он может фильтровать по году. Данные приходят из
публичного JSON API. Авторизация не требуется.

**Почему этот приоритет**: Это простейший сквозной срез — сборка SPA → публичный API →
отрисованная страница — доказывает работоспособность всего фундамента до введения сложности
аутентификации.

**Независимый тест**: Открыть `/app/competitions` в режиме инкогнито; увидеть соревнования за
текущий год; переключить фильтр года и убедиться в обновлении списка; в Network-панели
проверить, что `GET /api/v1/competitions` возвращает корректный envelope.

**Сценарии приёмки**:

1. **Дано** анонимный посетитель открывает `/app/competitions`, **Когда** страница загружается,
   **Тогда** он видит список соревнований с названием, диапазоном дат и годом.
2. **Дано** список соревнований открыт, **Когда** посетитель меняет фильтр года, **Тогда**
   список обновляется без полной перезагрузки страницы.
3. **Дано** список соревнований отображается, **Когда** инспектируется ответ API, **Тогда**
   он соответствует стандартному envelope: `{ "data": [...], "meta": { "pagination": {...} } }`.
4. **Дано** API недоступен, **Когда** страница пытается загрузиться, **Тогда** показывается
   понятное сообщение об ошибке, а не пустой экран.
5. **Дано** анонимный посетитель обновляет страницу на `/app/competitions`, **Когда** страница
   перезагружается, **Тогда** SPA shell загружается корректно (нет 404 от сервера).

### User Story 2 — Аутентифицированный пользователь создаёт соревнование через SPA (Приоритет: P2)

Аутентифицированный пользователь открывает `/app/competitions/create` в SPA, заполняет форму
(название, описание, даты, флаг массового старта), отправляет её, и новое соревнование
появляется в списке — без полной перезагрузки страницы.

**Почему этот приоритет**: Это валидирует приватный уровень API, Bearer-токен-поток
аутентификации и путь мутации данных — паттерны, которые будут переиспользованы на каждом
следующем защищённом экране SPA.

**Независимый тест**: Войти через `POST /api/v1/auth/login`, с полученным токеном вызвать
`POST /api/v1/competitions` с валидными данными, убедиться, что соревнование создано и ответ
соответствует single-resource envelope.

**Сценарии приёмки**:

1. **Дано** неаутентифицированный посетитель открывает `/app/competitions/create`, **Когда**
   страница загружается, **Тогда** он перенаправляется на страницу входа SPA (форма не
   показывается).
2. **Дано** аутентифицированный пользователь находится на списке соревнований, **Когда** он
   нажимает «Создать соревнование», **Тогда** открывается форма создания.
3. **Дано** пользователь заполнил все обязательные поля и отправил форму, **Когда** форма
   отправлена, **Тогда** API-вызов успешен, пользователь видит уведомление об успехе и
   перенаправляется в список, где новое соревнование уже отображается.
4. **Дано** пользователь отправил форму с незаполненными обязательными полями (например, без
   названия), **Когда** валидация на сервере не прошла, **Тогда** форма показывает инлайновые
   ошибки по полям без перехода на другую страницу.
5. **Дано** токен пользователя истёк, **Когда** он пытается отправить форму, **Тогда** SPA
   перенаправляет на страницу входа с сообщением об истечении сессии.
6. **Дано** запрос валиден, **Когда** инспектируется ответ API, **Тогда** он возвращает
   `201 Created` с данными созданного соревнования в стандартном single-resource envelope.

### User Story 3 — Пользователь входит в SPA (Приоритет: P3)

Пользователь вводит учётные данные на странице входа SPA, получает токен и перенаправляется в
защищённый раздел SPA. Последующие API-вызовы из SPA автоматически включают токен. Выход из
системы уничтожает токен на сервере.

**Почему этот приоритет**: Поток входа/выхода — это фундамент аутентификации, от которого
зависят все будущие приватные страницы SPA. Без него US-2 невозможна.

**Независимый тест**: Вызвать `POST /api/v1/auth/login` с валидными учётными данными; получить
токен; вызвать `GET /api/v1/auth/me` с токеном; вызвать `DELETE /api/v1/auth/logout`; убедиться,
что последующие вызовы с отозванным токеном возвращают 401.

**Сценарии приёмки**:

1. **Дано** пользователь отправил корректные учётные данные, **Когда** форма входа отправлена,
   **Тогда** он перенаправляется в дашборд SPA (или на страницу, с которой пришёл) без полной
   перезагрузки.
2. **Дано** пользователь ввёл неверные учётные данные, **Когда** форма отправлена, **Тогда**
   отображается понятное сообщение об ошибке, пользователь остаётся на странице входа.
3. **Дано** аутентифицированный пользователь нажал «Выйти», **Когда** действие завершено,
   **Тогда** токен отозван на сервере и пользователь возвращается в публичную зону SPA.
4. **Дано** пользователь авторизован и открывает новую вкладку браузера с SPA, **Когда**
   вкладка загружается, **Тогда** он по-прежнему аутентифицирован (токен сохранён между
   вкладками).

### User Story 4 — Разработчик добавляет новую страницу в SPA (Приоритет: P4)

Бэкенд-разработчик следует руководству по фронтенду, создаёт новый `.vue`-компонент страницы,
регистрирует маршрут, и новая страница появляется по адресу `/app/{route}` — без влияния на
существующий Blade-сайт или другие страницы SPA.

**Почему этот приоритет**: Это повторяемый паттерн, которому будут следовать все будущие
миграции страниц. Руководство должно делать его однозначным.

**Независимый тест**: Разработчик создаёт страницу «Hello from SPA» по адресу `/app/hello`,
следуя только руководству; убеждается, что она загружается; убеждается, что существующая
Blade-страница `/groups` работает как прежде.

**Сценарии приёмки**:

1. **Дано** SPA установлен, **Когда** разработчик создаёт компонент страницы и регистрирует
   маршрут, **Тогда** страница доступна по адресу `/app/{route}`.
2. **Дано** разработчик обновляет браузер на любом URL `/app/*`, **Тогда** сервер возвращает
   SPA shell — не 404.
3. **Дано** SPA и Blade-сайт работают одновременно, **Когда** открывается Blade-страница,
   **Тогда** она работает точно как прежде (нулевые регрессии).

### Граничные случаи

- **Прямой URL / обновление браузера на маршруте SPA**: Nginx обязан отдавать SPA shell для
  любого пути `/app/*`. Отсутствие этой настройки — ошибка №1 при деплое SPA.
- **Конфликт маршрутов Blade и SPA**: Пространство имён `/app/*` исключает конфликты. Впредь
  никаких Blade-маршрутов под `/app/*` создаваться не должно.
- **Истёкший или отозванный токен**: API возвращает 401; SPA удаляет токен и перенаправляет
  пользователя на страницу входа с понятным сообщением. Новый токен получается обычным login;
  refresh-токены не используются.
- **Сосуществование старого API (`/api/…`)**: Старые маршруты API остаются нетронутыми. Новые
  маршруты — под `/api/v1/…`. Пересечений нет.
- **Сосуществование Vite + laravel-mix**: Оба сборщика выводят результат в непересекающиеся
  пути под `public/`. Старый `mix-manifest.json` и новый Vite-манифест не конфликтуют.
- **Безопасность хранения токена**: Bearer-токен хранится в Pinia memory store и сохраняется
  между вкладками через `localStorage`; XSS-защита обязательна. Sanctum-токен имеет ограниченный
  TTL в 1440 минут (1 день), после истечения требуется обычный login.

## Требования *(обязательный раздел)*

### Функциональные требования

**Фронтенд-фундамент**

- **FR-001**: Репозиторий ДОЛЖЕН включать SPA-сборку на базе Vite (Vue 3 + TypeScript),
  производящую готовые к продакшену статические ресурсы, независимо и без конфликтов с
  существующей сборкой laravel-mix.

- **FR-002**: Весь новый фронтенд-код ДОЛЖЕН быть написан на TypeScript со строгой проверкой
  типов (`strict: true`). Сборочный конвейер ДОЛЖЕН завершаться ошибкой при наличии
  TypeScript-ошибок.

- **FR-003**: Проект ДОЛЖЕН применять единый стиль кода фронтенда через ESLint (flat config,
  ESLint 9+) и Prettier, запускаемые одной командой `npm run lint`. Конфигурация ESLint ДОЛЖНА
  включать плагины `eslint-plugin-vue` и `typescript-eslint` и запрещать: использование `any`,
  неиспользуемые переменные, прямые мутации props, `console.log` в продакшн-коде.

- **FR-004**: PrimeVue 4 ДОЛЖЕН быть установлен и настроен как библиотека компонентов
  (тема Aura). Минимум компоненты пилота (DataTable, Column, InputText, Button, Toast,
  DatePicker) регистрируются глобально в `main.ts`.

**Стандарты фронтенд-кода (Frontend Foundation)**

- **FR-004a**: Репозиторий ДОЛЖЕН содержать файл `FRONTEND.md` с явно зафиксированными
  правилами (манифест): соглашения об именовании файлов и компонентов, паттерн API-вызовов,
  правила управления состоянием (Pinia), правила маршрутизации (Vue Router), структура
  директорий, команды разработки/сборки/тестирования.

- **FR-004b**: Все компоненты SPA ДОЛЖНЫ быть написаны в стиле Composition API с `<script setup
  lang="ts">`. Options API запрещён для нового кода (разрешён только в старых Vue-компонентах
  Blade-сайта).

- **FR-004c**: API-вызовы ДОЛЖНЫ делаться исключительно через центральный Axios-клиент
  (`api/client.ts`). Прямые вызовы `fetch` или `axios.create()` внутри компонентов запрещены.

- **FR-004d**: Глобальное состояние ДОЛЖНО управляться только через Pinia stores. Передача
  данных между несвязанными компонентами через `provide/inject` или event bus запрещена.

- **FR-004e**: Каждый тип, возвращаемый из API, ДОЛЖЕН быть типизирован в `api/types.ts`.
  Использование `any` или необъявленных типов для API-ответов запрещено.

**Сосуществование SPA**

- **FR-005**: Все маршруты SPA ДОЛЖНЫ обслуживаться под URL-префиксом `/app/*`. Ни один
  существующий Blade-маршрут или URL не изменяется.

- **FR-006**: Сервер (Nginx) ДОЛЖЕН возвращать SPA HTML shell для любого URL, совпадающего с
  `/app/*`, включая прямую навигацию и обновление браузера, чтобы Vue Router мог обрабатывать
  маршруты на стороне клиента.

- **FR-007**: Все существующие автотесты ДОЛЖНЫ оставаться зелёными после введения фундамента
  SPA. Blade-сайт не модифицируется.

**API аутентификации**

- **FR-008**: `POST /api/v1/auth/login` ДОЛЖЕН принимать email и пароль, валидировать
  учётные данные и возвращать Sanctum API-токен в стандартном envelope:
  `{ "data": { "token": "...", "token_type": "Bearer" } }`.

- **FR-008a**: Sanctum personal access tokens ДОЛЖНЫ иметь серверный срок действия 1440 минут
  (1 день), заданный через `sanctum.expiration`. После истечения токен считается недействительным;
  refresh-токены и endpoint `/api/v1/auth/refresh` в этой фиче не используются.

- **FR-009**: `DELETE /api/v1/auth/logout` ДОЛЖЕН отзывать токен текущего пользователя.
  Требует валидный Bearer-токен. Возвращает 204 No Content при успехе.

- **FR-010**: `GET /api/v1/auth/me` ДОЛЖЕН возвращать базовый профиль аутентифицированного
  пользователя (id, name, email) в стандартном envelope. Требует валидный Bearer-токен.

- **FR-011**: Все защищённые API-эндпоинты ДОЛЖНЫ возвращать `401 Unauthorized` со стандартным
  error envelope при вызове без валидного токена.

**Публичный API соревнований**

- **FR-012**: `GET /api/v1/competitions` ДОЛЖЕН возвращать постраничный список соревнований в
  стандартном collection envelope. Аутентификация не требуется.

- **FR-013**: Эндпоинт ДОЛЖЕН принимать необязательный query-параметр `?year=` для фильтрации
  по году. При отсутствии параметра — по умолчанию текущий год (согласованно с поведением
  Blade-сайта).

- **FR-014**: Каждый элемент соревнования в коллекции ДОЛЖЕН включать как минимум: `id`,
  `name`, `description`, `from`, `to`, `year`, `mass`.

- **FR-014a**: `GET /api/v1/competitions` остаётся публичным endpoint. При валидном Bearer-токене
  каждый элемент дополнительно включает `created` и `updated`; без валидного токена эти поля не
  возвращаются.

**Приватный API соревнований**

- **FR-015**: `POST /api/v1/competitions` ДОЛЖЕН создавать новое соревнование. Требует валидный
  Bearer-токен; отдельная роль или permission для создания не требуется. Возвращает `201 Created` с созданным соревнованием в стандартном
  single-resource envelope.

- **FR-016**: Эндпоинт создания ДОЛЖЕН валидировать тело запроса: `name` (обязательное, макс.
  255), `description` (обязательное, макс. 255), `from` (обязательное, валидная дата), `to`
  (обязательное, валидная дата, не раньше `from`), `mass` (необязательное булево, по умолчанию
  false). При ошибке
  валидации — возвращать `422 Unprocessable Entity` со стандартным error envelope с ошибками
  по полям.

- **FR-017**: Эндпоинт создания ДОЛЖЕН передавать идентификатор аутентифицированного
  пользователя в Application-слой (как `UserId`), чтобы поля `created` и `updated` (Impression)
  заполнялись корректно — согласованно с тем, как создаёт соревнования существующая Blade-форма.

**Разделение маршрутов (бэкенд)**

- **FR-018**: Все новые V1 API-эндпоинты ДОЛЖНЫ быть зарегистрированы в новом выделенном
  провайдере (`ApiV1RoutesServiceProvider`). Существующий `ApiRoutesServiceProvider` и его
  маршруты НЕ ДОЛЖНЫ модифицироваться.

- **FR-019**: Все новые V1 API-контроллеры ДОЛЖНЫ находиться в неймспейсе
  `App\Bridge\Laravel\Http\Controllers\Api\V1\`. Существующие контроллеры в
  `App\Bridge\Laravel\Http\Controllers\Api\` НЕ ДОЛЖНЫ модифицироваться.

**Стандартный API response envelope**

- **FR-020**: Все V1-эндпоинты ДОЛЖНЫ использовать следующую структуру ответов:
  - Коллекция: `{ "data": [...], "meta": { "pagination": { "total": N, "per_page": N, "current_page": N, "last_page": N } }, "links": { "first": "...", "last": "...", "prev": null, "next": "..." } }`
  - Единичный ресурс: `{ "data": { ... } }`
  - Ошибки: `{ "errors": [{ "code": "...", "message": "...", "field": "..." }] }`

**Пилотные страницы SPA**

- **FR-021**: SPA ДОЛЖЕН включать публичную страницу `/app/competitions`, отображающую список
  соревнований через PrimeVue DataTable, загружаемый из `GET /api/v1/competitions`. Страница
  ДОЛЖНА включать селектор года, повторно запрашивающий API при смене значения.

- **FR-022**: SPA ДОЛЖЕН включать защищённую страницу `/app/competitions/create` с формой для
  всех обязательных полей (name, description, from, to, mass). При успешной отправке вызывает
  `POST /api/v1/competitions` и перенаправляет в список. Неаутентифицированные пользователи
  перенаправляются на страницу входа SPA.

- **FR-023**: SPA ДОЛЖЕН включать страницу входа `/app/login`, которая вызывает
  `POST /api/v1/auth/login` и при успехе сохраняет токен и перенаправляет пользователя на
  изначально запрошенную страницу (или на список соревнований по умолчанию).

**Безопасность**

- **SEC-001 — Пароли**: Пароли пользователей НИКОГДА не хранятся в открытом виде и не
  возвращаются в API-ответах. Хранение — только в виде bcrypt-хеша (Laravel default).
  Поле `password` исключено из всех JSON-ресурсов через `hidden` на модели.

- **SEC-002 — Bearer-токен на фронте**: Bearer-токен хранится в Pinia memory store и
  `localStorage`, чтобы авторизация сохранялась между вкладками. Sanctum-токен имеет TTL 1440
  минут (1 день). При выходе или истечении токена он немедленно удаляется из памяти и
  `localStorage`, а при выходе на сервере отзывается через `DELETE /api/v1/auth/logout`.

- **SEC-003 — Rate limiting на login**: Эндпоинт `POST /api/v1/auth/login` ДОЛЖЕН быть
  защищён rate limit-ом (не более 10 попыток в минуту с одного IP). Используется
  Laravel throttle middleware. При превышении — 429 Too Many Requests.

- **SEC-004 — XSS: никакого v-html с пользовательскими данными**: В SPA-компонентах
  ЗАПРЕЩЕНО использовать `v-html` для вывода данных, полученных из API или введённых
  пользователем. Vue экранирует шаблонные выражения `{{ }}` автоматически — используем
  только их. Это требование закреплено в ESLint-правиле `vue/no-v-html`.

- **SEC-005 — CORS**: API-эндпоинты `/api/v1/*` ДОЛЖНЫ возвращать корректные CORS-заголовки.
  Разрешённые origin-ы ограничены значением `APP_URL` и `localhost` для разработки.
  `Access-Control-Allow-Origin: *` ЗАПРЕЩЁН для продакшна.

- **SEC-006 — Чувствительные данные в ответах**: API-ресурсы НЕ ДОЛЖНЫ включать
  внутренние поля: `password`, `remember_token`, `created`/`updated` Impression (поля `by`
  содержат user_id — не для публичного API). Impression-поля включаются только для
  аутентифицированных запросов и только там, где это явно требуется.

- **SEC-007 — Валидация на сервере всегда**: Клиентская валидация форм — только UX-помощь.
  Все данные ОБЯЗАНЫ проходить валидацию на сервере независимо от клиента. Контроллер
  никогда не доверяет входным данным без `$request->validate()`.

- **SEC-008 — SQL-инъекции**: Все запросы к БД выполняются через Eloquent/QueryBuilder с
  параметризованными биндингами. Сырые строки в запросах (`whereRaw`, `selectRaw`) с
  пользовательскими данными ЗАПРЕЩЕНЫ без явного биндинга параметров.

- **SEC-009 — Mass assignment**: Все Eloquent-модели ДОЛЖНЫ иметь явный `$fillable` или
  `$guarded`. `$guarded = []` (отключение защиты) ЗАПРЕЩЁН.

- **SEC-010 — HTTPS в продакшне**: Nginx в продакшне ДОЛЖЕН принудительно перенаправлять
  HTTP → HTTPS. SPA-ассеты и API вызываются только по HTTPS. Токены никогда не передаются
  по незащищённому соединению.

**Тестирование**

- **FR-024**: Все V1 API-эндпоинты, поставляемые в этой фиче, ДОЛЖНЫ быть покрыты PHPUnit
  интеграционными тестами в неймспейсе `Tests\Feature\Api\V1\`, с общим базовым тест-кейсом
  (`ApiV1TestCase`), предоставляющим вспомогательные проверки: форма envelope, метаданные
  пагинации, установка Bearer-токена, типовые HTTP-статусы.

- **FR-025**: Фронтенд-гейт качества (`npm run ci`) ДОЛЖЕН запускать lint + typecheck и
  возвращать ненулевой код завершения при любой ошибке.

**Документация и деплой**

- **FR-026**: Репозиторий ДОЛЖЕН включать руководство по фронтенду (`FRONTEND.md`), охватывающее:
  структуру директорий, как добавить новую страницу SPA, как вызвать API (публичный и приватный),
  основы библиотеки компонентов, поток аутентификационного токена, команды разработки и сборки.

- **FR-027**: Репозиторий ДОЛЖЕН включать инструкцию по деплою, охватывающую: сборку
  фронтенд-ресурсов, настройку Nginx для SPA-роутинга `/app/*` и сосуществование с
  существующими ресурсами.

### Ключевые сущности

- **SPA Shell**: Точка входа `index.html`, обслуживаемая для всех маршрутов `/app/*`.
  Загружает Vue + Vue Router + PrimeVue + Pinia.
- **Auth Store (Pinia)**: Хранит текущий токен и данные пользователя. Токен живёт в памяти и
  `localStorage` для сохранения между вкладками и имеет TTL 1440 минут (1 день), заданный
  Sanctum на сервере. Предоставляет `login()`, `logout()` и реактивное состояние
  `isAuthenticated`. После 401 из-за истечения токена очищает состояние и предлагает обычный login.
  Используется API-клиентом и navigation guards Vue Router.
- **API Client**: Настроенный экземпляр Axios, автоматически прикрепляющий Bearer-токен к
  каждому запросу и глобально обрабатывающий 401, перенаправляя на `/app/login`.
- **V1 API Controller**: Тонкий инвокабельный action-класс в
  `App\Bridge\Laravel\Http\Controllers\Api\V1\`. Вызывает Application-layer сервисы напрямую
  (например, `ListCompetitionsService`, `AddCompetitionService`), оборачивает результат в
  Laravel API Resource.
- **API Resource**: Laravel `JsonResource` / `ResourceCollection` в
  `App\Bridge\Laravel\Http\Resources\Api\V1\`. Обеспечивает стандартный формат envelope.
  `CompetitionResource` сериализует `ViewCompetitionDto` в формат envelope и добавляет `created`
  и `updated` только для запроса с валидным Bearer-токеном.
- **ApiV1RoutesServiceProvider**: Единая точка регистрации всех маршрутов `/api/v1/*`.
  Отдельный файл от легаси `ApiRoutesServiceProvider`.
- **ApiV1TestCase**: Абстрактный PHPUnit базовый класс в `Tests\Feature\Api\V1\` со
  вспомогательными проверками: форма envelope, метаданные пагинации, установка заголовка
  Bearer-токена, типовые HTTP-статусы (200, 201, 401, 422).

## Критерии успеха *(обязательный раздел)*

### Измеримые результаты

- **SC-001 — Скорость онбординга**: Разработчик, впервые работающий с фронтендом проекта,
  следует руководству и запускает дев-сервер с отображением пилотной страницы менее чем за
  30 минут.

- **SC-002 — Скорость гейта качества**: `npm run ci` (lint + typecheck) завершается менее чем
  за 60 секунд на всей фронтенд-кодовой базе.

- **SC-003 — Загрузка публичной страницы**: `/app/competitions` загружается и отображает данные
  менее чем за 2 секунды на стандартном широкополосном соединении с холодного старта.

- **SC-004 — Покрытие API тестами**: 100% V1 API-эндпоинтов, поставленных в этой фиче,
  покрыты PHPUnit интеграционными тестами, валидирующими: HTTP-статус, форму envelope и ключевые
  поля ресурса.

- **SC-005 — Нулевые регрессии**: Все существующие PHPUnit-тесты остаются зелёными после
  введения фундамента.

- **SC-006 — Корректность auth-потока**: Полный цикл вход → доступ к защищённому эндпоинту →
  выход → 401 проверяем через API-тесты и вручную через SPA менее чем за 2 минуты.

- **SC-007 — Изоляция маршрутов**: Старые эндпоинты `/api/…` и все Blade-маршруты продолжают
  работать без изменений; ни один маршрут из старых провайдеров не затронут.

- **SC-008 — Полнота инструкции по деплою**: Разработчик выполняет продакшн-деплой фронтенда,
  следуя только задокументированной процедуре, без обращений к коллегам.

- **SC-009 — Брут-форс защита**: `POST /api/v1/auth/login` возвращает 429 после 10 попыток
  с одного IP за минуту. Проверяется интеграционным тестом.

- **SC-010 — Нет утечки пароля**: Ни один API-ответ (успешный, ошибочный, отладочный) не
  содержит поле `password` или его хеш. Проверяется тестом на эндпоинт `/api/v1/auth/me`
  и любой другой ответ, включающий данные пользователя.

- **SC-011 — XSS ESLint-гейт**: Наличие `v-html` в любом SPA-компоненте приводит к
  провалу `npm run lint`. Нулевых исключений (`eslint-disable`) не должно быть без
  явной проверки ревьюером.

## Допущения

- **Список соревнований публично доступен в новом API**: В существующем Blade-сайте список
  соревнований публичен. Новый `GET /api/v1/competitions` следует той же политике — авторизация
  не требуется. Эндпоинт создания защищён, согласованно с поведением Blade-сайта. Это даёт
  естественную пару публичный + приватный без каких-либо изменений политики доступа.

- **Форма создания соревнования соответствует существующей Blade-форме**: Пилотная страница
  создания охватывает те же поля, что и существующий `CompetitionDto`: `name`, `description`,
  `from`, `to`, `mass`. Никаких дополнительных полей или правил валидации в этом спеке не
  вводится.

- **Application-слой и доменные контракты не модифицируются**: V1-контроллеры вызывают существующие
  `ListCompetitionsService` и `AddCompetitionService` напрямую — это полноценные Application-layer
  сервисы с чистыми DTO-контрактами. Никакие легаси Services или Repositories не трогаются.
  Домен соревнований — один из наиболее проработанных в проекте, именно поэтому он выбран как
  пилот.

- **Sanctum уже доступен**: Laravel Sanctum включён в Laravel 13. Новый Composer-пакет не нужен.
  Sanctum-specific модель/адаптер и настройки размещаются в `Infrastructure/Sanctum`; Domain User
  не получает трейт `HasApiTokens`.

- **Blade-сайт остаётся полностью нетронутым**: Никакие Blade-шаблоны, маршруты или
  Blade-контроллеры не затрагиваются. Старая сборка laravel-mix продолжает создавать
  `public/mix-manifest.json` для Blade-сайта; Vite собирает в отдельный путь.

- **Тема PrimeVue**: Используется тема Aura (дефолтная для PrimeVue 4). Кастомная тема выходит
  за рамки этого спека.

- **Нет мобильной/адаптивной вёрстки**: Пилотные страницы должны корректно работать только
  на десктопе.

- **Нет i18n в SPA**: Один язык на текущем этапе. Локализация SPA будет рассмотрена в будущем
  спеке.

- **Хранение токена**: Bearer-токен хранится в Pinia memory store + `localStorage` для
  сохранения между вкладками. Sanctum-токен имеет TTL 1440 минут (1 день); после истечения
  пользователь выполняет обычный login заново. Refresh-токены не используются.

- **Нет CDN**: Статические ресурсы обслуживаются Nginx напрямую. CDN-интеграция — задача
  будущего.

- **Модель деплоя не меняется**: Схема деплоя `git pull + docker compose up -d` сохраняется.
  Шаг сборки фронтенда добавляется в Dockerfile, чтобы ресурсы были предварительно собраны
  в образе.
