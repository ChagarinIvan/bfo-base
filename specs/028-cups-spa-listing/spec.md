# Feature Specification: SPA-листинг кубков

**Feature Branch**: `028-cups-spa-listing`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "Перенести страницу листинга кубков на SPA, добавить JSON API с фильтрами по году, названию и видимости для авторизованных, использовать лёгкий узкий DTO и удалить старый legacy API."

## User Scenarios & Testing

### User Story 1 - Просмотреть кубки в SPA (Priority: P1)

Посетитель открывает раздел кубков в SPA и получает список кубков с выбором года,
поиском по названию и переходами к существующим страницам кубка и его таблицам.

**Why this priority**: Листинг является основной пользовательской точкой входа и должен
работать без Blade-страницы.

**Independent Test**: API request-тест и component-тест SPA подтверждают загрузку списка,
выбор года, поиск, пагинацию, состояния загрузки/ошибки/пустого результата и ссылки.

**Acceptance Scenarios**:

1. **Given** посетитель открывает `/app/cups`, **When** страница загружается, **Then** она
   выбирает доступный год по умолчанию и показывает только видимые кубки этого года.
2. **Given** список загружен, **When** посетитель выбирает другой год, **Then** отправляется
   новый запрос и отображается список выбранного года.
3. **Given** список загружен, **When** посетитель вводит название, **Then** список обновляется
   по частичному регистронезависимому совпадению после debounce, а короткий запрос не вызывает
   некорректную фильтрацию.
4. **Given** API возвращает несколько страниц, **When** посетитель меняет страницу, **Then**
   SPA загружает соответствующую страницу и сохраняет фильтры.
5. **Given** строка кубка отображена, **When** посетитель нажимает название или ссылку таблицы,
   **Then** открывается соответствующий существующий URL кубка или группы.

### User Story 2 - Управлять видимостью списка (Priority: P2)

Аутентифицированный пользователь фильтрует кубки по состоянию «видимый/невидимый», а
анонимный посетитель не получает доступа к этому фильтру или скрытым кубкам.

**Why this priority**: Служебный просмотр невидимых кубков нужен редакторам, но не должен
раскрывать скрытые данные публичному посетителю.

**Independent Test**: API request-тесты выполняют одинаковые запросы анонимно и авторизованно,
а SPA-тест проверяет доступность фильтра только после гидрации auth store.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован, **When** он выбирает «невидимый», **Then** API возвращает
   только невидимые активные кубки с сохранёнными фильтрами года и названия.
2. **Given** пользователь авторизован, **When** он выбирает «все», **Then** API возвращает
   видимые и невидимые активные кубки.
3. **Given** пользователь анонимен, **When** он запрашивает параметр видимости или открывает
   страницу, **Then** параметр игнорируется/недоступен, а ответ содержит только видимые кубки.
4. **Given** пользователь выходит из системы после выбора служебного фильтра, **When** список
   обновляется, **Then** скрытые кубки и служебные столбцы не остаются видимыми.

### User Story 3 - Обслуживать listing через узкий API-контракт (Priority: P2)

Клиент получает компактную запись кубка, достаточную для listing, без тяжёлых данных
деталей и без зависимости от legacy Blade-сервиса.

**Why this priority**: Узкий контракт уменьшает payload и позволяет безопасно удалить старую
реализацию listing, не затрагивая detail и admin flows.

**Independent Test**: контрактный/API-тест проверяет поля, фильтры, pagination headers,
ограничение видимости и отсутствие legacy web listing route.

**Acceptance Scenarios**:

1. **Given** корректный запрос к `/api/v1/cups`, **When** API отвечает, **Then** каждая запись
   содержит только идентификатор, название, год, тип, число этапов, дату последнего этапа,
   группы и авторизованные impression/action-поля согласно контракту.
2. **Given** запрос содержит неизвестный или пустой параметр, **When** API валидирует запрос,
   **Then** возвращается стандартная ошибка валидации без SQL-ошибки.
3. **Given** legacy Blade listing больше не нужен, **When** маршруты проверяются, **Then**
   `/cups` не регистрируется, а существующие `/cups/{id}/show` и admin/detail actions работают.

## Edge Cases

- Поиск с ведущими/замыкающими пробелами обрезается; пустое значение отключает фильтр имени.
- Год вне перечисления отклоняется стандартной ошибкой валидации.
- Запрос с `visible` анонимного пользователя не может вернуть невидимые записи.
- Пустой результат показывает понятное состояние без ошибки и без устаревших строк.
- Сохранённый фильтр видимости после logout сбрасывается к публичному состоянию.
- У кубка без событий дата последнего события отображается пустой, а группы остаются доступными.
- Ошибка API сохраняет выбранные фильтры и показывает возможность повторить загрузку.

## Requirements

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять публичный JSON GET endpoint `/api/v1/cups`.
- **FR-002**: Endpoint ДОЛЖЕН поддерживать фильтры `year`, `name`, `visible`, `page` и `perPage`.
- **FR-003**: `year` ДОЛЖЕН проверяться по существующему набору допустимых годов, а `name`
  ДОЛЖЕН обрезать пробелы и искать частичное регистронезависимое совпадение.
- **FR-004**: Анонимный запрос ДОЛЖЕН возвращать только активные видимые кубки и игнорировать
  попытку запросить невидимые или все записи.
- **FR-005**: Авторизованный запрос ДОЛЖЕН поддерживать режимы только видимые, только невидимые
  и все активные записи.
- **FR-006**: API ДОЛЖЕН возвращать стандартный paginated `Slice` с pagination headers проекта.
- **FR-007**: Listing DTO ДОЛЖЕН быть узким и не включать данные, необходимые только для detail,
  расчётов или экспорта.
- **FR-008**: SPA ДОЛЖНА иметь маршрут `/app/cups`, загружать годы и кубки через API и отображать
  loading, error и empty states.
- **FR-009**: SPA ДОЛЖНА поддерживать фильтры года и названия, pagination и ссылки на существующие
  cup detail/table URLs.
- **FR-010**: SPA ДОЛЖНА показывать фильтр видимости только авторизованным пользователям и
  сбрасывать служебное состояние при logout.
- **FR-011**: Для авторизованного пользователя listing ДОЛЖЕН показывать impression/action
  столбцы согласно существующим паттернам SPA; анонимному пользователю они недоступны.
- **FR-012**: После переноса `/cups` listing route, старый Blade listing action/service/search DTO,
  не используемые только этим listing, ДОЛЖНЫ быть удалены; detail и admin cup routes остаются.
- **FR-013**: Новые и изменённые backend и SPA поведения ДОЛЖНЫ быть покрыты узкими unit,
  API request и component tests; существующие cup detail/admin тесты должны продолжить проходить.
- **FR-014**: Все новые пользовательские тексты ДОЛЖНЫ быть локализованы.

### Key Entities

- **Cup listing item**: компактное представление активного кубка: id, name, year, type,
  events count, last event date, groups и доступные authenticated impressions/actions.
- **Cup listing criteria**: нормализованные значения года, названия, режима видимости и pagination.
- **Visibility mode**: публичный режим только visible и авторизованные режимы visible/invisible/all.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Посетитель может открыть SPA-листинг и применить год, название и пагинацию без
  перехода на Blade `/cups`.
- **SC-002**: Авторизованный пользователь может получить каждый из трёх режимов видимости,
  а анонимный запрос не получает невидимых кубков во всех API-тестах.
- **SC-003**: 100% полей listing API покрыты контрактным тестом, а payload не содержит полей,
  предназначенных только для detail/calculation/export.
- **SC-004**: В production route list отсутствует `/cups` listing route, при этом существующие
  cup detail/admin routes и их regression tests остаются рабочими.
- **SC-005**: Все новые SPA/API тесты проходят, а стандартные quality gates изменённых слоёв не
  выявляют новых ошибок форматирования или типов.

## Assumptions

- Существующая auth-система, `OptionalAuthenticateApiV1`, `Year`, `Slice` и правила pagination
  переиспользуются.
- URL `/app/cups` является каноническим SPA URL; ссылки navbar меняются на него.
- Detail кубка и операции create/edit/delete/table/export не входят в эту фичу и остаются legacy
  web-поверхностями до отдельной спецификации.
- Для имени используется debounce и минимальная длина поиска, согласованная с текущими SPA listings.
- “Удаление старых legacy API” означает удаление старого Blade listing entrypoint и его уникальных
  DTO/service зависимости, а не удаление существующих API/detail contracts других сущностей.
