# Feature specification: Последний перерасчёт разряда спортсмена

**Feature Branch**: master, текущая ветка сохранена
**Created**: 2026-11-01
**Status**: Implemented and locally validated
**Input**: Полный spec-kit. Хранить у Person время последнего перерасчёта разряда
и причину. Новые поля являются частью PersonView рядом с текущим разрядом,
доступны только авторизованным пользователям. Новый блок UI не нужен.

## User scenarios and testing

### User story 1: Последний успешный расчёт, P1

Ответственный за данные видит, когда разряд конкретного спортсмена был рассчитан
последний раз, независимо от того, поменялся ли итоговый разряд.

Independent test: выполнить два успешных расчёта в разные моменты, затем сбой.

1. Given Person без метаданных, when расчёт успешен, then сохранены время и причина.
2. Given разряд не меняется, when успешный расчёт повторён, then время обновлено.
3. Given сохранены метаданные, when расчёт/сохранение падает, then прежние значения сохранены.
4. Given старые Person, when применена миграция, then оба поля неизвестны, старые даты не выдумываются.

### User story 2: Причина расчёта, P1

Ответственный отличает ручной запуск от обработки протокола, ежедневной проверки
и других существующих источников перерасчёта.

Independent test: каждому действующему источнику соответствует однозначная причина.

1. Given источник запуска, when расчёт выполнен, then сохранено его enum-значение.
2. Given очередь/массовый расчёт, when выполняется задача, then причина не теряется,
   время относится к исполнению расчёта, а не постановке задания в очередь.
3. Given остальные изменения Person, when меняется имя/клуб, then metadata расчёта не меняется.

### User story 3: Доступ через PersonView, P2

Авторизованный потребитель получает метаданные вместе с текущим разрядом спортсмена.

Independent test: сравнить guest/auth ответы существующих Person endpoints.

1. Given авторизованный пользователь, when получен PersonView, then новые nullable поля доступны.
2. Given гость, when получен тот же PersonView, then новые поля отсутствуют, rankId доступен как прежде.
3. Given Person ещё не пересчитывался после миграции, when auth читает PersonView, then оба поля null.

### Edge cases

- WithoutRank также является успешным результатом расчёта.
- Повторное исполнение задания является новым успешным расчётом, сохраняется последнее время выполнения.
- Отсутствующий/выключенный Person не получает metadata и сохраняет прежнюю обработку not found.
- Ошибка транзакции откатывает и разряд, и metadata, и сохранённую историю.
- Часовой пояс и формат времени следуют текущим timestamp-контрактам проекта.
- Миграция не запускает массовый расчёт и не переписывает актуальные разряды.

## Requirements

- **FR-001**: Person MUST хранить nullable время последнего успешного расчёта.
- **FR-002**: Person MUST хранить nullable причину из закрытого набора действующих источников.
- **FR-003**: Каждый успешный расчёт MUST атомарно обновлять оба поля вместе с rank state,
  включая случай неизменившегося разряда. Ошибка MUST сохранять прежнее committed состояние.
- **FR-004**: Все действующие пути расчёта MUST передавать корректную причину; очередь сохраняет источник.
- **FR-005**: Существующие Person MUST получить null/null без недостоверного backfill.
- **FR-006**: Новые поля MUST входить в существующий PersonView вместе с rankId,
  но сериализоваться только для authenticated, в camelCase. Нового endpoint/UI нет.
- **FR-007**: Commands, транзакции, lock, Impression updated и PersonRanksUpdated MUST сохранять контракты.
- **FR-008**: Изменения MUST иметь unit/integration/API tests, полный quality run и updates запись.

### Key entities

- Person, его актуальный разряд и metadata последнего расчёта.
- Причина расчёта, ограниченный набор бизнес-источников.
- PersonView, существующее представление с авторизованной группой полей.

## Success criteria

- **SC-001**: 100% действующих путей расчёта классифицированы и покрыты проверками.
- **SC-002**: Успех, неизменившийся разряд и rollback дают ожидаемые metadata.
- **SC-003**: Ни один guest PersonView не содержит новых полей, auth получает их и разряд вместе.
- **SC-004**: Полный набор гейтов проходит; миграция обратима и не меняет исходные разряды.

## Assumptions and clarifications

- Пользователь выбрал БД/API без UI и явно ограничил доступ authenticated.
- Это поля существующего PersonView, не отдельный resource.
- Историческое время неизвестно, поэтому null вместо фиктивной даты миграции.
- Полный прогон включает specify/review/plan/review/tasks/analyze/implement/converge.
- Ветку автоматически не переключать, deploy/commit/push не входят в этот запрос.
- Существующий Eloquent Person остаётся REF-13; чистая модель и mapper отдельная
  ограниченная задача манифеста. Новые framework зависимости в Domain не добавляются.

### Confirmed reason categories

- manual: явный ручной пересчёт и ручная активация/изменение даты активации.
- protocol: обработка/замена/очистка протокола и изменение привязки результатов к Person.
- daily: проверка истечения разрядов и наступления отложенной активации.
- refill: существующая административная команда полного перерасчёта.

Причина описывает источник операции; пользовательский request не выбирает её.
Generic queue jobs сохраняют переданную причину, старые payload без неё используют manual.
