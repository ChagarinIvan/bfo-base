# Инструкции для Codex

Перед любой задачей в этом репозитории учитывать следующие документы:

1. `CLAUDE.md` — краткие правила, применяемые к каждому запросу.
2. `.specify/memory/constitution.md` — главный источник архитектурных принципов,
   ограничений стека и Definition of Done.
3. `.specify/workflows/speckit/workflow.yml` и `.specify/templates/` — правила
   spec-kit и формат артефактов.
4. `.agents/skills/speckit-*/SKILL.md` — Codex-версия команд spec-kit. В проекте
   также сохранены `.claude/skills/speckit-*/SKILL.md` для Claude Code.
5. Актуальную фичу в `specs/`. Сейчас следующая рабочая фича —
   `specs/004-spa-foundation/`; её `spec.md`, `plan.md`, `research.md`,
   `data-model.md`, `contracts/` и `checklists/requirements.md` нужно читать
   перед реализацией. `tasks.md` для неё ещё не создан.

При навигации по коду и рефакторинге, если применимо, предпочитать MCP-инструменты
`phpstorm-index`. Если инструменты недоступны в текущей сессии, использовать
`rg` и стандартные средства проекта без блокировки задачи.

Для Codex использовать команды spec-kit в skills-режиме с `$speckit-*`:
`$speckit-constitution`, `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`,
`$speckit-tasks`, `$speckit-analyze`, `$speckit-implement` и `$speckit-converge`.
Default integration в `.specify/integration.json` — `codex`; Claude-интеграция
установлена параллельно и использует `/speckit-*`.

Локальный MCP-сервер подключается к Codex так:

```bash
codex mcp remove phpstorm-index >/dev/null 2>&1
codex mcp add phpstorm-index --url http://127.0.0.1:29175/index-mcp/streamable-http
```

После подключения проверить сервер командой `codex mcp list`. Он должен иметь
статус `enabled`. После изменения конфигурации может потребоваться новый запрос
или сессия Codex, чтобы инструменты появились в доступном наборе.

## Рабочие правила

- Сначала определить, относится ли запрос к существующей спецификации. Для
  новой функциональности сохранять цикл `specify → review → plan → review →
  tasks → implement` и обновлять соответствующие артефакты в `specs/`.
- Не расширять область текущей фичи молча. Если требования расходятся со
  спецификацией или конституцией, зафиксировать расхождение и уточнить его до
  реализации.
- Сохранять незакоммиченные изменения пользователя, особенно изменения в
  `specs/004-spa-foundation/`. Перед правкой пересекшихся файлов проверить
  `git status` и минимизировать дифф.
- Новый код следует целевым слоям `Application / Domain / Bridge /
  Infrastructure`. Новые `Services` и `Repositories` не создавать; фасады
  Laravel не использовать; зависимости передавать через конструктор и
  интерфейсы, где это разумно.
- Для PHP использовать PHP 8.5 / Laravel 13 и импортировать имена через `use`,
  не писать inline-FQCN. Для SPA соблюдать решения и контракты фичи 004.
- Изменения поведения покрывать тестами. Перед завершением пропорционально
  задаче проверять `composer test`, `composer stan`, `composer cs`,
  `composer rector` (или dry-run), запуск приложения и отсутствие новых N+1.
- Не считать задачу завершённой только по изменению кода: сверять результат с
  acceptance scenarios, контрактами и чеклистом соответствующей спецификации.

## Текущая точка проекта

  `003-test-suite-overhaul` уже реализованы; их `tasks.md` содержит историю
  решений и полезные ограничения.
- Стек: PHP 8.5, Laravel 13, MySQL 8.4, Redis 8, Nginx 1.28; фронтенд
  постепенно переводится с Blade на SPA.
- Ветка и текущие изменения могут не совпадать с названиями спецификаций — не
  переключать ветки и не откатывать файлы без явного запроса.
